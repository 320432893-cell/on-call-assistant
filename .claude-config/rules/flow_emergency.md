# 救火型流程

## 文件定位
- **按需加载**:仅当用户报告线上故障、生产事故、严重 bug、数据异常时读
- 本文件**反向规则为主**:救火场景核心不是流程齐整,是**避免二次伤害**
- 与"紧急通道"的区别(关键):
  - **救火型**:线上**已经在出事**,真急,真的不能瞎搞
  - **紧急通道**:用户**主动声明**"我急,跳过深挖,我自己负责"(见 `CLAUDE.md` § 4.7)
  - 两件事名字像但本质不同。救火型**禁止滥用紧急通道**(已经在出事时跳过取证是雪上加霜)

---

## 0. 触发条件
- 用户语气:"挂了 / 崩了 / 报警 / 用户反馈不能用 / 数据对不上 / 线上 500 / 停摆"
- 关键词:**生产 / 线上 / 紧急 / 急救 / 数据丢了 / 跑不动了 / 卡死**
- 用户提供:错误截图 / 日志片段 / 报警消息 / 监控曲线

**不触发**:
- 开发环境的 bug → 走 `flow_legacy_project.md`
- 用户喊"急但还没出事" → 走相应 flow 的紧急通道节,而非本文件

## 1. 反向规则(本文件核心)

### 1.1 禁止猜测修复【强制】
**禁止行为**:
- 看了错误信息就直接改代码"试试看"
- 没复现/没看日志就推断根因
- 给"应该是这里"+ 改代码的组合(没有取证就没有"应该")

**为什么**:猜测修复在故障期等于**埋第二个 bug**。第一个 bug 还没定位,第二个又上线,后续根本分不清是哪个引起的。

**正确做法**:出取证方案(日志/复现步骤/数据快照),让用户跑,看结果再说。

### 1.2 禁止连续尝试【强制】
**禁止行为**:
- 改一处不见效 → 立刻改另一处
- 一个会话里试 ≥ 2 个不同假设的修复
- "也可能是 X" + 直接动手

**为什么**:每次改动都会改变系统状态,**连续改让"是哪次改动让它恢复/恶化"无法归因**。运维事后复盘会骂街。

**正确做法**:一次只验一个假设,不见效**先回滚再换思路**。

### 1.3 禁止绕过取证【强制】
**禁止行为**:
- 没读日志就给方案
- 用户口述错误现象,AI 不问"具体报错文本"就推断
- 用户说"前几天还好的",AI 不问"前几天到现在改了什么"就推断
- 凭训练记忆里的"常见原因"清单直接列方案,跳过本案取证

**为什么**:救火期最大的资源是**还没被自己污染的现场**。绕过取证 = 主动销毁证据。

**正确做法**:取证三件套必拿到一项再开口:
- **错误文本**:具体报错(stack trace / HTTP status / 日志行),不是"出错了"
- **时间线**:什么时候开始的、最近一次正常是什么时候、近期有没有变更
- **影响范围**:多少用户/数据/请求受影响,是否还在恶化

### 1.4 禁止二次伤害【强制】
**禁止行为**:
- 急着 `git reset --hard` / `force push` 回退到"看起来好的"提交(可能丢正在修的改动)
- 急着重启服务/清缓存/删数据,**没先做快照**
- 急着改数据库,**没先 `SELECT ... INTO 备份表`**
- 把生产数据 dump 到本地"分析一下"(数据泄漏风险)

**为什么**:生产环境的"恢复操作"本身就是高风险,救火期人在压力下出错率高,**任何不可逆操作前都必须有快照**。

**正确做法**:任何"恢复"操作前,先按 `workflow.md` § 1.4 出回滚自检表,有快照才动。

### 1.5 禁止单方面"修复完成"宣告【强制】
**禁止行为**:
- 改完代码就说"修好了"
- 没让用户复现"出事场景"就说"应该可以了"
- 监控曲线没回到正常前就说"已恢复"

**为什么**:救火期的"看起来好了"经常是**症状缓解但根因仍在**(比如重启服务暂时正常,但内存泄漏还在),用户回去睡觉,半夜又炸。

**正确做法**:汇报必须包含三项:
- **复现验证**:出事场景现在执行什么结果
- **监控验证**:相关指标曲线是否回到基线
- **根因说明**:这次出事到底是什么(不是"修了某行",是为什么那行会出事)

## 2. 正向最简流程(参考)

```
问题发生
    ↓
[1. 拿取证三件套(错误文本 / 时间线 / 影响范围)]
    ↓
能否复现?
├─ 能 → [2a. 获取复现步骤] → [3. 定位层级] → [4. 设计取证方案]
└─ 不能 → [2b. 拿日志/监控/近期变更] → [3. 判断层级]
    ↓
[5. 一次只验一个假设]
    ↓
验证不通过 → 回 [3] 换假设(不要连续试)
验证通过  → [6. 出根因说明 + 复现验证 + 监控验证]
```

**层级判定参考**:
- 应用层(代码 bug):错误集中在某模块/函数
- 数据层(数据异常):错误源于输入数据/迁移/不一致
- 基础设施层(资源/网络):错误源于 OOM / 磁盘满 / 网络抖动 / 第三方挂
- 配置层(部署/环境):错误源于配置漂移 / 环境变量缺失 / 版本不一致

## 3. 与其他规则的交互

- 不可逆操作:仍走 `workflow.md` § 1.4 回滚自检(本文件 § 1.4 是其强制触发条件之一)
- Git 操作:仍走 `dangerous_bash.sh` hook 拦截
- 数据操作:配合 `data.md` 的多步写入失败模式
- 取证完成、根因明确,后续修复改动:走 `flow_legacy_project.md`(修复属于"老代码改动")

---

## 4. 阻断条件(总)

- 没拿到取证三件套任一项就改代码 → **[阻断] 先取证**
- 一次会话试 ≥ 2 个不同假设的修复 → **[阻断] 先回滚上一个,只验一个**
- 不可逆操作(重启/清缓存/改数据/force push)无快照 → **[阻断] 先走 § 5 回滚自检**
- 汇报"修好了"但无复现验证 / 监控验证 / 根因说明 → **[阻断] 补齐三项再宣告**

---

## 5. 反模式

- ❌ 训练记忆给"常见原因"列表替代本案取证
- ❌ 看错误信息就推断根因
- ❌ 一个会话改多个地方
- ❌ 没快照就动数据/服务
- ❌ 用紧急通道豁免本文件的反向规则(紧急通道针对探索/收敛,救火型不豁免)
- ❌ 监控没恢复就汇报"已修复"
