# 风险识别协议

## 文件定位
- **按需加载**:仅当主流程进入"风险识别阶段"时读
- 本协议替代任何"经典风险点枚举清单",AI 必须在每次新项目时按本协议**现场推理**,不依赖记忆
- 配套 `info_guidance.md`(信息缺口的引导漏斗)

---

## 0. 协议结构

风险识别 = **A 推理树** + **D 双向对照** + **业务维度反向探测** + **C 对抗角色** + **E 推理日志公开** + **二次补充**

五件套缺一不可。AI 在风险识别阶段必须**逐项执行**并**输出推理日志**(过程,不只是结论)。

---

## 1. A 推理树(系统性视角)

对项目本身,按 4 个分支推理:

### 1.1 这个系统跟谁打交道?(列依赖)
对每个外部依赖(数据源 / API / 系统 / 文件 / 用户输入),问 4 个反向问题:
- **会不会变?** 变了我怎么办?
- **会不会慢?** 慢了我怎么办?
- **会不会挂?** 挂了我怎么办?
- **会不会骗你?**(返回错值/格式变/被劫持) 骗了我怎么办?

### 1.2 这个系统有什么状态?(列状态)
对每个状态(内存变量 / 文件 / DB / 第三方副作用),问 3 个问题:
- **状态丢了会怎样?**
- **状态错了会怎样?**
- **状态被偷看到会怎样?**(隐私/安全)

### 1.3 这个系统接收什么?产出什么?
- **输入异常**:空 / 错 / 超大 / 重复 → 各自怎么办?
- **输出影响**:
  - 输出错了,谁会受影响?
  - 输出延迟了,谁会受影响?
  - 输出丢了,谁会受影响?

### 1.4 这个系统跑在什么时间维度?
- 跑两次,结果一致吗?(确定性)
- 跑到一半挂了,从哪继续?
- 跑到一半被 kill / 断电,数据完整吗?

---

## 2. D 双向对照(基于用户场景反推)

**前提**:用户必须先讲清三层场景:

```
L_a 主流程:从开始到结束,理想情况下做了什么?(列步骤)
L_b 数据流:数据从哪来,到哪去?(列流向)
L_c 时间线:这一切大概多久完成?(列耗时)
```

**反推**:对每个节点应用 13 个反推维度,问"如果不理想会怎样":

### 2.1 流程 6 维(对 L_a 每一步)
- **失败**:这一步失败会怎样?
- **慢**:这一步慢 10 倍会怎样?
- **重复**:这一步执行两次会怎样?
- **并发**:多人同时触发这一步会怎样?
- **中断**:这一步执行到一半被打断会怎样?
- **跳过**:这一步被跳过会怎样?

### 2.2 数据 4 维(对 L_b 每一段)
- **空**:数据为空 / 缺字段 怎样?
- **错**:类型错 / 格式错 / 值越界 怎样?
- **大**:数据量超预期 10 倍 怎样?
- **重**:重复数据 怎样?

### 2.3 时间 3 维(对 L_c 每一段)
- **慢**:慢 10 倍 怎样?
- **超时**:无响应 怎样?
- **卡**:进程不动 怎样?

---

## 3. 业务维度反向探测(8-10 维)

用户描述可能漏掉某些业务维度。AI 完成 D 反推后必须主动追问:

| 维度 | 探测话术 |
|------|---------|
| 权限 | "你描述里没提'权限',这个项目涉及多角色 / 数据隔离吗?" |
| 金额/数量 | "涉及钱 / 库存 / 配额 这些'数得清且不能错'的吗?" |
| 状态 | "有没有'未提交 / 已提交 / 已完成 / 已撤销'这种状态流转?" |
| 历史 | "有老数据要兼容吗?数据迁移 / 版本演进 / 归档?" |
| 通知 | "出事了谁先知道?用户 / 你 / 监控 / 没人?" |
| 撤销 | "用户做了之后能反悔吗?反悔后已影响的下游怎么办?" |
| 时间 | "有定时任务 / 时区 / 截止日期 / 时效性吗?" |
| 空间 | "数据存哪?能装下吗?清理策略?" |
| 并发 | "同一个东西会被多人同时改吗?" |
| 审计 | "谁做了什么,要不要留痕?" |

**规则**:用户回答"有"则按 A/D 重新推理该维度;回答"无"则记录一条假设。

---

## 4. C 对抗角色(外部视角,3 个起步)

AI 扮演三个对抗角色,每个角色提 3 题:

### 4.1 恶意用户
- 重复点同一按钮 100 次?
- 输入超长字符串 / SQL 注入 / 路径遍历?
- 同时开多个会话操作?

### 4.2 烂网络
- 请求中途断?
- 响应延迟 30 秒?
- 响应是 502 / 503 / 504 / 重定向风暴?

### 4.3 烂硬件
- 磁盘写满?
- 内存涨到上限?
- 进程被 kill / OOM / 断电?

---

## 5. E 推理日志强制公开

每条反推必须**给出过程**,不只是结论:

```
[推理日志格式]
反推维度 X:____
应用对象(项目里哪个节点):____
推理过程:____(为什么这是个风险 / 为什么不是)
结论:□ 风险 □ 不是风险
应对:□ 防御方案 ____ □ 接受现状(理由 ____) □ 待验证假设(假设 ____)
```

**禁止**:
- 只写"已考虑/无问题"不给过程
- 只列维度名不应用到具体节点
- 不公开思考直接给应对

---

## 6. 终止条件(三个机制全满足才能离开风险识别阶段)

### 机制 1:每个反推维度都已应用
- A 推理树 4 分支全走完
- D 反推 13 维度对 L_a/b/c 每个节点都过一遍
- 业务维度 10 项全探测
- C 对抗角色 3 个全扮演

### 机制 2:每个反推出的风险点都有应对
- 防御 / 接受 / 待验证假设,三选一,不能空着

### 机制 3:用户主动确认
- AI 输出风险列表 + 应对清单
- 用户确认"无补充"

---

## 7. 二次补充触发再推理

任何阶段用户补充了新信息(新场景 / 新依赖 / 新维度) → AI 必须**回到 D 反推**对新增节点应用 13 维度,然后重走机制 1-3。

---

## 8. 输出格式(给用户看的)

风险识别完成后必须输出:

```
[风险识别报告]

— 用户场景三层 —
L_a: ____
L_b: ____
L_c: ____

— A 推理树结论 —
依赖反推:____ 项,识别风险 ____ 个
状态反推:____ 项,识别风险 ____ 个
输入输出反推:____ 项,识别风险 ____ 个
时间维度反推:____ 项,识别风险 ____ 个

— D 双向对照结论 —
对节点 [节点名] 应用 13 维度,识别风险 ____ 个

— 业务维度探测结论 —
权限:有/无 | 金额:有/无 | 状态:有/无 | ...

— C 对抗角色结论 —
恶意用户:识别风险 ____ 个
烂网络:识别风险 ____ 个
烂硬件:识别风险 ____ 个

— 风险点 + 应对清单 —
| # | 风险描述 | 来源 | 应对 |
|---|---------|------|------|

— 待验证假设清单 —
| # | 假设内容 | 验证方式(将来跑起来如何确认) |
|---|---------|---------------------------|

— 推理日志 —
(完整推理过程,逐条)
```

---

## 9. 反模式(违反即视为协议失效)

- ❌ 跳过推理树 / 反推 / 业务维度 / 对抗角色 中任一项
- ❌ 推理日志写"已考虑"不给过程
- ❌ 反推得出风险但无应对
- ❌ 用户补充新信息后不回到反推
- ❌ 用枚举的"经典风险目录"代替现场推理
