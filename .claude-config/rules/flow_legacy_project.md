# 老项目流程

## 文件定位
- **按需加载**:仅当 CLAUDE.md 项目类型判定为"老项目/收敛型"时读
- 配套脚本:`~/.claude/hooks/legacy_health_check.sh`(门 1 + 门 2 自动跑)
- 老项目最大风险:**地基烂还硬改导致越改越烂**。本流程的核心是"先体检再改"

---

## 0. 触发条件
- 用户对已有项目提改动需求
- 关键词:封装 / 重构 / 加功能 / 修 bug / 把 X 改成 Y / 优化

---

## 1. 流程总图

```
1. 用户描述改动需求
2. 门 1 皮毛检查(脚本自动)
3. 门 1 异常 → 高熵预警 + 三种走法,停止
4. 门 1 通过 → 门 2 健康检查(脚本自动)
5. 门 2 异常 → 健康报告 + A/B/C 走法,停止
6. 门 2 通过 → 门 3 本次改动可行性(AI 语义判断)
7. 门 3 阻塞 → 改动影响图 + A/B/C 走法,停止
8. 门 3 通过 → 现状盘点 + 风格一致性自检
9. 用户复核 + 选走法
10. 进入增量改动
11. 工具链自动检查
```

---

## 2. 门 1:皮毛检查(自动)

**调用**:`bash ~/.claude/hooks/legacy_health_check.sh gate1 <项目路径>`

**检查项**:
- 项目大小(文件数 / 总行数)
- 依赖管理(requirements.txt / pyproject.toml 是否存在 + 是否锁版本)
- 测试存在(tests/ 目录 + test_*.py 数量)
- README 存在
- 版本控制(.git 存在)

**异常标准**:
- 无 README + 无 requirements + 无 tests + 文件平铺 100+ 文件 → **高熵项目**
- 任一基础设施缺失 → **基础设施缺口**

**异常处理**:输出"高熵预警报告"+ 三种走法,停止等用户。

---

## 3. 门 2:健康检查(自动)

**调用**:`bash ~/.claude/hooks/legacy_health_check.sh gate2 <项目路径>`

**检查项**:
- ruff 违规密度(违规数 / 千行代码)
- 文件大小分布(>500 行文件数)
- 函数大小分布(>100 行函数数)
- 循环依赖(import-linter 或 pydeps)
- 最近修改时间分布(看是否混乱叠加修改)

**评分粗略**:
- ruff < 50/千行 + 无 >500 行文件 + 无循环依赖 → **健康**
- 50-200/千行 / 有 >500 行文件 → **一般**
- > 200/千行 / 有循环依赖 / 函数 >300 行 → **烂**

---

## 4. 门 3:本次改动可行性(AI 语义判断)

AI 必须做:
- 找到本次需求要改的文件(grep / 调用关系分析)
- 评估这些文件的代码质量
- 评估"按需求直接改"的成本(改几个文件 / 影响几个调用方 / 测试是否存在)
- 评估"先重构再改"的成本

**决策**:
- 健康 → 直接进步骤 8
- 一般但本次改动局部 → 直接进步骤 8,但提示"顺手清理范围"
- 改动会扩散到 ≥ 3 个烂文件 → **阻塞**,出 A/B/C 走法

---

## 5. A/B/C 走法模板

### A. 直接改(预计 ___ 分钟/小时)
- 风险:____
- 适合:这个项目临时用 / 一次性

### B. 先解决阻塞 + 再改(预计 ___)
- 步骤:
  1. ____
  2. ____
  3. 然后加 X 功能,只动改造后的相关文件
- 适合:长期用

### C. 只重构不加新功能(预计 ___)
- 重构完用户复核再决定加不加 X
- 适合:想先看重构成本和质量

## 6. 现状盘点(走法 A 进入施工前必出)

```
[现状盘点]

— 架构层次 —
分层 / 平铺 / 状态机 / 注册表 / 函数式 / 混合

— 命名风格 —
snake_case / camelCase / 混用

— 已用范式 —
列出代码里能识别的范式(若有)

— 依赖技术栈 —
关键库列出

— 测试覆盖 —
% 或 "无"
```

---

## 7. 改动影响图(每次改动前必出)

```
[改动影响图]

— 改动落点 —
- 文件 ____ + 函数 ____

— 影响调用方(grep 列出) —
- 调用位置 ____

— 影响测试 —
- 对应测试文件 ____(若有)

— 风格一致性自检 —
□ 本次改动是否引入新风格?(否 / 是,原因 ____)
□ 本次改动是否引入新范式?(否 / 是,原因 ____)
□ 本次改动是否新建已有 utils?(grep 证据)

— 改名 / 删除后扫描 —
□ 旧名残留:已 grep,无 / 有(位置 ____)
□ 孤儿函数:已 grep,无 / 有(列表 ____)
```

---

## 8. 老项目特别红线

### 风格分裂红线
- 老代码用 snake_case → 新加代码不准用 camelCase
- 老代码函数式 → 不准硬塞 OOP 类
- 老代码 print → 老项目沿用 print(直到统一改造为止),不能新代码 logging 老代码 print

### 范式分裂红线
- 老代码 if/elif → 新加分支沿用 if/elif,除非改造整段
- 老代码无状态机 → 新加流程沿用,除非改造整段

### 重复造轮子红线
- 必须 grep 已有 utils,优先复用
- 新建函数前 grep 同名 / 类似函数

### 幽灵引用红线
- 改名 / 删除后必须 grep 旧名 → 无残留
- 改函数签名后必须 grep 调用方 → 全部更新

---

## 9. 紧急通道

用户显式"急,直接改":
- 跳过门 2 / 门 3 / 现状盘点
- 但门 1 必跑(< 1 分钟,基础设施红线不能破)
- 输出降级声明:列出未做的检查 + 可能的风险

---

## 10. 反模式

- ❌ 不跑门 1/门 2 直接改老项目
- ❌ AI 自行决定走 A/B/C 不让用户选
- ❌ 改动后不 grep 调用方
- ❌ 引入新风格不说明
- ❌ 重新实现老项目已有 utils
