# 老项目流程

## 文件定位
- **按需加载**:仅当 CLAUDE.md 项目类型判定为"老项目/收敛型"时读
- 配套脚本:`~/.claude/hooks/legacy_health_check.sh`(门 1 + 门 2 自动跑)
- 老项目最大风险:**地基烂还硬改导致越改越烂**。本流程的核心是"先体检再改"

---

## 0. 触发条件
- 用户对已有项目提改动需求
- 关键词:封装 / 重构 / 加功能 / 修 bug / 把 X 改成 Y / 优化

---

## 1. 流程总图

```
1. 用户描述改动需求
2. 门 1 皮毛检查(脚本自动)
3. 门 1 异常 → 高熵预警 + 三种走法,停止
4. 门 1 通过 → 门 2 健康检查(脚本自动)
5. 门 2 异常 → 健康报告 + A/B/C 走法,停止
6. 门 2 通过 → 门 3 本次改动可行性(AI 语义判断)
7. 门 3 阻塞 → 改动影响图 + A/B/C 走法,停止
8. 门 3 通过 → 现状盘点 + 风格一致性自检
9. 用户复核 + 选走法
10. 进入增量改动
11. 工具链自动检查
```

---

## 2. 门 1:皮毛检查(自动)

**调用**:`bash ~/.claude/hooks/legacy_health_check.sh gate1 <项目路径>`

**检查项**:
- 项目大小(文件数 / 总行数)
- 依赖管理(requirements.txt / pyproject.toml 是否存在 + 是否锁版本)
- 测试存在(tests/ 目录 + test_*.py 数量)
- README 存在
- 版本控制(.git 存在)

**异常标准**:
- 无 README + 无 requirements + 无 tests + 文件平铺 100+ 文件 → **高熵项目**
- 任一基础设施缺失 → **基础设施缺口**

**异常处理**:输出"高熵预警报告"+ 三种走法,停止等用户。

---

## 3. 门 2:健康检查(自动)

**调用**:`bash ~/.claude/hooks/legacy_health_check.sh gate2 <项目路径>`

**检查项**(本脚本独有):
- ruff 违规密度(违规数 / 千行代码)
- 最近修改时间分布(看是否混乱叠加修改)

**与 engineering_audit hook 的分工**(避免重复):
- 文件大小 >500 行 / >300 行 (.vue) → `engineering_audit.sh` 已自动扫
- 循环依赖 (pydeps) / 死代码 (vulture) → `engineering_audit.sh` 已自动扫
- 大函数 >100 行 → ruff PLR0915 + engineering_audit 双层覆盖
- .gitignore / 大文件入库 / tests/ 缺失 → `engineering_audit.sh` 红线层

> 老项目接手时:门 1 (legacy_health_check gate1) → 门 2 (gate2 跑独有项) → engineering_audit 自动报全景。

**评分粗略**:
- ruff < 50/千行 + 无 >500 行文件 + 无循环依赖 → **健康**
- 50-200/千行 / 有 >500 行文件 → **一般**
- > 200/千行 / 有循环依赖 / 函数 >300 行 → **烂**

## 4. 门 3:本次改动可行性(AI 语义判断)

### 4.1 改前必出: 散弹度测绘 + 雷区清单查表【强制】

改任何老代码前,**必须**先做:

```
[散弹度测绘]
- 本次需求关键词: ____ (用户给 / AI 提议用户确认)
- 关键词出现位置: ____ (grep 结果, 文件:行号, 客观事实)
- 散弹度: N 处

[雷区清单查表]
- 本次涉及的文件是否在 docs/PROJECT_PLAN.md 雷区清单里?
  □ 命中 (位置 ____, 用户既定决策: ____ → 直接按既定决策执行)
  □ 未命中
```

> 关键词 grep 是机械事实,AI 糊弄不了。"散弹度"是计数,不是判断。

### 4.2 决策

AI 必须做:
- 找到本次需求要改的文件(grep / 调用关系分析)
- 评估"按需求直接改"的成本(改几个文件 / 影响几个调用方 / 测试是否存在)
- 评估"先重构再改"的成本

**决策**:
- 健康 + 散弹度 ≤ 3 → 直接进步骤 8
- 一般但本次改动局部 + 散弹度 ≤ 3 → 直接进步骤 8,但提示"顺手清理范围"
- 散弹度 ≥ 4 → **阻塞**,出 A/B/C 走法 + 标注是哪种反模式(DIP / 注册表 / 配置硬编码 / 状态机散布,见 code.md)
- 改动会扩散到 ≥ 3 个烂文件 → **阻塞**,出 A/B/C 走法

### 4.3 改后必跑: 散弹回扫【强制】

改完代码后,**必须** grep 当初识别的关键词,确认没有遗漏:

```
[散弹回扫]
- 关键词当初: N 处
- 改后剩余: M 处 (M=0 ✅ / M>0 列出位置: ____)
```

**漏改即阻断**:M > 0 且非"刻意保留"→ **[阻断] 补改或在汇报里写明保留理由**。

## 8. 老项目特别红线

> **2026-05-18 hook 接管声明**:
> - 风格分裂(snake/camel 混用)→ `ruff N` 规则集已物理拦截(`.ruff.toml`)
> - 幽灵引用(改名/删除后旧名残留)→ `rename_audit.sh` hook 在 Edit/MultiEdit 后自动 grep 全项目报警
> - 重复造轮子(死代码 / 未用 import)→ `vulture` + `ruff F401`(pre-commit)接管
>
> 本节红线仍是思考层强制(hook 只查机械模式,语义判断仍需 AI),但**机械层不再依赖 AI 自觉**。

### 风格分裂红线
- 老代码用 snake_case → 新加代码不准用 camelCase(`ruff N` 已物理拦)
- 老代码函数式 → 不准硬塞 OOP 类(语义层,AI 自觉)
- 老代码 print → 老项目沿用 print(直到统一改造为止),不能新代码 logging 老代码 print

### 范式分裂红线
- 老代码 if/elif → 新加分支沿用 if/elif,除非改造整段
- 老代码无状态机 → 新加流程沿用,除非改造整段

### 重复造轮子红线
- 必须 grep 已有 utils,优先复用
- 新建函数前 grep 同名 / 类似函数

### 幽灵引用红线(hook 已接管)
- 改名 / 删除后必须 grep 旧名 → 无残留(`rename_audit.sh` 自动报)
- 改函数签名后必须 grep 调用方 → 全部更新(语义层,AI 自觉 + import-linter 兜底)

---

## 9. 紧急通道

用户显式"急,直接改":
- 跳过门 2 / 门 3 / 现状盘点
- 但门 1 必跑(< 1 分钟,基础设施红线不能破)
- 输出降级声明:列出未做的检查 + 可能的风险

---

## 10. 反模式

- ❌ 不跑门 1/门 2 直接改老项目
- ❌ AI 自行决定走 A/B/C 不让用户选
- ❌ 改动后不 grep 调用方
- ❌ 引入新风格不说明
- ❌ 重新实现老项目已有 utils
