# 规则治理

## 文件定位
- **按需加载**:仅当新增/修改/审计规则文件时读
- 本文件管"规则文件本身怎么写、怎么改、怎么消歧",是元层规则
- 不涉及任何业务流程/项目执行——那些在 `workflow.md` / `flow_*.md`

---

## 1. 规则词定义

| 词汇 | 含义 |
|------|------|
| **禁止/不得** | 绝对不可执行 |
| **必须** | 命中后必须执行 |
| **需先** | 未满足前置条件前不得继续 |
| **默认** | 用户未反对时采用,可被覆盖 |
| **优先** | 多方案时的首选,非强制 |

读规则文件时按本表理解,不擅自降级或升级语气。

---

## 2. 规则层级

- 全局层:跨领域通用规则(`CLAUDE.md`)
- 工作流层:执行约束、横切关注点(`workflow.md`)
- 流程层:按项目类型加载(`flow_new_project.md` / `flow_legacy_project.md`)
- 协议层:专项协议(`risk_reasoning.md` / `info_guidance.md`)
- 专题层:单一领域规则(`code.md` / `gui.md` 等)
- 项目局部层:仅当前项目业务规则(项目内 CLAUDE.md)

**层级使用原则(M3 能上提就上提)**:
- 同一阻断点/同一思想,**完整清单只放最高合适层一处**,其他层只保留"红线 + 单向引用"
- 跨文件引用单向(上层引下层),禁止反向引用、禁止 A→B→C 链式跳读
- 同主题分散在多个文件 = 违规,必须合并或重组

---

## 3. 双轨维护原则(机械层 vs 语义层)

规则体系分两条并行轨道,**新增任何约束前先判定它该走哪轨**——走错轨即视为违反 M1 四维。

### 3.1 机械层(hook / ruff / mypy / import-linter / 其他静态工具)

**特征**:触发即报、可重放、零信任 AI 自觉、退出码或 stderr 可见

**该走机械层的约束**:
- 模式可静态检测(grep / ast / 装饰器扫描)
- 数字阈值(行数 / 大小 / 复杂度)
- 命名规范、import 方向、API 形状
- 危险命令、危险配置硬编码

**禁止**:
- 写"建议性"机械检查(stderr 报但默认放过) — 那是文档不是工具
- 在机械层做语义判断(误报 ≥ 30% 即应回退到 AI 思考层)

**同步**:hook/.ruff.toml/.importlinter 改完 git commit,push/pull 即生效。**不在规则 md 里复述检查清单**——会与工具状态脱节(阶段 2 教训)。

### 3.2 语义层(规则 .md 文件)

**特征**:思想沉淀、业务/架构判断、AI 思考时加载

**该走语义层的约束**:
- 思想范式(状态机 / 注册表 / DIP 抽象 vs 具体 / 失败模式 / 幂等)
- 流程纪律(救火反向规则 / 五层穷究 / 风险识别 5 件套)
- 业务判断(异常分层引擎/服务/边界 / 配置 vs 代码归属 / 接口契约稳定性)

**禁止**:
- 与工具状态强耦合的填空检查表(那是 hook 的事,见 §3.1)
- 把数字阈值写在 md 里(应写在 hook 参数 / ruff 规则配置里)
- "建议/尽量/请考虑"类暧昧词

### 3.3 轨道间引用方向

- **md → hook** 单向引用:规则文档可声明"X 已由 Y hook 接管,本节只留语义层"
- **hook ↛ md** 禁止反向:hook 内不写"详见 X.md § Y"(hook 是机械的,用户看 stderr 直接处置)

### 3.4 新增约束的判定流程

```
触发(踩坑/对抗审计/用户提议)
    ↓
是模式还是语义?
    ├─ 模式 + 可静态检测 → 走 §3.1 机械层 → 查 §3.5 矩阵决定具体道具
    ├─ 语义 + 业务判断   → 走 §3.2 语义层
    └─ 混合              → 拆分:机械部分入 hook,语义部分入 md
        ↓
    跑 §4.1 四维过滤
    机械层:跑 §3.1 误报率自检 + §3.6 hook 单测要求
    语义层:跑 §4.2 M4 上限
```

### 3.5 工具职责矩阵(机械层分工)

机械层下沉到具体道具时,**先查本表选道具,选不到才考虑写 hook**。
原则:**通用规则交成熟工具,hook 只做工具管不到的部分**。

| 检查类型                     | 唯一负责道具                  | 配置位置                 | 禁止另写                 |
|------------------------------|-------------------------------|--------------------------|--------------------------|
| 风格/命名/复杂度/简化/性能   | `ruff check`                  | `.ruff.toml`             | bash 正则、自写 lint     |
| 格式化                       | `ruff format`                 | `.ruff.toml`             | black / autopep8         |
| 类型/可空性/签名             | `mypy --strict`               | `.mypy.ini`              | bash 抓 `def` 关键字     |
| 模块分层依赖                 | `import-linter`               | `.importlinter`          | bash 抓 `import` 关键字  |
| 代码安全(eval/exec/弱哈希)   | `ruff S` + `bandit`           | `.ruff.toml` / pyproject | bash 抓 eval/exec        |
| 依赖 CVE                     | `pip-audit`                   | pre-commit / CI          | 自维护 CVE 列表          |
| 密钥泄漏                     | `detect-secrets`              | `.secrets.baseline`      | bash 正则抓 token        |
| 测试覆盖率                   | `pytest-cov`                  | pyproject `[tool.coverage]` | bash 数测试文件个数   |
| JSON / YAML / TOML 语法      | pre-commit 标准 hook          | `.pre-commit-config.yaml`| 自写语法校验 bash        |
| 系统级危险动作               | bash hook                     | `~/.claude/hooks/`       | 用 lint 工具管 shell     |
| 第三方 CLI 调用反模式        | bash hook                     | `~/.claude/hooks/`       | 强写 ruff 自定义规则     |
| 领域语义反模式(时序泄漏等)   | bash hook                     | `~/.claude/hooks/`       | 强塞 ruff/mypy           |
| 流程胶水(规则激活/迭代约束)  | bash hook                     | `~/.claude/hooks/`       | -                        |

**禁止**:
- 通用规则(前 9 行)写新 bash hook — 已有道具的事
- 把 hook 适用域(后 4 行)塞进 ruff 自定义规则 — 维护成本高、误报率高

### 3.6 bash hook 必带单测(新 hook 强制 / 旧 hook 渐进)

bash 正则脆,错一字符静默失效。**新增 bash hook 必须满足**:
1. **文件头注释**写明"为什么不能用 §3.5 矩阵里的成熟工具",写不出理由即不该存在
2. **同目录配 `tests/test_<name>.sh`**,至少 3 正样本 + 3 反样本(含边界:空文件、巨大文件、含中文/特殊字符)
3. 任一条不满足,**不得合入 manifest.json / settings.json**

**旧 hook**:不一次性补齐,但**修改任一旧 hook 时必须当场补单测**(改即补)。

**禁止**:声称"显然能跑"跳过单测、把测试样本写进 hook 文件本体。

## 4. 写入前检查

- 是否与上层规则冲突
- 是否与同层规则重复
- 是否本应下沉到更局部层级
- **§3 判定的轨道是否正确**

---

## 5. 规则写入要求

每条规则必须明确:
- **触发条件**
- **执行动作**
- **适用边界**

**禁止写入**:无明确触发/动作/边界的空泛说明;"建议""尽量""应该"等无标准表述。

### 5.1 新增规则前的重要性评估(M1 四维过滤)
新增任何强制规则前必须四维自检,缺一项即不写入强制层:

| 维度 | 问题 | 通过标准 |
|------|------|---------|
| 影响 | 违反后影响是否深远? | 跨模块/跨项目/影响交付,非局部细节 |
| 易违反度 | AI 是否易违反? | AI 不主动遵守即出问题(不靠 lint 能查到) |
| 代价 | 违反代价是否大? | 难回滚、数据损坏、生产事故 |
| 可自检 | 自检是否能落地? | 自检项具体可勾选,AI 不会变成"☑全部通过"走过场 |

**未通过任一维度的处理**:
- 影响不深远 → 推荐级附录
- 易违反度低(lint 能查) → 推荐级附录或交给工具链
- 代价小 → 推荐级附录
- 可自检度低 → 推荐级附录或拆分为多条更具体规则

**高代价规则豁免**:涉及数据损坏 / 生产事故 / 不可逆操作的规则,即便 M4 总数超限也不豁免删除——按代价优先保留。

### 5.2 单文件强制规则总数上限(M4 执行容量平衡)
单个规则文件强制规则**不超过 10 条**。超过时必须二选一:
- 合并职责相近的规则
- 把次要规则降级到附录推荐

**原因**:规则数 > 10 时 AI 显著倾向"打勾走过场",违反规则约束 AI 的根本目的。

**例外**:§5.1 高代价豁免条款命中时可超限,但需在文件顶部声明"本文件因高代价规则豁免 M4"。

---

## 6. 规则写入的拒绝引导

当用户要求新增规则时,按以下标准判断是否拒绝:

| 用户要求类型 | 处理方式 | 引导话术 |
|-------------|---------|---------|
| "建议/尽量/考虑"类表述 | 拒绝写入强制规则 | "此条属于建议性质,请放入【推荐清单】而非强制规则" |
| 具体样式/配色/间距/圆角 | 拒绝写入 | "样式细节建议先跑起来再迭代调整,不写入强制规则" |
| 与代码结构无关的交互细节 | 拒绝写入 | "交互细节建议边用边调,如需记录可放入项目备注" |
| 无明确阻断条件 | 拒绝写入 | "请补充'不合规怎么办'的阻断条件后再评估" |
| 未通过 §5.1 四维过滤 | 拒绝写入强制 | "建议降级到附录推荐级或交给 lint/工具链" |

**处理原则**:维护规则文件边界,但不对抗用户意图。拒绝时说明理由并提供替代方案。

## 7. 修改后复查

- 是否与`CLAUDE.md`及相关专题md口径一致
- 跨文件引用是否有效(节标题改了同步更新引用方)
- 是否引入重复主定义
- **是否违反 §6 的拒绝标准**
- **是否违反 §5.1 四维过滤、§5.2 总数上限**
- **跨文件职责重合复查(M2)**:同一阻断点是否被两条规则触发?若是,合并到更上层规则或用单向引用替代;同主题完整清单是否只在一处?
- **§3 双轨判定**:机械层规则是否被错塞进了规则 md?语义层是否被错塞进了 hook?

**引用规范**:跨文件引用必须使用节标题,禁止行号引用。

## 8. 规则冲突处理

按以下优先级:**`flow_emergency.md`(救火型反向红线,最高)** → `CLAUDE.md` → `workflow.md` → `governance.md`(本文件) → 流程层(flow_new / flow_legacy / onboarding) → 专题规则

**为什么救火型最高**:线上故障期任何"流程齐整"的要求都要让位于"避免二次伤害"。其他流程的紧急通道、任务链显式化、置信度阻断在救火期可豁免,但 `flow_emergency.md` 的反向红线**不豁免**。

仍无法归类,**询问用户**。

## 9. 规则执行分级（T1/T2/T3）

规则不砍,但**执行方式分级**——不是所有规则都能靠 AI 自觉,高损失规则必须机械强制。

### 9.1 三级定义

| 级别 | 含义 | 执行方式 | 违反代价 |
|------|------|----------|----------|
| **T1 机械强制** | hook exit 2 阻断,AI 过不去 | `exploration_gate.sh` 等 PreToolUse hook | 方向错误 / 全部返工 |
| **T2 检查点** | AI 在特定时刻输出自检框,用户可见可追问 | AI 自检 + 用户监督 | 遗漏风险 / 次优决策 |
| **T3 最佳实践** | AI 尽力,不强制 | 规则文档存在即可 | 代价可控 |

### 9.2 T1 机械强制清单（≤5 条）

| # | 规则 | hook | 检测方式 |
|---|------|------|----------|
| 1 | 探索型：用户确认前禁止输出代码 | `exploration_gate.sh` (PreToolUse Edit/Write) | 检查状态文件是否有"已确认"标记 |
| 2 | 探索型：必须有 ≥2 方案对比 | 同上 | 确认标记的前置条件 = 方案已输出 |
| 3 | 低理解度阻断 | 同上 | ≤2 维理解度时阻断代码输出 |

**状态流转**：
```
rule_activator 检测到探索型 → 写 /tmp/claude_task_exploratory
AI 输出方案对比 + 用户回复确认词 → rule_activator 写 /tmp/claude_task_confirmed
exploration_gate 检查: exploratory 存在 + confirmed 不存在 → exit 2
```

### 9.3 T2 检查点清单

AI 在以下时刻**必须输出自检框**（格式见 § 9.4）：

| 时刻 | 必检项 |
|------|--------|
| 探索型：输出方案前 | 五层穷究到 L 几 / 信任边界是否深挖 / 对抗分析 |
| 探索型/收敛型：输出代码前 | 影响范围 / 用户已确认范围 |
| 任务完成时 | 范式汇报（用了什么 / 不用什么） |
| 新决策点（方案变更/风险发现） | 双层输出（专业 + 通俗） |

### 9.4 T2 自检框格式

```
[自检] 探索型-方案输出前
✓ 穷究: L3(信任边界已挖)
✓ 方案对比: A/B/C 三选
✓ 对抗: "如果 A 方案错了 → 影响是..."
✗ 待确认清单: 还没列 → 下一步补
```

用户看到 ✗ 可以追问；AI 看到自己的 ✗ 应主动补齐再继续。

### 9.5 双层输出的"继续"豁免

- 用户说"继续"/"做"/"开始" → AI 进入**执行态**，可省通俗层
- 遇到**新决策点**（方案变更 / 风险发现 / 阻断报告）→ 强制恢复双层
- 判定原则不变：**动手即双层,执行态可省,决策点必恢复**

## 10. 反模式

- ❌ 同一阻断点在多个文件主定义
- ❌ 用"建议/尽量"表述写强制规则
- ❌ 未跑 M1 四维就新增强制规则
- ❌ 单文件强制规则超 10 条还硬塞(无高代价豁免声明)
- ❌ 跨文件用行号引用(改一次全坏)
- ❌ 改规则不复查 M2 职责重合
- ❌ 把可静态检测的模式塞进规则 md(违反 §3 双轨,应入 hook)
- ❌ 把业务语义判断写进 hook(误报率 ≥ 30%,应回退到规则 md)
