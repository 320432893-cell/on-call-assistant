# 规则维护流程

## 1. 文件定位

触发:

- 修改、新增、删除、压缩、迁移规则文件。
- 修改 hook、settings、memory、规则索引、规则副本。
- 讨论规则应该保留、删除、下放工具、改写成什么形态。

动作:

- 本文件只管“规则维护时怎么讨论、怎么确认、怎么写入”。
- 本文件不向上引用其他规则，避免读取链路膨胀。
- 默认只改 Codex 副本；原始 Claude 文件未获明确授权不得改。

边界:

- 用户只是问规则内容时，只读解释，不进入写入流程。
- 业务代码任务不加载本文件，除非任务本身是在改规则或 hook。

## 2. 默认状态：讨论态

规则维护默认处于讨论态。

讨论态允许:

- 读取目标文件。
- 分析现有规则。
- 发散规则设计。
- 提出保留、删除、压缩、下放工具、改写方案。
- 说明 AI 执行压力和可能糊弄点。

讨论态禁止:

- 写入规则文件。
- 修改 hook / settings / memory / 索引。
- 删除或覆盖旧规则。
- 把“可以、继续、ok、先这样、看看”当成写入授权。

只有用户明确说以下含义，才进入执行态:

- “确认写入”
- “按这个版本改”
- “执行落盘”
- “可以改这个文件”
- “确认可以修改”

反向审查:

- 授权词收窄会让协作变慢，但规则维护误写的代价更高，所以这里优先保护用户决策权。

## 3. 讨论重点

AI 不只整理用户意见，必须主动暴露自己的执行边界。

讨论时必须覆盖:

- 哪部分执行压力大。
- 哪部分容易被 AI 糊弄成打勾。
- 哪部分容易误伤正常开发。
- 哪部分更适合下放给成熟工具。
- 哪部分会增加上下文读取负担。
- 哪部分可能改变用户原本想法。
- 哪部分不该写入规则。

禁止:

- 纯迎合用户，把所有偏好都写成强规则。
- 只从代码质量看规则，不讨论架构、设计哲学、协作成本、长期维护。
- 把规则维护做成机械清单填空。

## 4. 发散方式

规则维护阶段应尽量发散，但发散必须服务于落地。

AI 至少从以下角度审查:

- 保留: 这条规则解决什么高代价问题。
- 删除: 这条规则是否只是噪音或重复。
- 压缩: 是否能改成更短的触发/动作/边界。
- 下放: 是否应交给 ruff、mypy、import-linter、pytest、pre-commit、CI 或 hook。
- 拒绝: 是否不该写入，因为不可执行、误伤大、读取负担高。
- 长期副作用: 半年后是否会让 AI 或用户更难维护。

边界:

- 不要求引用用户原话做账本。
- 必要时可以复述用户意图，但重点是暴露理解偏差、执行压力和设计取舍。

## 5. 写入前确认

进入执行态前，AI 必须先给拟改摘要。

拟改摘要必须包含:

- 目标文件。
- 准备保留什么。
- 准备删除或压缩什么。
- 准备新增什么。
- 是否只改副本。
- 是否涉及 hook / 工具链下放。
- 是否仍有未决问题。

规则:

- 用户确认拟改摘要后再写。
- 若用户直接给出明确写入授权，可跳过长方案，但仍要在写入前用一句话说明目标文件和写入范围。
- 涉及删除原始规则、改原始 Claude 文件、改全局配置、改 hook 阻断逻辑时，必须单独确认。

## 6. 执行后反馈

每次写入后必须反馈:

- 改了哪个文件。
- 改动影响什么 AI 行为。
- 是否触及原始文件。
- 是否还有未处理冲突或待讨论点。

反馈控制:

- 小改动一句话即可。
- 中大改动列清单。
- 高风险改动必须说明原因、影响和后续风险。

## 7. 本流程的反模式

- 还在讨论就写入。
- 把“可以”“继续”误判成授权。
- 不说执行压力，只把规则整理得好看。
- 不反对用户明显高成本或低收益的规则。
- 能交给成熟工具却写进 Markdown。
- 规则写完不反馈影响。
- 为了完整性增加大量跨文件引用。
