# 浏览器自动化语义规则

## 1. 文件定位

- 本文件管浏览器自动化任务的语义风险，当前默认技术栈为 Playwright。
- Playwright 是当前优先实现；除非用户明确要求，不主动切换 Selenium、RPA 或其他方案。
- 本文件不写成 Playwright API 清单，重点管登录态、等待、句柄、iframe、弹窗、验证码、失败现场、批量执行和用户取证。
- 前端页面开发、用户交互体验、数据写出/合并/去重/覆盖不在本文件展开；只有任务真实命中对应风险时，再分别读取对应规则。

核心目标：自动化脚本可恢复、可取证、少误操作，不靠猜测等待，不在目标系统状态不明时继续提交或抓取。

---

## 2. 触发分级

### 2.1 小脚本：轻量执行

命中场景：

- 一次性打开页面、读取少量公开信息、简单点击或截图。
- 无登录态、无验证码、无批量循环、无写入或提交副作用。

AI 行为：

- 优先使用 Playwright 原生 locator、自动等待和超时。
- 失败时至少保留错误原因和必要截图。
- 不引入复杂会话、检查点、反爬模拟。

### 2.2 中风险：提高取证与恢复

命中场景：

- 需要登录态。
- 批量抓取、下载、翻页、循环操作。
- 目标页面包含 iframe、弹窗、新 tab、动态加载。
- 操作失败后重跑成本较高。

AI 行为：

- 设计登录态检测、等待策略、失败现场自动取证和进度记录。
- 明确检查点或失败清单。
- 用户可能需要配合时，先自动取证，再给用户短步骤取证指令。

### 2.3 高风险：先讨论再写

命中场景：

- 验证码、短信验证、滑块、人机验证。
- 税务、外汇、银行、企业管理系统等强登录态或高价值系统。
- 表单提交、状态变更、审批、删除、批量写入、重复提交可能产生副作用。
- 需要规避风控、模拟人类行为、使用第三方打码或绕过策略。

AI 行为：

- 先讨论授权、合规、目标系统规则、失败影响和回滚方式。
- 默认优先人工介入，不主动设计规避风控。
- 用户明确拍板后再实现，并保留进度、证据和中止路径。

---

## 3. 合规、授权与验证码边界

- 验证码、短信验证、滑块、人机验证默认视为访问控制或风控信号，不当作普通技术障碍。
- 默认策略是人工介入：脚本暂停，提示用户完成验证，然后继续。
- 第三方打码、识别模型、绕过策略、反检测模拟必须先和用户讨论授权、合规和目标系统规则。
- 不确定目标系统是否允许自动化时，先问用户，不替用户假设。
- 需要保存账号、cookie、storage state、session 文件时，必须考虑敏感信息和本地保护。

AI 反向审查：

- 不要主动建议绕过验证码或规避风控。
- 用户要求“自动过验证码”时，必须说明合规、封号、数据安全和维护成本风险。

---

## 4. 登录态、会话与长任务恢复

- 强登录态系统和长任务必须有登录态检测：跳转登录页、特定错误提示、关键元素缺失、接口返回异常等。
- 会话过期处理必须明确：暂停通知用户、保存进度退出、或在用户确认后重登录。
- 批量任务应有检查点或失败清单，避免失败后只能从头重跑。
- 多次运行的浏览器上下文、`user-data-dir`、storage state 应明确复用或隔离策略。
- 运行结束和异常退出应关闭 context/browser，并清理临时目录或说明保留原因。
- 凭据、cookie、storage state 不写入日志，不随便提交到仓库。

AI 反向审查：

- 自动重登录可能需要保存凭据和处理验证码，风险高于暂停让用户介入。
- 复用浏览器配置方便，但会隐藏状态污染；隔离更稳定但登录成本更高。

## 5. 等待、定位与页面句柄

- 优先使用 Playwright 自动等待、语义 locator、role/text/label/test id 等稳定选择器。
- 关键元素要等待明确状态：visible、attached、enabled、detached 或 URL/network 状态。
- 禁止用固定 `time.sleep` 代替等待条件；只有外部系统节流、下载生成等少数场景可例外，并说明理由。
- 页面跳转、新 tab、弹窗、iframe 切换后，必须重新获取 page/frame/locator，不复用旧句柄。
- 动态 ID、时间戳、随机 class 不能作为稳定选择器；录制产物必须人工审查。
- 超时不是单纯调大 timeout，要判断：页面没加载、选择器错、权限失效、接口失败、弹窗遮挡、iframe 未切换。

AI 反向审查：

- `codegen` 只能作为起点，不能直接代表稳定脚本。
- 看到 flaky 等待时，优先找状态条件和页面原因，不靠加 sleep 掩盖。

## 6. 弹窗、iframe、下载上传与注入

- 可能出现 alert/confirm/prompt 时，应在触发操作前注册或准备 dialog 处理。
- 自定义模态框按普通 DOM 处理，但要确认遮罩、焦点和按钮实际生效。
- iframe 和多层 iframe 必须显式定位 frame，跨 frame 后重新定位元素。
- 文件上传优先用 Playwright 官方方式，如 `set_input_files`；系统文件选择器和拖拽上传需要单独验证。
- 文件下载必须等待下载事件、确认文件完整写入，并记录保存路径。
- 原生 Playwright 操作失败后，才考虑 JS/CSS 注入。
- 注入后必须验证页面状态、表单校验、事件触发和后续请求，不以“没有报错”当成功。
- 注入不得绕过目标系统业务校验或权限限制。

AI 反向审查：

- 直接 `evaluate` 改值很容易绕过前端事件链，后续提交可能失败或产生假成功。
- 下载和上传是文件系统副作用，必须确认路径、覆盖和完整性。

## 7. 失败现场与自动取证

- 关键操作失败时，先自动取证，再打扰用户。
- 关键操作包括：登录、提交、跳转、查询、抓取、翻页、下载、上传、状态变更。
- 自动取证优先保存：截图、当前 URL、页面标题、关键 HTML、console 日志、最近失败请求、时间戳。
- 文件名包含时间戳和操作名，避免覆盖。
- 截图和 HTML 可能含敏感信息；保存路径、保留周期和分享范围要谨慎。
- 自动取证不足以定位时，再升级到用户 F12 或业务页面取证。

最低取证集：

- 当前 URL。
- 全屏截图。
- 失败操作名。
- 时间戳。
- 异常消息。

AI 反向审查：

- 没有现场证据就反复改选择器，通常是在猜。
- 失败后继续批量执行可能扩大影响，应先判断是否中止。

---

## 8. 用户协作取证

- 用户不是只能聊天的人；用户可以帮助确认业务提示、登录状态、网络响应、页面元素和真实操作结果。
- 让用户取证前，AI 应先尝试 Playwright trace、截图、HTML、console/network 自动取证。
- F12 取证指令必须短，原则上不超过 3 步。
- 指令必须具体：去哪个面板、做哪个操作、回传什么内容。
- 必须说明用户回传的信息用于判断什么，避免让用户无目的排查。
- 用户反馈和自动取证矛盾时，优先承认不确定，继续取证，不强行解释。

示例：

```md
请帮我取 3 个信息：
1. 打开 F12 -> Network。
2. 重新点一次“查询”。
3. 把失败的红色请求状态码和响应内容发我。
我用它判断是登录过期、参数错误，还是后端接口失败。
```

## 9. 批量执行、进度与数据安全

- 批量抓取、下载、提交应有进度反馈：当前页/总页数、当前记录、成功/失败数量、预计剩余时间。
- 大批量任务应记录单次耗时或阶段耗时，避免用户不知道脚本是否卡住。
- 批量任务必须有失败清单，失败项不要静默丢失。
- 会产生副作用的操作必须考虑幂等：重复提交、重复下载、重复审批、重复写文件是否安全。
- 抓取结果写文件、合并、去重、覆盖用户文件时，触发数据风险门禁。
- 任务中断后必须能说明已完成什么、未完成什么、是否可重跑。

AI 反向审查：

- 抓取和提交不是同一风险等级；提交类自动化必须更保守。
- 重试可能修复偶发失败，也可能造成重复副作用。

---

## 10. 工具与验证分工

优先工具：

- Playwright：默认浏览器自动化实现。
- Playwright trace：复杂失败的首选取证产物。
- `playwright codegen`：生成初始脚本，不直接当成稳定脚本。
- 截图、HTML、console、network 日志：失败现场基础证据。

工具下放：

- 固定 `time.sleep` 由 semgrep 静态规则扫描提醒。
- 基础 Python 风格、异常、import 交给 Ruff。
- 数据输出正确性和幂等由数据规则与测试验证。

验证策略：

- 小脚本至少跑一次目标路径。
- 登录态、批量、下载、提交类任务要验证失败分支和恢复方式。
- 跑不了真实目标系统时，说明未验证项、需要用户配合的业务步骤和剩余风险。
