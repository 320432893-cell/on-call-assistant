# Web 前端语义规则

## 1. 文件定位

- 本文件管 Web 前端的语义风险，不绑定 Vue 3、React、Svelte、ECharts 或具体 UI 库。
- Vue / ECharts 是重要经验来源，但只能作为示例，不作为所有项目的默认强制栈。
- 本文件重点是组件边界、API 契约、异步状态、状态权威源、图表数据、错误边界和 Web 安全。
- 用户交互、按钮、空状态、窗口承载、诊断入口等通用体验问题不在本文件展开；只有任务真实命中交互设计时再读取 `interaction.md`。
- 通用代码范式、异常、日志、测试语义不在本文件展开；只有任务真实命中代码语义判断时再读取 `code.md`。

核心目标：避免前端状态失真、接口契约散落、异步失败不可见、图表误导用户、关键区域一崩拖死整页。

---

## 2. 触发分级

### 2.1 小改：轻量执行

命中场景：

- 文案、样式、局部布局、小展示 bug。
- 不新增接口调用、不改变状态来源、不改变图表数据、不改变关键用户路径。
- 不涉及鉴权、敏感信息、错误边界。

AI 行为：

- 沿用项目现有框架、目录、组件风格。
- 不借小改拆大组件、引入 store、改技术栈。
- 只判断是否破坏既有交互和数据展示。

### 2.2 中改：说明数据流和影响面

命中场景：

- 新增或修改组件职责。
- 新增接口调用、异步数据加载、表格/列表/图表展示。
- 新增跨组件状态、URL query、store、缓存。
- 修改用户可见错误提示、加载状态、空状态。

AI 行为：

- 说明数据从哪里来、在哪里转换、谁是权威源、失败怎么展示。
- 涉及用户交互细节时按需读取 `interaction.md`。
- 保持与项目已有状态管理和 API 封装方式一致。

### 2.3 大改：先讨论再写

命中场景：

- 引入或替换前端框架、状态管理、图表库、请求库、构建工具。
- 改关键业务页面、路由结构、鉴权流程、全局错误处理。
- 改公开 API 契约、字段语义、数据单位、图表统计口径。
- 前端改动会影响后端契约、部署、性能或用户验收路径。

AI 行为：

- 先讨论方案、迁移成本、风险、回滚和验证方式。
- 用户明确拍板后再写。
- 必要时维护项目记忆层中的架构和交付信息。

## 3. 组件与模块边界

- 组件拆分不以固定行数作为唯一标准，而以职责是否混杂、变化点是否独立、复用是否真实存在为准。
- 当一个组件同时承担展示、请求、状态编排、数据转换、图表配置、复杂表单校验时，应考虑拆分。
- Vue 可拆 component / composable；React 可拆 component / hook；其他框架按等价方式处理。
- 小页面、小管理后台、一次性页面不为了显得规范强行拆碎。
- 页面级组件可以编排数据流，但不应把所有业务转换和 UI 细节都堆在模板里。
- 可复用组件应有清晰输入输出，不隐式依赖全局状态。

AI 反向审查：

- 过度拆分会增加跳转成本和维护成本。
- 不拆分会让数据转换、状态和展示互相缠住，后续改动容易误伤。
- AI 必须根据真实变化点判断，不按行数机械拆。

---

## 4. API 调用与前后端契约

- 新增后端接口调用优先走项目已有 API 层、service 层或请求封装，不在组件里散落 `fetch` / `axios` / client 调用。
- 字段映射要有明确位置，不能在模板和多个组件里临时改字段名。
- 前端不能暗改后端语义：`null`、空数组、0、false、缺失字段不能被随意混成同一种展示。
- 请求参数、响应字段、状态码、错误结构变化属于契约风险，必要时同时检查后端规则。
- 接口契约不清时，先查后端代码、接口文档、mock 或运行结果；查不到再问用户，不自己发明字段。
- 鉴权 token、cookie、header、用户身份相关逻辑应集中处理，不散落在普通组件。

AI 反向审查：

- 用户要求“前端先兼容一下”时，要判断这是临时兼容、字段迁移还是掩盖后端契约混乱。
- 如果兼容逻辑会长期存在，应建议放到明确映射层或 adapter，而不是散在模板。

---

## 5. 异步数据与错误边界

- 异步数据必须考虑 loading、success、error、empty；具体展示细节属于交互风险，只有任务真实命中交互设计时再读取 `interaction.md`。
- Promise rejection、`async/await` 异常、请求取消、超时都不能无处理。
- 关键业务区域应有局部错误边界，避免一个图表、表格或第三方组件拖垮整页。
- 错误信息面向用户时，不直接暴露接口原文、堆栈、SQL、内部路径、token 或技术栈细节。
- 请求刷新、搜索、分页、筛选等连续操作要考虑竞态：旧请求返回覆盖新请求、重复提交、取消和防抖。
- 页面卸载或条件变化时，应考虑取消请求、忽略过期响应或清理订阅。

AI 反向审查：

- 不要只写 happy path。
- 如果错误边界成本明显高于收益，可以说明理由，但关键业务区域不能只有全局兜底。

---

## 6. 状态管理与唯一权威源

- 每份状态必须能说清唯一权威源：组件本地、父组件、store、URL query、后端、浏览器存储。
- 仅当前组件使用的状态留本地；跨组件树或跨页面共享的状态才考虑 store。
- 可分享、可回退、刷新后应保留的状态，优先考虑 URL query 或路由参数。
- 后端权威数据不要在前端复制出多个会互相漂移的副本。
- 子组件不直接修改父组件传入的 prop；用框架推荐事件或回调路径修改。
- Store 不应变成所有临时 UI 状态的垃圾桶。
- 浏览器存储中的状态要考虑过期、版本兼容和敏感信息。

AI 反向审查：

- 跨组件复制 state 是高风险信号。
- 为了省事把所有状态塞进 store，会让项目后期更难维护。
- URL query、store、本地 state 三者混用时，必须明确优先级和同步方向。

---

## 7. 图表与数据展示

- 图表和表格必须验证字段存在、单位、时间维度、空数据和异常数据。
- 异常数据要主动怀疑：全 0、全部相同、缺失率高、时间错乱、单位混淆、分类维度缺失。
- 大数据量展示要考虑采样、分页、虚拟滚动、禁用动画、服务端聚合或服务端分页。
- 图表配置不应掩盖数据问题；例如把缺失值默默当 0 可能误导用户。
- 统计口径、数据截止时间、单位换算、筛选范围应有明确来源；是否展示给用户按 `interaction.md` 判断。
- ECharts、Chart.js、D3 等具体库按项目现状使用，不为单个图表轻易换库。

AI 反向审查：

- 图表“能画出来”不等于可信。
- 用户要求快速出图时，也要检查字段、单位和异常数据，否则容易产出看似专业的误导图。

---

## 8. Web 安全与敏感信息

- 前端不能持有不该下发的 secret、服务端密钥、管理凭据。
- 用户可见内容和浏览器控制台不要泄露 token、内部路径、SQL、堆栈、接口原始错误。
- `v-html`、`dangerouslySetInnerHTML` 或等价能力必须有可信来源和 XSS 风险判断。
- 用户输入进入 URL、HTML、Markdown、图表 tooltip、下载文件名时，要考虑转义和注入。
- localStorage/sessionStorage/cookie 存储要区分敏感度、过期和跨站风险。
- 依赖第三方脚本、地图、图表、埋点、登录组件时，要考虑隐私、可用性和失败降级。

AI 反向审查：

- 不要因为“只是内部系统”就展示敏感调试信息。
- 诊断入口和调试模式必须脱敏，不能成为泄露入口。

---

## 9. 测试与工具分工

工具优先负责：

- 格式：Prettier 或项目指定 formatter。
- 基础 lint：ESLint / Biome / Oxlint 等项目现有工具。
- 类型：TypeScript / vue-tsc / svelte-check 等。
- 单元与组件行为：Vitest / Jest / Testing Library。
- 关键用户路径：Playwright / Cypress。

AI 仍需判断：

- 状态权威源是否清楚。
- API 契约是否稳定。
- 图表和数据展示是否可信。
- 异步失败和竞态是否处理。
- 关键用户路径是否覆盖真实风险。

验证策略：

- 小改跑相关 lint/type/test 或做定向手工验证。
- 接口、状态、图表、关键页面改动优先跑对应组件测试或 E2E。
- 跑不了测试时，说明原因、替代验证和剩余风险。
