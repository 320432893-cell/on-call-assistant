# 打包与交付语义规则

## 1. 文件定位

- 本文件管构建产物、打包、分发、版本、配置、运行时依赖和交付验证。
- PyInstaller 是桌面 Python 交付的重要默认经验，但本文件不只服务 PyInstaller。
- 本文件适用于桌面程序、CLI、本地工具、浏览器自动化工具、Web 服务、Docker、zip/目录分发等交付形态。
- GUI 运行体验、浏览器自动化运行策略、架构配置边界不在本文件展开；只有任务真实命中对应风险时，再读取对应规则。

核心目标：交付物在目标环境能跑、能配置、能追溯、能排查，不靠开发机残留依赖侥幸成功。

---

## 2. 触发分级

### 2.1 试包 / 内部验证：轻量执行

命中场景：

- 本机临时试包。
- 给自己验证打包命令。
- 不准备发给其他用户或部署到正式环境。

AI 行为：

- 可以复用开发环境，但必须说明这不是正式交付验证。
- 至少运行一次产物或等价入口。
- 不把“本机能跑”当成正式交付完成。

### 2.2 正式交付：完整执行

命中场景：

- 发给其他用户。
- 部署到测试 / 生产环境。
- 交付 exe、zip、Docker 镜像、Web 服务、CLI 工具包。
- 用户需要按说明安装、配置或运行。

AI 行为：

- 检查依赖、资源、配置、版本、运行时外部依赖、最小可用链路。
- 形成分发清单和用户说明。
- 说明验证结果、未验证项和剩余风险。

### 2.3 高风险交付：先讨论再写

命中场景：

- 多环境构建、生产配置、密钥、账号、证书。
- 自动更新、安装器、服务注册、系统权限、计划任务。
- 数据迁移、覆盖用户文件、会产生不可逆副作用。
- 产物用于客户现场、生产系统、税务/外汇/银行/企业管理系统。

AI 行为：

- 先讨论环境、回滚、密钥、权限、验收路径和失败处理。
- 用户明确拍板后再做。
- 必要时维护项目记忆层和交付说明。

## 3. 依赖、资源与动态加载

- 打包前应识别项目实际依赖来源：`pyproject.toml`、lock 文件、requirements、package manager、子项目依赖。
- 动态加载必须额外检查：`importlib`、`spec_from_file_location`、`__import__`、`sys.path` 修改、插件目录。
- 静态资源必须明确是否随产物分发：模板、图片、图标、配置样例、证书占位、浏览器驱动、Playwright browsers、模型文件。
- 运行时生成内容不要预打进产物：日志、缓存、临时文件、输出目录里的旧结果。
- PyInstaller 目录版默认整体分发 `dist/<name>/`，不能只拿 exe。
- 发现依赖缺失时，优先修构建配置或依赖声明，不靠用户手动复制 site-packages。

AI 反向审查：

- 开发环境能 import 不代表打包环境能 import。
- 动态加载和插件机制是依赖漏收集高发点，不能只看主入口 import。

---

## 4. 构建环境与可复现性

- 正式交付应使用干净或专用构建环境，避免开发机残留依赖污染。
- 内部快速试包可用开发环境，但必须标注“未完成正式交付验证”。
- 构建命令、依赖安装方式、目标平台、Python/Node 版本应可复现。
- Python 包安装若需要联网，默认优先清华源，除非项目已有明确源配置。
- 不擅自切换包管理器或构建工具；先识别项目现有工具链。
- 构建脚本应尽量自动生成版本、收集资源、清理旧产物和执行 smoke test。

AI 反向审查：

- 复现不了的构建等于交付风险。
- 临时手工步骤越多，下一次交付越容易失败。

---

## 5. 配置、密钥与多环境

- 产物不得内置生产密钥、账号、token、证书私钥或不可公开 URL。
- 环境差异应通过配置文件、环境变量、启动参数或部署配置表达，不通过改代码重打包。
- 需用户修改的配置必须说明字段、示例、必填/可选、默认值和错误提示位置。
- 运行时目录必须明确：日志、输出、缓存、下载、临时文件、配置文件。
- 多环境交付要明确 dev/test/prod 的配置来源、密钥隔离和切换方式。
- 配置样例可以随产物分发，但真实密钥不能随产物分发。

AI 反向审查：

- “为了方便先写死配置”会变成交付事故。
- 用户不知道改哪个配置，比程序报错更糟，因为无法自助修复。

---

## 6. 版本、构建元数据与可追溯

- 正式交付产物必须能追溯来源：版本号、git commit、构建时间、构建环境。
- 运行时应能查看版本信息：`--version`、`/version`、`/health`、GUI 关于页、标题栏、VERSION 文件等任选适合方式。
- 临时试包可以轻量标记，但不能和正式版本混淆。
- 版本号不要只靠手写常量；优先由 git tag、commit、构建时间或构建脚本生成。
- 用户反馈问题时，AI 应能从版本信息判断对应代码状态。

AI 反向审查：

- 无版本信息的产物出了问题很难复现。
- 只说“最新包”没有工程意义。

---

## 7. 最小可用链路验证

正式交付前必须跑最小可用链路，按交付形态选择：

- 桌面程序：主窗口可打开，核心操作可执行，资源加载正常，退出流程正常。
- CLI：`--help` 可用，核心命令可跑，错误退出码合理，输出路径可写。
- Web 服务：根路径或健康检查可访问，关键 API 正常，静态资源正常，配置加载正确。
- 浏览器自动化工具：浏览器可启动，登录/人工登录流程明确，关键页面可达，下载/输出路径可写。
- Docker / 服务部署：容器可启动，health check 可过，日志可查看，配置挂载路径正确。

验证失败时，不得视为交付完成；必须说明失败点、修复方案或未验证风险。

AI 反向审查：

- 打包命令成功不等于产物可用。
- 只验证启动不验证核心路径，用户拿到后仍可能不可用。

---

## 8. 分发清单与用户说明

正式分发必须说明：

- 分发内容：exe 目录、zip、Docker 镜像、脚本包、配置样例、资源目录。
- 启动方式：双击、命令行、服务启动、Docker 命令、计划任务。
- 外部运行时依赖：浏览器、Playwright browsers、数据库客户端、VC++ 运行库、系统权限、网络访问。
- 用户需要修改的配置：文件位置、字段含义、示例、必填项。
- 日志位置、输出位置、缓存位置、临时文件位置。
- 常见失败和排查方式。
- 升级或覆盖安装时，哪些文件应保留，哪些可以删除。

PyInstaller 目录版特别注意：

- `exe` 与 `_internal` 或依赖目录必须保持相对位置。
- 不要单独分发 exe。
- 用户说明中要明确“整个目录一起复制/解压后运行”。

AI 反向审查：

- 交付说明不是形式主义；它决定用户能否脱离开发者运行。
- 缺少日志和配置说明，会让后续排障成本转嫁给用户。

---

## 9. 体积、运行时依赖与故障排查

- 正式交付记录产物大小；体积明显异常时再深入排查。
- 体积异常常见原因：环境污染、误收集可选依赖、浏览器/模型/大数据文件、hook 误收集、动态导入扩大依赖。
- 运行时外部依赖必须列清楚，尤其是浏览器、Playwright browsers、驱动、VC++ 运行库、字体、系统库、数据库客户端。
- 打包失败优先排查入口、依赖声明、资源收集、spec/构建配置，不顺手重构业务代码。
- 用户现场故障应优先收集版本、日志、配置摘要、系统环境、启动命令和错误截图。

AI 反向审查：

- 体积大不一定是错，但异常增长必须有解释。
- 为了打包成功乱删依赖或改业务逻辑，风险通常更大。

---

## 10. 工具与自动化下放

适合工具化：

- 产物大小统计。
- dist 文件清单生成。
- 动态 import / sys.path 扫描。
- VERSION 文件生成。
- git commit / 构建时间注入。
- smoke test 命令。
- secret 扫描。
- PyInstaller spec 资源收集。
- Docker health check。

AI 仍需判断：

- 交付形态是否匹配用户使用场景。
- 最小可用链路是否覆盖真实验收路径。
- 配置和密钥边界是否安全。
- 用户说明是否足够让非开发者运行。
- 未验证项是否可接受。

验证策略：

- 试包：说明运行了什么、没验证什么。
- 正式交付：说明构建环境、产物、版本、最小链路、外部依赖、剩余风险。
- 失败时：不要只给报错，给下一步取证路径。
