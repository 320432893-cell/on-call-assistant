# 桌面 GUI 技术语义规则

## 1. 文件定位

- 本文件管桌面 GUI / 本地可视化工具的技术语义风险，不绑定单一框架。
- 默认覆盖 PySide6 / Qt 经验，但规则核心适用于 Tkinter、DearPyGui、Flet、Electron、Tauri、WebView 壳等 GUI 形态。
- 本文件重点是 UI 线程、后台任务、状态一致性、任务生命周期和 GUI 技术边界。
- 用户交互体验、按钮细节、窗口承载、F12 诊断入口不在本文件展开；只有任务真实命中交互设计时再读取 `interaction.md`。
- 打包、分发、PyInstaller、版本信息不在本文件展开；只有任务真实命中交付时再读取 `package.md`。

核心目标：GUI 不卡死、不跨线程乱改 UI、不丢状态、不吞异常、不把任务停止和失败混在一起。

---

## 2. 触发分级

### 2.1 小改：轻量执行

命中场景：

- 改按钮文案、布局微调、显示 bug、小输入校验。
- 不新增后台任务、不改变任务生命周期、不改变危险操作。
- 不涉及主线程阻塞、状态机、关闭行为、诊断入口。

AI 行为：

- 沿用现有 GUI 框架和项目风格。
- 只检查是否破坏既有状态和交互路径。
- 不借小改重构整个窗口或引入新框架。

### 2.2 中改：说明状态和用户路径

命中场景：

- 新增按钮、表单、弹窗、结果区、日志区。
- 新增或修改页面/窗口状态切换。
- 新增用户可见错误提示。

AI 行为：

- 说明用户路径：用户点什么、看到什么、失败怎么办、如何恢复。
- 判断是否需要读取 `interaction.md`；涉及交互细节时读取。
- 如果状态散落或按钮状态互相影响，优先收敛到统一状态更新函数。

### 2.3 大改：先讨论再写

命中场景：

- 新增耗时任务、后台线程、批处理、文件处理、网络请求。
- 新增删除、覆盖、重置、终止等危险操作。
- 改任务生命周期、主窗口结构、全局状态、关闭行为。
- 引入或替换 GUI 框架、线程模型、任务调度模型。

AI 行为：

- 先讨论状态模型、后台任务机制、中止策略、错误可见性、诊断入口和验证方式。
- 用户明确拍板后再写。
- GUI 交互地基允许较高推理压力，优先避免用户反复补充按钮、关闭、日志、F12 等细节。

---

## 3. 状态与 UI 一致性

- 多状态流转应集中表达，避免到处散落 `setEnabled`、`setVisible`、样式切换或等价控件状态修改。
- 任务至少区分：未开始、运行中、成功、失败、用户停止；按业务需要增加暂停、部分完成。
- UI 控件状态必须跟任务状态一致：运行中不能重复触发同一任务，失败后应允许恢复或重试。
- 用户主动停止和系统异常失败必须区分，日志和 UI 都不能混成一个 failed。
- 状态切换函数应可读、可查、可维护；小窗口可轻量实现，大窗口应有显式状态表或集中方法。

AI 反向审查：

- 看到多个按钮、日志、进度条、结果区互相影响时，不要继续堆局部 if；先判断是否需要集中状态。
- 不要为了小文案或简单布局改动重建状态机。

---

## 4. UI 线程与后台任务边界

- 耗时 IO、网络请求、批处理、文件读写、计算任务不得阻塞 UI 线程。
- 后台任务不得直接操作 UI 控件，必须通过框架推荐的主线程调度机制回到 UI 线程。
- PySide6 / Qt 示例：Signal-Slot、`QMetaObject.invokeMethod`、`QThread`、`QRunnable + QThreadPool`。
- 其他 GUI 框架按其官方推荐方式处理主线程调度，不把 Qt 方案机械套过去。
- 高频日志、进度、状态刷新应节流或缓冲，避免 UI 被刷新拖卡。
- 窗口关闭、任务取消、应用退出时，后台任务应有明确停止或收尾策略。

AI 反向审查：

- 如果用户说“先直接跑一下”，但任务可能卡 UI，必须指出主线程阻塞风险。
- 不确定框架线程模型时，先查项目现有实现或官方推荐方式，不凭经验猜。

---

## 5. 耗时任务生命周期

- 预计超过几秒的任务，应提供阶段、进度、日志流三者之一；复杂任务优先提供日志或阶段。
- 可中止任务必须有中止信号路径：UI 操作 -> 任务控制 -> 实际停止点 -> UI 状态回收。
- 中止后要说明中间产物处理：清理、保留、标记为部分完成或等待用户决定。
- 任务完成、失败、中止都应有用户可见反馈。
- 批处理任务应考虑部分成功、失败项汇总、重试入口或导出失败详情。

AI 反向审查：

- 不要把“关闭窗口”当作任务中止策略；关闭只是用户行为，任务仍需明确收尾。
- 不要吞掉后台异常；至少写日志并反馈给 UI。

---

## 6. 错误提示与可恢复性

- GUI 面向用户的错误提示使用业务语言，不直接展示 traceback、异常类名、SQL、token、内部路径等敏感细节。
- 详细技术信息进入日志、诊断面板或可复制详情区。
- 错误提示至少回答两个问题：发生了什么、影响什么、用户能做什么。
- 可恢复错误应提供重试、重新选择、打开日志、复制详情、返回上一步等路径。
- 不可恢复错误应说明当前数据或任务状态，避免用户误以为已经成功。

AI 反向审查：

- 只弹“失败”没有价值；要能帮助用户和 AI/开发者继续取证。
- 内部工具也不应把敏感配置和凭据直接展示给用户。

---

## 7. 调试、日志与协作取证

- 复杂 GUI、内部工具、批处理工具、文件处理工具、有后台任务的工具，应考虑诊断入口；具体交互入口属于交互风险，只有任务真实命中交互设计时再读取 `interaction.md`。
- GUI 技术层至少保证：最近错误可见、日志位置可找、任务状态可查、关键输入输出路径可追踪。
- 诊断信息不得泄露密钥、token、完整隐私数据或生产敏感内容。
- 用户需要协助排查时，优先让用户提供可复制诊断信息，而不是截图猜测。

---

## 8. 测试与工具分工

- 纯逻辑、状态计算、路径处理、数据转换优先写普通 pytest。
- GUI 交互测试可用 pytest-qt 或框架对应工具，但不强制每个项目引入。
- Ruff 负责 import、未使用变量、异常风格、现代语法等机械问题。
- Markdown 规则只保留工具难以判断的 GUI 语义：线程、状态、生命周期、恢复、取证。
