# 架构边界与架构记忆

## 1. 文件定位

触发:

- 架构边界调整。
- 模块职责变化。
- 脚本转应用、加 GUI、加 Web、加 CLI。
- 入口 / 服务 / 引擎 / 外部依赖边界变化。
- source of truth、degraded / 回退策略变化。
- 引入新外部依赖或跨模块契约。

动作:

- 本文件只管架构级边界和架构记忆维护。
- 不向上引用其他规则，避免读取链路膨胀。
- 机械检查交给 Ruff / basedpyright / import-linter；本文件只保留语义判断。

边界:

- 代码级范式不在本文件展开。
- 老项目小改不强制完整架构审计，但必须判断是否触及架构产物。

## 2. 项目记忆层优先

架构判断必须优先利用项目记忆层，而不是每次从零推理。

项目记忆层:

- `docs/PROJECT_MAP.md`: 稳定项目地图。
- `docs/ARCHITECTURE.md`: 架构决策和取舍。
- `docs/AI_HANDOFF.md`: 近期风险、未验证项、下次接手重点。

执行分级:

- 小改: 只判断是否触及项目记忆层，不强制全读。
- 中改: 读取相关的 `PROJECT_MAP` / `ARCHITECTURE` 片段。
- 大改: 完整读取三份产物，并在改后维护。

如果产物不存在:

- 新项目: 先形成最小项目地图和架构决策。
- 老项目: 先做接手 / 熟悉模式，补最小地图。

反向审查:

- 不读已有产物会重复造架构判断。
- 每次全读产物会拖慢小改。
- 重点是按改动风险选择读取深度。

## 3. 架构变更门

以下不是普通代码改动，必须先讨论影响面:

- 改模块职责。
- 改入口 / 服务 / 引擎边界。
- 改 source of truth。
- 改 degraded / 回退策略。
- 引入新外部服务、SDK、中间件、数据库。
- 改公共接口或跨模块契约。
- 把脚本封装成应用、服务、GUI、CLI。

讨论必须覆盖:

- 为什么现在需要改架构。
- 影响哪些模块、入口、数据流、状态流。
- 是否和既有架构决策冲突。
- 是否需要更新项目记忆层。
- 如果不改架构，代价是什么。

## 4. 脚本转应用

触发:

- 脚本加 GUI / Web / CLI。
- 单文件脚本开始长期使用。
- 同一脚本出现多个入口或多处重复编排。

动作:

- 先识别核心处理逻辑、IO、配置、入口。
- 核心逻辑先抽成可独立调用的函数或模块。
- 入口只负责参数、配置、依赖装配、启动。
- UI / Web / CLI 只适配输入输出，不承载核心业务算法。

阻断:

- 核心逻辑仍混着 UI / Web / CLI 对象。
- 同一业务流程在多个入口重复编排。
- 脚本封装后仍无法独立测试核心逻辑。

## 5. 边界规则

入口层:

- 只做配置加载、参数解析、依赖装配、启动。
- 不写业务条件分支。
- 不直接做数据处理或算法。

服务 / 编排层:

- 组织业务流程。
- 调用引擎、仓储、外部适配器。
- 处理业务级错误和降级决策。

引擎层:

- 处理纯计算、纯转换、核心算法。
- 不依赖 UI / Web 框架对象。
- 不直接读写外部系统，除非该模块本身就是 IO 适配器。
- 输入输出使用普通数据结构或明确模型。

外部适配层:

- 封装 HTTP、SDK、数据库、文件系统、消息队列。
- 不把第三方细节泄漏到核心业务层。

阻断:

- 核心逻辑 import UI / FastAPI / CLI 框架。
- 框架对象穿透到引擎层。
- 入口层承载业务流程。

## 6. 配置与环境边界

动作:

- 路径、URL、阈值、账号、开关、环境差异走配置。
- 状态机、算法、业务规则、流程编排走代码。
- 环境差异通过配置注入，不在业务逻辑里写 `if env == "prod"` 分支。

阻断:

- 同一配置值在多文件硬编码。
- 环境差异散落在业务分支。
- secret、token、password 进入代码、日志或文档。

## 7. 外部服务边界

触发:

- 调用外部 HTTP API。
- 调用第三方 SDK。
- 跨服务 RPC。
- 新增或修改重试、降级、熔断逻辑。

必须明确:

- 超时。
- 重试上限。
- 降级或错误传播策略。
- 幂等性。
- 可观测性。
- 失败是否影响 source of truth。

阻断:

- 外部调用无超时。
- 无限重试。
- 不幂等操作直接重试。
- 外部服务失败会污染 source of truth。

## 8. 公共复用

动作:

- 第一次出现的局部逻辑可留在局部。
- 第二次跨文件或跨入口重复时，考虑提取公共能力。
- 老项目先查已有公共能力，再新增。
- 新公共能力必须有明确职责边界。

边界:

- 不为“未来可能复用”提前抽象。
- 不把差异很大的逻辑硬塞进同一个公共模块。

阻断:

- 页面、入口或服务层重复实现已有公共能力。
- 第三次复制同类逻辑仍不抽取。

## 9. 架构产物维护

架构相关改动后，必须检查是否维护项目记忆层。

更新 `PROJECT_MAP`:

- 入口变化。
- 运行 / 测试方式变化。
- 核心目录职责变化。
- 关键数据流 / 状态流变化。

更新 `ARCHITECTURE`:

- 架构边界变化。
- source of truth 变化。
- degraded / 回退策略变化。
- 引入或废弃重要方案。
- 关键取舍变化。

更新 `AI_HANDOFF`:

- 有未验证风险。
- 有临时方案。
- 有下次接手必须先看的模块。
- 有近期架构债。

防膨胀:

- 小改只修正过期事实，不追加流水账。
- 中大改只写未来接手需要的信息。
- 旧记录过期时先修正或删除，再新增。

## 10. 本文件反模式

- 架构判断不看已有项目记忆层。
- 小改强制全量架构审计。
- 入口里写业务流程。
- 核心逻辑依赖框架对象。
- 外部调用无超时、无限重试。
- 环境差异写进业务分支。
- 为未来可能复用提前抽象。
- 架构变更后不维护项目记忆层。
