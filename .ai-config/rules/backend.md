# FastAPI / Starlette 后端语义规则

## 1. 文件定位

- 本文件只管 FastAPI / Starlette / HTTP API 层的语义风险。
- 不重复 `code.md` 的通用异常、日志、测试、范式规则。
- 不重复 `architecture.md` 的整体分层、外部依赖、架构记忆规则。
- 不重复 `data.md` 的数据契约、幂等、失败模式细节。
- 本文件不是每次后端小改都要填的检查表；只在命中后端语义边界时读取。

核心目标：避免 API 契约暗改、权限漏判、事务边界模糊、后台任务不可见、HTTP 层基础设施缺失。

---

## 2. 触发分级

### 2.1 小改：轻量执行

命中场景：

- 已有接口内部逻辑微调。
- 小 bug 修复。
- 路径解析、参数兼容、文件/文件夹支持之类局部改动。
- 不改变路由、鉴权、请求/响应结构、数据库写入语义。

AI 行为：

- 先读相关路由、service、测试或调用点。
- 判断是否改变外部 API 契约；没有改变时不展开完整后端规则。
- 优先做最小改动和定向验证。
- 如发现实际触及契约、权限、事务或后台任务，升级到中改/大改。

### 2.2 中改：说明影响面

命中场景：

- 新增或修改路由。
- 修改请求参数、响应字段、状态码或错误结构。
- 新增数据库写操作。
- 修改鉴权依赖或用户身份传递。

AI 行为：

- 简短说明影响面：接口、调用方、数据、权限、测试。
- 保持与项目现有 FastAPI 组织方式一致。
- 修改前如存在兼容性或权限疑问，先问用户或给出选项。

### 2.3 大改：先讨论再写

命中场景：

- API 版本策略、公开接口破坏性变更。
- 权限模型、租户隔离、资源所有权规则变化。
- 事务边界、后台任务机制、队列、middleware、全局异常处理变化。
- 会影响部署、监控、回滚或多个调用方。

AI 行为：

- 先讨论方案、风险、迁移路径、回滚方式和验证方式。
- 用户明确拍板后再写。
- 必要时维护 `docs/PROJECT_MAP.md`、`docs/ARCHITECTURE.md`、`docs/AI_HANDOFF.md`。

## 3. 路由与 API 契约

- 公开 API 的路径、方法、请求参数、响应字段、状态码、错误语义都属于契约，不能暗改。
- 新增公开接口时，优先沿用项目现有版本前缀、router 分组和路径命名风格。
- 破坏性变更必须先说明：删字段、改字段含义、改返回结构、改状态码、改权限、改错误格式。
- 旧项目已有未版本化接口时，不机械补 `/v1`；先判断项目现状、调用方和迁移成本。
- 内部接口也要明确调用边界：谁调用、是否可被外部访问、是否需要鉴权。

AI 反向审查：

- 用户要求“顺手改返回结构”“字段名改一下”“状态码换一下”时，必须提醒调用方兼容风险。
- 如果兼容保留成本低，优先建议新增字段或新增接口，而不是直接破坏旧契约。

---

## 4. 请求 / 响应模型

- 新增正式接口时，优先使用 Pydantic 模型表达请求和响应。
- `response_model` 对公开接口有价值；旧项目若已有轻量 dict 风格，不强行大规模重构。
- `dict` / `Any` 只适合动态结构、透传结构或旧项目局部兼容；使用时要说明边界。
- 不直接把 ORM 对象、内部配置对象、异常对象返回给客户端。
- 必填、可空、默认值、枚举、范围限制应尽量在模型或验证逻辑中表达。

AI 反向审查：

- 如果为了快而返回裸 dict，必须判断这是小范围兼容还是会扩大成长期契约债。
- 如果改动只是旧接口小修，不要借机重做全套 schema，除非用户确认。

---

## 5. 鉴权、权限与资源边界

- 新增路由必须明确：公开、登录用户、管理员、内部调用、服务间调用。
- FastAPI 鉴权优先通过 `Depends(...)` 或项目已有依赖注入方式表达。
- 路由函数内手写鉴权逻辑只能作为旧代码兼容或极小修复；新增模式应优先收敛到统一依赖。
- 涉及用户数据、租户数据、设备数据、项目数据时，必须判断资源所有权或访问范围。
- 不同权限等级混在同一个 router 时，先判断项目现状；新增代码应避免继续扩大混乱。

AI 反向审查：

- 用户要求“这个接口先不加权限”时，必须问清是否内部接口、临时接口、是否有网关保护，以及暴露后果。
- 权限规则不清时，不得凭感觉补一个看似合理的鉴权。

---

## 6. 数据库写入与事务边界

- 单步写入按项目现有 session/transaction 模式处理。
- 多步写入必须判断原子性：全部成功、允许部分成功、失败补偿、重试是否安全。
- 事务内不要包含外部 HTTP、文件长 IO、sleep、人工等待、后台任务派发后的不可控逻辑。
- 跨 service 写入时，事务边界应在编排层清晰表达，避免每层各自 commit 造成半成功。
- Schema 变更、迁移、回滚属于大改，先讨论。

AI 反向审查：

- 看到“先写库再调外部服务”或“调外部服务成功再写库”时，必须考虑失败顺序和补偿策略。
- 不确定现有 session 生命周期时，先读项目代码，不要猜。

---

## 7. 后台任务与异步边界

- FastAPI `BackgroundTasks` 只适合短、小、失败可接受或可人工重试的任务。
- 重要任务、长任务、需要重试/持久化/监控的任务，应讨论 Celery、RQ、arq、调度器或项目已有队列。
- 后台任务不能复用请求级 DB session、request/response 对象或临时上下文。
- `asyncio.create_task` 脱离请求生命周期时，必须有异常可见性和关闭策略。
- 同步阻塞 IO 进入 async 路由前，先判断是否需要线程池或改用异步客户端。

AI 反向审查：

- 用户说“后台跑一下就行”时，必须说明失败不可见、进程重启丢失、重试缺失和排查困难。
- 小型本地工具或非关键任务可以接受轻量方案，但要明确代价。

---

## 8. HTTP 层可观测性

- 新建 FastAPI 项目、首次接入 middleware、排查生产问题时，检查 trace_id、请求日志、5xx 错误日志。
- 单个路由小改不强制补全全局观测体系。
- 5xx 错误应能关联请求、路径、用户或调用方、trace_id 或等效排查标识。
- 慢请求阈值、日志字段、指标系统沿用项目现状；不要为了规则引入重型监控栈。
- 错误响应不要泄露内部堆栈、凭据、SQL、文件路径等敏感信息。

AI 反向审查：

- 如果缺少基础观测导致 bug 无法定位，应优先建议补最小取证点，而不是盲修。
- 不要把每个小 bug 都升级成监控改造。

---

## 9. 测试与验证

- 后端测试优先覆盖外部契约：状态码、响应字段、错误分支、鉴权、边界输入。
- 小改可以用定向单测、集成测试、最小复现或手工命令验证。
- 修改路由/契约/权限/事务时，优先补或运行对应 pytest/httpx 测试。
- 测试跑不起来时，说明原因、已做的替代验证和剩余风险。

工具分工：

- Ruff 负责 import、现代语法、部分复杂度和常见代码问题。
- mypy/pyright 负责类型约束。
- pytest/httpx 负责接口行为。
- Markdown 规则只保留工具看不懂的后端语义判断。
