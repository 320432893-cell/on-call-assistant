# HTTP API 体检

本文件用于 FastAPI / Starlette / HTTP API 改动前的语义体检。

目标是避免 API 契约暗改、权限漏判、事务半成功、后台任务失败不可见、错误响应泄漏和调用方可见行为未验证。

## 1. 默认体检

改 API 前先判断：

- 是否改变路径、方法、请求参数、响应字段、状态码或错误结构。
- 是否影响前端、外部调用方、内部调用方或服务间调用。
- 是否改变鉴权、权限、用户身份传递、租户或资源所有权。
- 是否写数据库、改事务边界、迁移 schema 或改变提交顺序。
- 是否新增后台任务、长任务、调度器、队列或 async 边界。
- 是否影响 5xx、慢请求、请求日志、trace_id 或错误响应。
- 是否有最小 API 验证路径。

## 2. API 契约

规则：

- 路径、HTTP 方法、请求参数、响应字段、状态码、错误结构都属于契约。
- 破坏性变更先说明调用方兼容影响。
- 兼容成本低时，优先新增字段或新增接口，不直接破坏旧结构。
- 新增公开接口时沿用项目现有 router 分组、路径命名和版本策略。
- 内部接口也要明确调用边界：谁调用、是否暴露、是否需要鉴权。
- 不直接返回 ORM 对象、内部配置对象、异常对象或未过滤的第三方响应。

## 3. 权限和资源边界

规则：

- 新路由必须明确：公开、登录用户、管理员、内部调用或服务间调用。
- 鉴权方式沿用项目已有依赖注入或中间件模式。
- 涉及用户、租户、项目、设备、文件等资源时，必须判断资源所有权或访问范围。
- 权限规则不清时，先标记未确认，不凭感觉补一个看似合理的鉴权。
- 临时不加权限时，必须说明隔离方式和暴露后果。

## 4. 数据库写入和事务

规则：

- 单步写入沿用项目现有 session / transaction 模式。
- 多步写入先明确原子性：全部成功、允许部分成功、失败补偿或可重试。
- 事务内避免放外部 HTTP、长文件 IO、sleep、人工等待或不可控后台任务。
- 跨 service 写入时，事务边界放在编排层说明，避免多层各自 commit 造成半成功。
- schema、迁移、回滚、批量更新属于高风险数据改动，回到既有项目 / 数据规则处理。

## 5. 后台任务和异步边界

规则：

- `BackgroundTasks` 只适合短、小、失败可接受或可人工重试的任务。
- 重要任务、长任务、需要重试 / 持久化 / 监控的任务，先讨论队列或项目已有调度机制。
- 后台任务不复用请求级 DB session、request / response 对象或临时上下文。
- `asyncio.create_task` 脱离请求生命周期时，必须有异常可见性和关闭策略。
- 同步阻塞 IO 进入 async 路由前，先判断线程池、异步客户端或架构解构。

## 6. HTTP 可观测和错误响应

规则：

- 生产问题、5xx、慢请求或首次接入全局 middleware 时，检查 trace_id、请求日志和错误日志。
- 单个路由小改不升级成监控改造。
- 错误响应不泄漏内部堆栈、SQL、凭据、文件路径、环境变量或第三方密钥。
- 无法定位问题时，先补最小取证点，再修复。

## 7. 验证

改 API 后优先验证：

- 状态码。
- 响应字段。
- 错误分支。
- 鉴权和权限边界。
- 边界输入。
- 数据库写入结果。
- 后台任务是否可见、可追踪或可重试。

测试跑不了时，在 taskwork 闭包里记录替代验证和未验证风险。
