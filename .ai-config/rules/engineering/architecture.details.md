# 架构边界与架构记忆

## 0. 读取路径

默认必读:

- `1. 文件定位`
- `2. 项目记忆层优先`
- `3. 架构变更门`
- `9. 架构产物维护`
- `10. 本文件反模式`

按需读取:

- 脚本加 GUI / Web / CLI、单文件脚本长期化、多入口重复编排时，读取 `4. 脚本转应用`。
- 入口、服务 / 编排、引擎、外部适配职责变化时，读取 `5. 边界规则`。
- 配置、环境变量、secret、路径、URL、阈值、环境差异变化时，读取 `6. 配置与环境边界`。
- HTTP API、第三方 SDK、RPC、数据库、中间件、重试、降级、熔断变化时，读取 `7. 外部服务边界`。
- 跨文件 / 跨入口重复、公共模块、新公共能力、第三次复制同类逻辑时，读取 `8. 公共复用`。

细分读取:

- 只改入口启动参数: 读 `3. 架构变更门` 和 `5. 边界规则` 的入口层。
- 只改服务编排: 读 `3. 架构变更门` 和 `5. 边界规则` 的服务 / 编排层。
- 只改核心算法或转换逻辑: 读 `5. 边界规则` 的引擎层；若无边界变化，不展开完整架构审计。
- 只改外部调用适配: 读 `5. 边界规则` 的外部适配层和 `7. 外部服务边界`。
- 只改配置读取位置: 读 `6. 配置与环境边界`；若不影响 source of truth，不展开完整架构审计。
- 只维护项目记忆层: 读 `2. 项目记忆层优先` 和 `9. 架构产物维护`。

边界:

- 读取路径只控制注意力，不降低架构变更门、外部服务边界和项目记忆维护要求。
- 老项目小改只判断是否触及架构产物；未触及则不展开完整架构审计。
- 不确定某段是否命中时，先问用户一句或只读对应最小段落。

## 1. 文件定位

触发:

- 架构边界调整。
- 模块职责变化。
- 脚本转应用、加 GUI、加 Web、加 CLI。
- 入口 / 服务 / 引擎 / 外部依赖边界变化。
- source of truth、degraded / 回退策略变化。
- 引入新外部依赖或跨模块契约。

动作:

- 本文件只管架构级边界和架构记忆维护。
- 不向上引用其他规则，避免读取链路膨胀。
- 机械检查交给 Ruff / basedpyright / import-linter；本文件只保留语义判断。

边界:

- 代码级范式不在本文件展开。
- 老项目小改不强制完整架构审计，但必须判断是否触及架构产物。

## 2. 项目记忆层优先

架构判断必须优先利用项目记忆层，而不是每次从零推理。

项目记忆层:

- `docs/PROJECT_MAP.md`: 稳定项目地图。
- `docs/AI_HANDOFF.md`: 近期风险、未验证项、下次接手重点。

执行分级:

- 小改: 只判断是否触及项目记忆层，不强制全读。
- 中改: 读取相关的 `PROJECT_MAP` 片段，必要时读取 `AI_HANDOFF`。
- 大改: 完整读取 `PROJECT_MAP` 和 `AI_HANDOFF`，并在改后维护。

如果产物不存在:

- 新项目: 先形成最小项目地图、易懂架构图和架构边界。
- 老项目: 先做接手 / 熟悉模式，补最小地图。

反向审查:

- 不读已有产物会重复造架构判断。
- 每次全读产物会拖慢小改。
- 重点是按改动风险选择读取深度。

## 3. 架构变更门

以下不是普通代码改动，必须先讨论影响面:

- 改模块职责。
- 改入口 / 服务 / 引擎边界。
- 改 source of truth。
- 改 degraded / 回退策略。
- 引入新外部服务、SDK、中间件、数据库。
- 改公共接口或跨模块契约。
- 把脚本封装成应用、服务、GUI、CLI。

讨论必须覆盖:

- 为什么现在需要改架构。
- 影响哪些模块、入口、数据流、状态流。
- 是否和既有架构决策冲突。
- 是否需要更新项目记忆层。
- 如果不改架构，代价是什么。
- 这次架构调整会牺牲什么，牺牲是否值得。

架构牺牲项:

- 交付速度。
- 局部简单性。
- 文件数量和跳转成本。
- 学习成本。
- 迁移风险。
- 老项目局部一致性。
- 测试和验证成本。

牺牲值得的依据:

- 避免重复编排继续扩散。
- 避免 source of truth 混乱。
- 避免框架对象穿透核心逻辑。
- 避免外部失败污染数据或状态。
- 降低长期接手、测试、替换和排障成本。

阻断:

- 说不清架构调整牺牲什么。
- 说不清它避免了什么更高代价。
- 为了“更像架构”而增加层级、目录或抽象。

## 4. 脚本转应用

触发:

- 脚本加 GUI / Web / CLI。
- 单文件脚本开始长期使用。
- 同一脚本出现多个入口或多处重复编排。

动作:

- 先识别核心处理逻辑、IO、配置、入口。
- 核心逻辑先抽成可独立调用的函数或模块。
- 入口只负责参数、配置、依赖装配、启动。
- UI / Web / CLI 只适配输入输出，不承载核心业务算法。

阻断:

- 核心逻辑仍混着 UI / Web / CLI 对象。
- 同一业务流程在多个入口重复编排。
- 脚本封装后仍无法独立测试核心逻辑。

## 5. 边界规则

入口层:

- 只做配置加载、参数解析、依赖装配、启动。
- 不写业务条件分支。
- 不直接做数据处理或算法。

服务 / 编排层:

- 组织业务流程。
- 调用引擎、仓储、外部适配器。
- 处理业务级错误和降级决策。

引擎层:

- 处理纯计算、纯转换、核心算法。
- 不依赖 UI / Web 框架对象。
- 不直接读写外部系统，除非该模块本身就是 IO 适配器。
- 输入输出使用普通数据结构或明确模型。

外部适配层:

- 封装 HTTP、SDK、数据库、文件系统、消息队列。
- 不把第三方细节泄漏到核心业务层。

阻断:

- 核心逻辑 import UI / FastAPI / CLI 框架。
- 框架对象穿透到引擎层。
- 入口层承载业务流程。

## 6. 配置与环境边界

动作:

- 路径、URL、阈值、账号、开关、环境差异走配置。
- 状态机、算法、业务规则、流程编排走代码。
- 环境差异通过配置注入，不在业务逻辑里写 `if env == "prod"` 分支。

阻断:

- 同一配置值在多文件硬编码。
- 环境差异散落在业务分支。
- secret、token、password 进入代码、日志或文档。

## 7. 外部服务边界

触发:

- 调用外部 HTTP API。
- 调用第三方 SDK。
- 跨服务 RPC。
- 新增或修改重试、降级、熔断逻辑。

必须明确:

- 超时。
- 重试上限。
- 降级或错误传播策略。
- 幂等性。
- 可观测性。
- 失败是否影响 source of truth。

阻断:

- 外部调用无超时。
- 无限重试。
- 不幂等操作直接重试。
- 外部服务失败会污染 source of truth。

## 8. 公共复用

动作:

- 第一次出现的局部逻辑可留在局部。
- 第二次跨文件或跨入口重复时，考虑提取公共能力。
- 老项目先查已有公共能力，再新增。
- 新公共能力必须有明确职责边界。

边界:

- 不为“未来可能复用”提前抽象。
- 不把差异很大的逻辑硬塞进同一个公共模块。

阻断:

- 页面、入口或服务层重复实现已有公共能力。
- 第三次复制同类逻辑仍不抽取。

## 9. 架构产物维护

架构相关改动后，必须检查是否维护项目记忆层。

更新 `PROJECT_MAP`:

- 入口变化。
- 运行 / 测试方式变化。
- 核心目录职责变化。
- 关键数据流 / 状态流变化。
- 架构边界变化。
- source of truth 变化。
- degraded / 回退策略变化。
- 引入或废弃重要方案。
- 关键取舍变化。
- 架构图 / 结构图缺失、过期，或与当前模块职责、调用 / 数据流 / 状态流、外部依赖、关键边界不一致。

文档日期要求:

- 创建或实质更新 `PROJECT_MAP`、`AI_HANDOFF` 或其他项目维护文档时，必须在文档开头写 `最后修改日期: YYYY-MM-DD`。
- 架构边界、source of truth、运行入口、外部依赖、验证状态、接手风险变化时，同步刷新日期。
- 仅格式、错别字、链接修正且不改变事实时，可以不刷新日期，但完成汇报需说明。

`PROJECT_MAP` 结构图维护要求:

- 创建或更新 `PROJECT_MAP` 时，必须检查是否存在 AI 友好的结构图；没有则补最小图，过期则同步更新。
- 项目维护文档、接力文档、工具契约文档、规则说明文档中，只要内容涉及结构、流程、依赖、职责分工、检查体系或接手路径，优先用 Mermaid 给出第一屏总览。Mermaid 对 AI 解析友好，也方便用户通过 Markdown 预览渲染。
- Mermaid 必须服务理解，不为装饰而画；纯短说明、简单清单或没有关系结构的内容不强制画图。
- 默认使用 Mermaid 树状图，表达主模块、子模块、数据/索引、source of truth、外部依赖和 degraded / 回退边界。
- 如果 Mermaid 放在 memory / 项目记忆层 / 交接文档里，图上方必须备注：此图需要用支持 Mermaid 的 Markdown 预览打开，例如 GitHub、GitLab、VSCode Mermaid 插件或 Mermaid Live Editor。
- 树状图每层或主要分支应使用不同颜色区分；颜色必须克制、可读、服务扫描，不做装饰。
- 树状图不是文件树，必须体现模块职责和关键依赖；复杂数据流可补少量箭头。
- 不画装饰图；不要画过细调用链或让人难以理解的全量系统图。
- 小改未触及架构关系时，不强制重画；但如果发现结构图已明显过期，或 Mermaid 图缺少打开备注，必须在完成汇报中标出并建议更新。

更新 `AI_HANDOFF`:

- 有未验证风险。
- 有临时方案。
- 有下次接手必须先看的模块。
- 有近期架构债。
- 维护时必须同时满足两类读者：前半部分给用户可渲染的 Mermaid 总览图和打开备注，后半部分给 AI 的可执行事实、风险、验证状态、禁止动作和下一步。

防膨胀:

- 小改只修正过期事实，不追加流水账。
- 中大改只写未来接手需要的信息。
- 旧记录过期时先修正或删除，再新增。

## 10. 本文件反模式

- 架构判断不看已有项目记忆层。
- 小改强制全量架构审计。
- 入口里写业务流程。
- 核心逻辑依赖框架对象。
- 外部调用无超时、无限重试。
- 环境差异写进业务分支。
- 为未来可能复用提前抽象。
- 架构变更后不维护项目记忆层。
