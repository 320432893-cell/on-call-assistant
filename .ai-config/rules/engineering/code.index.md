# 代码结构坏味道复盘

本文件用于 AI 写完代码后的结构坏味道复盘。范式是治理脏代码 / 坏代码的工具，不是项目启动前的默认设计仪式。它只保留跨语言、跨框架都成立的少数高价值判断，不替代老项目影响面取证、架构体检或具体技术栈规则，也不展开格式、lint、类型等工具可稳定处理的问题。

默认触发:

- 写完一轮代码后，静态工具或 diff 暴露结构坏味道。
- 阶段闭包前发现局部修补可能压不住状态、分支、错误、外部依赖或公共行为风险。

事前例外:

- 中大改动在动手前已明确存在状态生命周期、多 handler、错误分流、外部依赖隔离或公共行为稳定性问题。
- 其他场景不预读本文件，不提前讨论范式。

## 1. 默认判断

按重要程度先看这五项:

1. 命中的坏味道是工具可直接修的局部问题，还是结构问题。
2. 是否真的需要新抽象，还是局部整理更清楚。
3. 状态、分支、外部依赖、错误结果是否已经复杂到需要收敛。
4. 公共行为是否会被调用方依赖，包括返回结构、异常、副作用。
5. 本次验证覆盖了哪些真实风险，哪些仍未验证。

小改优先沿用项目现状，不借机引入新范式。老项目中，本文件不得压过 `../process/flow_legacy_project.index.md` 的局部一致性和影响面判断。

## 2. 抽象取舍

默认:

- 一次性脚本、小改、单调用点逻辑优先直写。
- 已有项目风格能解决问题时，优先保持局部一致。
- 新抽象必须能控制真实变化点、状态复杂度、失败模式、测试替换需求或公共行为稳定性。
- 每轮结构复盘最多允许 1-2 个主导抽象；更多抽象先拆任务或降级为普通实现细节。

抽象应用门槛:

- 必须先有代码证据或事前例外，不凭空套复杂抽象。
- 它解决的具体复杂度。
- 它的真实执行代价: 改多少文件、影响多少调用方、增加多少测试 / 迁移 / 回滚 / 维护成本。
- 什么情况下这个抽象会失效或变成负担。
- 必须产出应用证据；没证据视为没应用。

抽象层级:

- 通用层默认只做少数稳定判断: 不变量识别、命令查询分离、错误结果是否应显式建模。
- 任务层按需激活: 状态机、策略 / 注册表、端口 / 适配器、流水线、解释器、CQRS。
- 任务层抽象必须先判断适用条件；不适用就拒绝。

引入窗口:

- 默认优先从本文件的高 ROI 设计抓手中选择。
- 如果现有抓手不符合真实业务复杂度，允许发散提出新的抽象。
- 新抽象必须说明业务触发点、为什么现有备选不适用、最小落地形态、失效边界和验证方式。
- 说不清这些内容时，回到直写或沿用现有项目风格。

## 3. 高 ROI 设计抓手

只在真实复杂度出现时考虑这些设计，不为了“更像工程化”而引入。

不变量:

- 适用: 业务规则必须始终成立，例如金额非负、状态转移合法、缓存和源数据一致。
- 不适用: 只是临时展示计算、无跨步骤约束。
- 应用证据: 不变量列表、何时检查、违反后如何处理。

命令 / 查询分离:

- 适用: 读操作和写操作混在一起，调用方难以判断是否有副作用。
- 不适用: 简单一次性脚本或局部私有函数，副作用清楚且无复用。
- 应用证据: 命令清单、查询清单、副作用边界。

状态机:

- 多个布尔值互相影响、生命周期分散、非法组合可能出现时，用显式状态收敛。
- 只有两个稳定状态且无非法转移风险时，不强制状态机。
- 应用证据: 状态列表、合法转移表、非法转移处理。

策略 / 注册表:

- key 路由、多 handler、三类以上可扩展分支，优先考虑策略映射或注册表。
- 分支固定、差异过大、共享接口别扭时，不强制抽象。
- 应用证据: key 到 handler 的映射、统一输入输出、默认 / 未知 key 处理。

端口 / 适配器:

- 外部依赖需要替换、mock、隔离失败或复用调用边界时，把核心逻辑和具体 SDK / IO 分开。
- 单一调用点、无替换需求、无测试隔离压力时，不强制接口化。
- 应用证据: 抽象边界清单、核心逻辑依赖什么、适配器负责什么。

结果 / 错误模型:

- 多种失败原因会被调用方分流处理时，用明确错误类型或结果对象承载语义。
- 只有顶层展示错误、调用方不分流时，不必制造复杂错误层级。
- 应用证据: 错误类别、调用方处理方式、哪些错误继续抛出。

流水线 / 解释器 / CQRS:

- 适用: 多阶段处理、可组合规则、读写模型天然分离且业务复杂度真实存在。
- 不适用: 单阶段线性逻辑、小功能、为了模式完整而拆分。
- 应用证据: 阶段清单 / 规则清单 / 读写模型边界，三者择其一即可。

坏味道识别:

- 静态工具只负责指出可机械识别的风险；本文件只判断它是局部修复、命名/边界整理，还是需要结构收敛。
- diff 信号优先看真实语义变化: 新增跨模块副作用、返回结构变化、异常语义变化、外部 IO / SDK 进入核心逻辑。
- 如果复杂度来自状态组合，优先考虑状态机；如果来自 key 路由或 handler 扩展，优先考虑策略 / 注册表。
- 如果复杂度来自外部依赖穿透核心逻辑，优先考虑端口 / 适配器；如果来自失败分流，优先考虑结果 / 错误模型。
- 如果复杂度来自读写副作用混杂，优先考虑命令 / 查询分离。

激活短语:

- “先做不变量分析”。
- “画状态转移表”。
- “列出依赖反转边界”。
- “把错误当成结果建模”。
- “拆出命令和查询边界”。

## 4. 鲁棒性设计

失败路径:

- 核心逻辑优先暴露真实失败，不静默吞错。
- 边界层兜底并转成调用方或用户能处理的错误，不暴露敏感内部细节。
- 外部依赖、文件、网络、数据库、并发任务要考虑超时、重试、幂等、部分成功和降级。

可排查性:

- 异常日志保留定位上下文和 traceback。
- 外部调用、关键状态转移、任务失败要能追踪。
- 敏感信息边界按语义判断: 哪些数据可记录、可返回、可展示，哪些只能内部处理；具体泄漏模式交给静态工具和审查补充。

公共行为:

- 修改公开函数、跨模块返回结构、跨边界数据结构、异常类型或副作用前，先查调用方。
- 破坏性变更必须说明谁受影响、是否兼容旧行为、需要怎样迁移。

模块内部私有函数可轻量处理，但如果调用方已经跨文件依赖其行为，按公共行为处理。

## 5. 验证记录

验证按本次真实风险选择，不做固定分级:

- bug 修复优先有复现或回归验证。
- 公共行为、状态流、异常路径、外部依赖改动要查调用方并做针对验证。
- 数据写入、权限、安全、生产事故相关改动要覆盖失败路径、回滚或降级。
- 抽象重构完成后，用 diff + 应用证据复核是否真的体现主导抽象。
- 跑不了或没条件验证时，写入 taskwork 阶段总结的“未验证”，不伪装成已完成。
