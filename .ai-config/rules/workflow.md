# 工作流

## 1. 文件定位

- 本文件只管任务前后两侧的横切规则：开始前查什么，执行前卡什么，结束时报什么。
- 项目类型流程在 `flow_*.md`；规则怎么写在 `governance.md`；专题规则按 `AGENTS.md` 入口按需读取。
- 本文件给 AI 执行，不做长表格自检；只保留能改变行为的触发、动作和边界。

---

## 2. 任务前体检

首次接触项目、切换目录、准备改文件或准备运行会改变状态的命令前，先做轻量体检。

必须检查：

- 仓库根：当前目录是否是用户目标项目。
- 工作区状态：是否已有用户改动、暂存内容、未跟踪文件。
- `.gitignore`：是否明显漏掉 `.env`、虚拟环境、缓存、索引、构建产物。
- 工具链：项目使用 `uv` / `pip` / `poetry` / `npm` / `pnpm` / `yarn` 中哪一种。
- 敏感和大体积产物：`.env`、密钥、模型权重、索引、数据库、日志、截图等是否可能误提交。

动作：

- 正常时不展开汇报，避免噪音。
- 发现异常时先报告异常和影响，再询问是否继续。
- 仓库根不一致、疑似密钥/环境文件暴露、已有用户改动可能被覆盖时，不得直接写入。

---

## 3. 执行前门禁

命中以下任一情况，先停在讨论态：

- 包管理或依赖操作前，尚未识别工具链和虚拟环境。
- 删除、覆盖、迁移文件或数据。
- 改公开 API、核心函数签名、跨模块契约。
- 重构涉及多个文件或多个模块。
- 数据库 schema、批量数据写入、索引重建、生产数据、安全边界或凭据相关。
- 用户意图、成功标准或影响范围不清。
- 缺少决策信息，且该信息影响方案、实现、验证、数据安全或生产风险。
- 新增外部依赖、工具链依赖、下载型 CLI、pre-commit/CI 工具。

动作：

- 说明要做什么、影响什么、为什么有风险。
- 给出回滚方式和回滚后验证点。
- 等用户拍板后再执行。
- 新增依赖或下载型工具时，先说明用途、必要性、安装位置、体积/耗时/网络风险、是否进入依赖/lock/CI/pre-commit、轻量替代方案和不引入的损失。
- 信息缺口先走最小触发器：AI 先自取；不能自取再问用户；仍不可得则标注未确认假设和验证方式。
- 信息缺口复杂、需要组织取证或假设分层时，再读取 `info_guidance.md`。

禁止：

- 未说明用途、成本和替代方案就新增依赖或运行会触发下载的工具。
- 用“应该没事”替代实际检查。
- 把横切风险混到完成汇报里事后才说。
- 自决删除 `.git/`、`.env`、锁文件、数据库、索引或用户资产。
- 把未确认假设写成事实。

---

## 4. 验证门

改动后必须按风险选择验证。存在直接相关测试时优先运行。

触发：

- 改的文件已有对应测试。
- 改的函数/路由/服务被测试 import 或调用。
- bug 修复。
- 行为变更。
- 重构影响调用链。

动作：

- 有测试且能运行：运行相关测试。
- bug 修复：优先补或运行能复现问题的用例。
- 行为变更：说明用什么路径验证新行为。
- 测试跑不了：说明原因、剩余风险和替代验证。
- 测试失败：先处理失败或回到讨论态，不把失败当作完成。

验证命令以项目配置为准，例如 `pytest`、`ruff`、`mypy`、`import-linter`、前端测试或 CI 命令。

---

## 5. 上下文耦合风险

同样的改动，在不同上下文中风险不同。以下情况会放大副作用：

- 工作区已有未提交或未跟踪改动。
- 暂存区混乱，用户可能随手 commit。
- 涉及 `.env`、密钥、锁文件、数据库、索引、生成产物。
- 改动叠加 git 历史操作、删除、迁移或批量写入。
- 用户正在纠偏或边界仍在讨论。

动作：

- 风险放大时先报告，不直接扩大改动范围。
- 必要时建议拆分步骤：先取证、再小改、再验证、最后讨论是否继续。
- 不借机做无关清理或重构。

---

## 6. 完成汇报

小任务完成时至少说明：

- 做了什么。
- 验证了什么。
- 没做什么或剩余风险。

中大任务完成时说明：

- 做了什么，涉及哪些文件或模块。
- 为什么这样做。
- 跑了什么验证，结果如何。
- 没跑什么验证以及原因。
- 工作区是否留下新文件、未跟踪文件、生成产物或需要用户关注的状态。
- 本次跳过、豁免或压缩了哪些规则。
- 涉及方案、架构、规则、工具链、重构时，说明反向审查结论。

禁止汇报：

- 与任务无关的审美建议。
- 用户已明确不关心的旁枝问题。
- “全部完成/都没问题”但不说明验证依据。

如果用户指出“你漏了 X”，立即补全，不争辩。
