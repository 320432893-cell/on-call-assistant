# 工作流

## 1. 文件定位

- 本文件只管任务前后两侧的横切规则：开始前查什么，执行前卡什么，结束时报什么。
- 项目类型流程在 `flow_*.md`；规则怎么写在 `governance.md`；专题规则按 `AGENTS.md` 入口按需读取。
- 本文件给 AI 执行，不做长表格自检；只保留能改变行为的触发、动作和边界。

---

## 2. 任务前体检

首次接触项目、切换目录、准备改文件或准备运行会改变状态的命令前，先做轻量体检。

必须检查：

- 仓库根：当前目录是否是用户目标项目。
- 工作区状态：是否已有用户改动、暂存内容、未跟踪文件。
- `.gitignore`：是否明显漏掉 `.env`、虚拟环境、缓存、索引、构建产物。
- 工具链：项目使用 `uv` / `pip` / `poetry` / `npm` / `pnpm` / `yarn` 中哪一种。
- 敏感和大体积产物：`.env`、密钥、模型权重、索引、数据库、日志、截图等是否可能误提交。

动作：

- 正常时不展开汇报，避免噪音。
- 发现异常时先报告异常和影响，再询问是否继续。
- 仓库根不一致、疑似密钥/环境文件暴露、已有用户改动可能被覆盖时，不得直接写入。

---

## 3. Taskwork 单步推进

触发:

- 中大任务。
- 规则、hook、lint、CI、settings、memory 维护。
- 架构、工具链、依赖、交付路径变更。
- 多文件改动、多阶段任务、用户正在纠偏或目标仍在讨论。

动作:

- 每次只推进一个 taskwork；一个 taskwork 只能有一个当前重心。
- 开始前说明本阶段目标、不做什么、当前想法、反对意见、是否需要用户拍板。
- 反对意见必须落到目标、成本、风险、上下文、验证或用户原意之一；不能写成空泛提醒。
- 执行中如果发现目标冲突、证据反转、成本失控、上下文不够干净，停止扩大改动，先重审。
- 完成后形成阶段闭包，再切换注意力到下一重心。

阶段闭包必须区分:

- 已拍板。
- 已执行。
- 推断。
- 未验证。
- 暂不处理。
- 下一重心。

用户可见程度:

- 连续推进或小任务: 短闭包即可，一两句话说明本阶段完成什么、未验证什么、下一步聚焦什么。
- 中大任务、高风险改动、规则/工具链/架构维护、多轮交接、上下文接近上限、用户纠偏或下一阶段需要重新拍板: 展示完整闭包。
- AI 必须先形成内部闭包，再决定展示粒度；不得用短汇报省略闭包判断。

边界:

- 小而明确的单文件修复可压缩 taskwork 表达，但仍需说明做了什么、验证了什么、剩余风险。
- 已闭包内容除非用户重新打开、证据反转或目标冲突，不反复争论。
- 如果闭包摘要不足，先说明缺口并回溯取证，不凭记忆补事实。
- 阶段闭包不是长期文档；只有稳定事实、架构决策或接力风险变化时，才沉淀到项目记忆层。

---

## 4. 执行前门禁

命中以下任一情况，先停在讨论态：

- 包管理或依赖操作前，尚未识别工具链和虚拟环境。
- 删除、覆盖、迁移文件或数据。
- 改公开 API、核心函数签名、跨模块契约。
- 重构涉及多个文件或多个模块。
- 数据库 schema、批量数据写入、索引重建、生产数据、安全边界或凭据相关。
- 用户意图、成功标准或影响范围不清。
- 缺少决策信息，且该信息影响方案、实现、验证、数据安全或生产风险。
- 新增外部依赖、工具链依赖、下载型 CLI、pre-commit/CI 工具。

动作：

- 说明要做什么、影响什么、为什么有风险。
- 给出回滚方式和回滚后验证点。
- 等用户拍板后再执行。
- 新增依赖或下载型工具时，先说明用途、必要性、安装位置、体积/耗时/网络风险、是否进入依赖/lock/CI/pre-commit、轻量替代方案和不引入的损失。
- 信息缺口先走最小触发器：AI 先自取；不能自取再问用户；仍不可得则标注未确认假设和验证方式。
- 信息缺口复杂、需要组织取证或假设分层时，再读取 `info_guidance.md`。

禁止：

- 未说明用途、成本和替代方案就新增依赖或运行会触发下载的工具。
- 用“应该没事”替代实际检查。
- 把横切风险混到完成汇报里事后才说。
- 自决删除 `.git/`、`.env`、锁文件、数据库、索引或用户资产。
- 把未确认假设写成事实。

---

## 5. 验证门

改动后必须按风险选择验证。存在直接相关测试时优先运行。

触发：

- 改的文件已有对应测试。
- 改的函数/路由/服务被测试 import 或调用。
- bug 修复。
- 行为变更。
- 重构影响调用链。

动作：

- 有测试且能运行：运行相关测试。
- bug 修复：优先补或运行能复现问题的用例。
- 行为变更：说明用什么路径验证新行为。
- 测试跑不了：说明原因、剩余风险和替代验证。
- 测试失败：先处理失败或回到讨论态，不把失败当作完成。

验证命令以项目配置为准，例如 `pytest`、`ruff`、`basedpyright`、`import-linter`、前端测试或 CI 命令。

---

## 6. 上下文耦合风险

同样的改动，在不同上下文中风险不同。以下情况会放大副作用：

- 工作区已有未提交或未跟踪改动。
- 暂存区混乱，用户可能随手 commit。
- 涉及 `.env`、密钥、锁文件、数据库、索引、生成产物。
- 改动叠加 git 历史操作、删除、迁移或批量写入。
- 用户正在纠偏或边界仍在讨论。

动作：

- 风险放大时先报告，不直接扩大改动范围。
- 必要时建议拆分步骤：先取证、再小改、再验证、最后讨论是否继续。
- 不借机做无关清理或重构。

---

## 7. 完成汇报

小任务完成时至少说明：

- 做了什么。
- 验证了什么。
- 没做什么或剩余风险。

中大任务完成时说明：

- 做了什么，涉及哪些文件或模块。
- 为什么这样做。
- 跑了什么验证，结果如何。
- 没跑什么验证以及原因。
- 工作区是否留下新文件、未跟踪文件、生成产物或需要用户关注的状态。
- 本次跳过、豁免或压缩了哪些规则。
- 涉及方案、架构、规则、工具链、重构时，说明反向审查结论。
- 如果任务包含多个 taskwork，必须给出短闭包或完整闭包，并明确下一重心或停止点。

禁止汇报：

- 与任务无关的审美建议。
- 用户已明确不关心的旁枝问题。
- “全部完成/都没问题”但不说明验证依据。

如果用户指出“你漏了 X”，立即补全，不争辩。
