# 浏览器自动化规则

本文件管浏览器自动化中的用户-AI协作、Playwright 能力选择和浏览器意外场景的鲁棒性设计。当前默认技术栈为 Playwright；除非用户明确要求，不主动切换 Selenium、RPA 或其他方案。

目标是让业务逻辑能实施: 登录能接上、页面变化能识别、失败能取证、批量能恢复、提交类动作不误操作，不靠猜测等待，不在目标系统状态不明时继续提交或抓取。

默认写业务自动化脚本。必要时可以使用 Playwright Test 测试脚本和录制功能辅助复现、验收、定位选择器和沉淀回归路径，但录制结果不能不经整理就当成稳定业务流程。

## 1. 先锁定业务闭环

写脚本前先明确:

- 业务动作: 打开、查询、抓取、下载、上传、提交、审批、删除。
- 成功信号: URL、页面提示、表格出现、下载完成、接口成功、状态字段变化。
- 失败信号: 登录页、权限提示、空结果、弹窗拦截、接口失败、超时、验证码、页面结构变化。
- 中止边界: 何时暂停等用户处理，何时保存进度退出，何时禁止继续批量执行。

轻量脚本: 一次性打开页面、读取少量公开信息、简单点击或截图；无登录态、无验证码、无批量循环、无写入或提交副作用。

- 优先使用 Playwright 原生 locator、自动等待和超时。
- 失败时至少保留错误原因和必要截图。
- 不引入复杂会话、检查点、反爬模拟。

复杂或高风险脚本: 登录态、会话恢复、批量抓取、下载、翻页、循环操作、iframe、弹窗、新 tab、动态加载、验证码、短信验证、滑块、人机验证、高价值系统、表单提交、状态变更、审批、删除、批量写入、重复提交。

- 先明确登录态、等待策略、失败取证、进度记录、检查点和中止路径。
- 涉及验证码、风控、强登录态或副作用提交时，先讨论授权、合规、失败影响和回滚方式。

## 2. 用户-AI协作边界

- 验证码、短信验证、滑块、人机验证默认视为访问控制或风控信号，不当作普通技术障碍。
- 默认策略是人工介入: 脚本暂停，提示用户完成验证，然后继续。
- 第三方打码、识别模型、绕过策略、反检测模拟必须先和用户讨论授权、合规和目标系统规则。
- 不确定目标系统是否允许自动化时，先问用户，不替用户假设。
- 保存账号、cookie、storage state、session 文件时，必须考虑敏感信息和本地保护。
- 凭据、cookie、storage state 不写入日志，不随便提交到仓库。
- 需要用户配合时，指令必须短: 当前卡在哪里、用户做什么、做完后脚本如何继续。
- 用户配合优先用于三类场景: F12 取证、Playwright 自动取证后的业务确认、诊断性 JS 注入。
- F12 取证最多 3 步，说明去哪个面板、做哪个操作、回传什么内容、用于判断什么。
- 诊断性 JS 注入只用于读取 DOM 状态、验证事件链或定位页面问题，不用于绕过权限、风控或业务校验。
- 用户反馈业务结果和脚本取证矛盾时，继续取证，不强行解释。

## 3. 登录态、会话和长任务恢复

- 强登录态系统和长任务必须有登录态检测: 跳转登录页、特定错误提示、关键元素缺失、接口返回异常等。
- 会话过期处理必须明确: 暂停通知用户、保存进度退出、或在用户确认后重登录。
- 批量任务应有检查点或失败清单，避免失败后只能从头重跑。
- 多次运行的浏览器上下文、`user-data-dir`、storage state 应明确复用或隔离策略。
- 运行结束和异常退出应关闭 context/browser，并清理临时目录或说明保留原因。

## 4. 浏览器状态机

轻量脚本不用状态机。登录、批量、提交、下载、验证码、多页面切换时，至少用状态机思维列出关键状态和中止条件。

- 常见状态: `INIT`、`NEED_LOGIN`、`NEED_HUMAN_VERIFY`、`READY`、`RUNNING`、`BLOCKED_BY_DIALOG`、`DOWNLOADING`、`FAILED_RETRYABLE`、`FAILED_FATAL`、`DONE`。
- 状态切换必须来自可观察信号: URL、关键元素、页面提示、接口响应、下载事件、弹窗事件。
- 未识别状态时先截图 / 记录 URL / 保存现场，不继续提交、审批、删除或批量写入。
- 可重试失败和致命失败要分开；重试前确认不会造成重复提交、重复下载或重复写文件。

## 5. 优先用 Playwright 强能力

- 优先使用 Playwright 自动等待、语义 locator、role/text/label/稳定属性等稳定选择器。
- 关键元素要等待明确状态: visible、attached、enabled、detached 或 URL/network 状态。
- 新 tab / 弹窗用 Playwright 的 popup/page 事件等待，下载用 download 事件等待，dialog 提前注册处理。
- iframe 优先用 frame locator 或明确 frame 定位，跨 frame 后重新定位元素。
- 复杂失败优先开启 trace；截图、HTML、console、network 作为现场证据。
- 必要时用 Playwright Test 固化关键路径验收，或用录制功能辅助识别页面结构和选择器。
- 原生 Playwright 能表达的等待、定位、上传、下载、弹窗处理，不先用 JS 注入绕过。

## 6. 浏览器意外的鲁棒性设计

- 页面跳转、新 tab、弹窗、iframe 切换后，必须重新获取 page/frame/locator，不复用旧句柄。
- 动态 ID、时间戳、随机 class 不能作为稳定选择器。
- 禁止用固定 `time.sleep` 代替等待条件；外部系统节流、下载生成等少数场景也必须优先使用 Playwright 等待或 `page.wait_for_timeout` 并说明理由，避免触发 semgrep 硬拦截。
- 超时不是单纯调大 timeout，要判断页面没加载、选择器错、权限失效、接口失败、弹窗遮挡、iframe 未切换。
- 可能出现 alert/confirm/prompt 时，应在触发操作前注册或准备 dialog 处理。
- 自定义模态框按普通 DOM 处理，但要确认遮罩、焦点和按钮实际生效。
- iframe 和多层 iframe 必须显式定位 frame，跨 frame 后重新定位元素。
- 文件上传优先用 Playwright 官方方式，如 `set_input_files`；系统文件选择器和拖拽上传需要单独验证。
- 文件下载必须等待下载事件、确认文件完整写入，并记录保存路径。
- 原生 Playwright 操作失败后，才考虑 JS/CSS 注入。
- 注入后必须验证页面状态、表单校验、事件触发和后续请求，不以“没有报错”当成功。
- 注入不得绕过目标系统业务校验或权限限制。

## 7. 失败现场和用户协作取证

- 关键操作失败时，先自动取证，再打扰用户。
- 关键操作包括登录、提交、跳转、查询、抓取、翻页、下载、上传、状态变更。
- 自动取证优先保存: 截图、当前 URL、页面标题、关键 HTML、console 日志、最近失败请求、时间戳。
- 最低取证集: 当前 URL、全屏截图、失败操作名、时间戳、异常消息。
- 文件名包含时间戳和操作名，避免覆盖。
- 截图和 HTML 可能含敏感信息；保存路径、保留周期和分享范围要谨慎。
- 自动取证不足以定位时，再升级到用户 F12、业务页面确认或诊断性 JS 注入。
- 用户反馈和自动取证矛盾时，继续取证，不强行解释。

## 8. 批量执行、进度和数据安全

- 批量抓取、下载、提交应有进度反馈: 当前页 / 总页数、当前记录、成功 / 失败数量、预计剩余时间。
- 大批量任务应记录单次耗时或阶段耗时，避免用户不知道脚本是否卡住。
- 批量任务必须有失败清单，失败项不要静默丢失。
- 会产生副作用的操作必须考虑重复执行安全: 重复提交、重复下载、重复审批、重复写文件是否安全。
- 任务中断后必须能说明已完成什么、未完成什么、是否可重跑。

## 9. 验证记录

- 小脚本至少跑一次目标路径。
- 登录态、批量、下载、提交类任务要验证失败分支和恢复方式。
- 跑不了真实目标系统时，说明未验证项、需要用户配合的业务步骤和剩余风险。
