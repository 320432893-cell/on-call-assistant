# 派发协议（tier1）— 注意力的执行机制

派发是 `AGENTS.md § 1` 注意力预算的执行手段：把大量过程、小量结论的活甩给子 agent，省主线注意力。

## 1. 起点：探查还是编织

每步先问：下一步是**把信息找出来 / 铺开**，还是**基于已有信息往下推**？

| 类型 | 是什么 | 默认动作 |
|---|---|---|
| 探查 | 找 / 读 / 查 / 枚举 / 遍历 / 比对——过程量大、结论量小 | 默认派子 agent |
| 编织 | 决策 / 设计 / 拍板 / 串因果——需连续推理 | 主线自己做，不可委托 |

混合任务 MUST 拆：探查子阶段派出去，编织留主线；不闷头一把做完。

## 2. 派发三闸门

判为探查后，过三闸才真派；任一不过则主线自做：

- **独立**：子任务互不依赖结果，文件范围不交叠（交叠不并行）。
- **结论可压缩**：主线只要结果，不要过程。
- **值得**：派发协调成本 < 自做成本；小到一次 grep 不派。

## 3. 粒度

- 扁平多项 → N 个独立探查派 N 个并行子 agent。
- 树 / 递归 → 把**子树根**交一个 agent 内部递归、只回聚合结论；在“分支自包含”的层级派发，不在叶子层铺成 N 个 agent。

## 4. 信息获取边界

承接 `AGENTS.md § 3` 停下闸的“知识缺口”两格，落到派发动作：

- **本地信息**（文件、仓库状态、日志、配置、脚本输出）MUST 主动读取，不甩给用户。
- **外部信息抓取**（搜索、文档、官网核对）默认派子 agent。
- **AI 拿不到的**（外部系统、F12、验证码、账号权限、私有后台）＋ **用户的业务真相 / 意图 / 明确要求**才要求用户提供，不许猜（见 `AGENTS.md § 3`）。

## 5. 协作纪律

- 派发后主线 MUST 继续推进可独立执行的下一步，不傻等。
- 主对话仅两个触点：派发瞬间一句话（任务 + 预期产出 + 文件范围 + 不阻塞主线）；合流瞬间一句话（结论 + 是否影响当前方案）。
- 子 agent 只做可复核的只读分析或授权的小范围任务；不得操作 UI、改业务状态或替主线拍板。
- 子 agent 复核的独立性是打折的（同源训练可能一起错）——真正独立的兜底是 oracle / 现实 / 用户（见 `AGENTS.md § 6.4`）。

## 6. 风险发散用派发（治“想不到高风险环节”）

高风险点不住在业务描述里，住在执行的缝里——这是探查任务，AI 主导、可派并行子 agent：

1. 翻译：业务流 → 执行流（步骤 + 步骤间的缝）。
2. 走每一步，强制问四种不出现在 happy path 的模式：**半成**（做一半中断）/ **重跑**（幂等吗）/ **乱序**（B 在 A 生效前跑）/ **中间态**。
3. 每步向下游追：错了爆炸半径多大、会不会被发现（`AGENTS.md § 0` 风险轴）。
4. 打分排序，产出结构化表：步骤 → 承重假设 → 爆炸半径 → 可检测性 → 谁担保。

分工：AI 保广度（浮出所有候选 + 翻译成“错了代价多大”）；用户用领域真相剪枝 / 加权；再派一个子 agent 专做**对抗补全**（“哪个高爆炸种子步不在这张表上？”）。
“半成 / 重跑”对操作型系统是一等问题，不埋进回退里。
