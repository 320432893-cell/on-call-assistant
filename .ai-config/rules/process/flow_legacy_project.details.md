# 老项目流程

## 0. 读取路径

默认只读主路径，避免小改被全项目审计拖住:

- `1. 文件定位`
- `2. 核心原则`
- `5. 体检分级`
- `6. 改前影响图`
- `10. 改后回扫`
- `11. 退出条件`
- `13. 本流程反模式`

按需读取:

- 接手陌生项目、陌生模块或用户要求先熟悉 -> `3. 接手 / 熟悉模式`
- 中大改、文档过期、模块职责 / 入口 / 配置 / 架构边界变化 -> `4. 项目记忆层`
- 影响范围不清、引用方分散、调用链复杂 -> `7. 散弹度与阻塞判断`
- 需要用户在多种走法里拍板 -> `8. A/B/C 走法`
- 用户明确说急、救急、先止损 -> `12. 紧急通道`

边界:

- 读取路径只控制注意力，不降低执行门禁。
- 命中按需段落时，只读该段和当前主路径相关内容，不顺手展开其他段。
- 如果不确定是否需要读取某段，按全局“阶段切换与规则读取”机制问用户一句。

## 1. 文件定位

触发:

- 已有项目改功能。
- 修 bug。
- 重构。
- 优化。
- 接手陌生代码。
- 修改已有接口、配置、数据流、状态流。

动作:

- 本文件用于老项目或已落地项目的增量维护。
- 核心目标是控制影响面，避免把已有复杂度改得更乱。
- 老项目每阶段都按全局“注意力锚”和“阶段切换与规则读取”机制执行；只读取能改变当前判断的规则。
- 不向上引用其他规则，不绑定特定 AI 工具 hook 路径。
- 机械检查交给成熟工具和项目现有工具；本文件只管 AI 如何判断、解释和决策。

边界:

- 新项目从零设计走新项目流程。
- 线上事故走救火流程。
- 小改不强制全项目审计，但必须做局部影响检查。

## 2. 核心原则

老项目先读现状，再判断改法，再动手。

AI 必须反对两类风险:

- 不体检就改。
- 借小需求夹带大重构。

默认策略:

- 局部一致优先于引入新范式。
- 最小破坏优先于顺手优化。
- 可回滚优先于大步改造。
- 复用现有能力优先于新造轮子。
- 先缩小影响面，再写代码。

注意力优先级:

1. 用户原始意图和本次改动边界。
2. 现有代码事实、调用方和影响深度。
3. 可验证路径和回滚路径。
4. 是否触及 source of truth、数据流、状态流、公共接口或配置。
5. 新改法会牺牲什么，以及牺牲是否值得。

反向审查:

- 老项目过度保守会延续坏设计。
- 需要引入新风格、新工具、新抽象时，必须把它作为明确改造范围，而不是夹带进小需求。
- 如果改造方案只说“旧代码太乱 / 结构太差 / 应该现代化”，但不说明当前需求被什么具体风险阻塞，视为夹带重构。

## 3. 接手 / 熟悉模式

触发:

- 首次接触陌生项目或陌生模块。
- 用户明确说“先接手”“理解一下”“先熟悉熟悉”。
- 切换到陌生工作目录，需要建立心智模型才能动手。

动作:

- 只读，不改代码。
- 目标是建立最小心智地图，而不是全量审计。
- 先做客观测绘，再决定通读 / 不通读。
- 结果沉淀到项目记忆层，不另建一次性接手主产物。

最小测绘:

- 项目入口。
- 运行 / 测试方式。
- 核心目录职责。
- top 大文件或复杂模块。
- 关键依赖。
- 关键数据流 / 状态流。
- 用户已知雷区。

通读判断:

- 小项目可通读核心文件。
- 中大型项目只读入口、核心链路、近期相关模块。
- 禁止假装全量理解。
- AI 必须声明读了什么、没读什么、理解置信度和下一步建议。

用户协同:

- 哪些地方你知道容易出问题？
- 哪些模块历史上改崩过？
- 哪些业务规则代码里看不出来？
- 哪些地方你希望我先别碰？

边界:

- 用户只是要求熟悉时，不进入改动流程。
- 用户切换到明确改动任务后，再按小改 / 中改 / 大改执行分级。

## 4. 项目记忆层

老项目通常会被多次接手，不能每次从零摸索；但文档也不能无限膨胀。

统一产物:

- `docs/PROJECT_MAP.md`: 长期项目地图、易懂架构图、架构边界和 source of truth。
- `docs/AI_HANDOFF.md`: 下一次 AI / 人接手需要的信息。

这些产物同时服务新项目和老项目。新项目落地后自然进入老项目维护阶段，不应重新设计一套文档。
专题规则提到这些产物时，只表示“判断是否需要读取或维护”，不表示每次任务都全量读取或写入。

### 4.1 PROJECT_MAP

只记录稳定事实:

- 项目目标和交付物。
- 运行入口。
- 测试命令。
- 核心目录职责。
- 关键数据流 / 状态流。
- 易懂架构图。
- 架构边界。
- source of truth。
- degraded / 回退策略。
- 外部依赖。
- 配置 / secrets 策略。
- 高风险模块。
- 常用排查命令。

禁止:

- 写聊天过程。
- 写临时猜测。
- 写大段解释。
- 把一次性任务细节塞进长期地图。

### 4.2 AI_HANDOFF

只记录下一次接手必要信息:

- 最近改了什么。
- 为什么改。
- 影响范围。
- 已验证什么。
- 未验证什么。
- 遗留风险。
- 下次接手先看哪里。

维护方式:

- 可以覆盖、压缩、滚动更新。
- 不做永久流水账。
- 有遗留风险时必须更新。

### 4.3 防膨胀纪律

- 小改不强制更新文档，除非发现文档过期。
- 中改触及模块职责、接口、测试入口、运行方式、配置时，检查并维护项目记忆层。
- 大改、重构、架构边界变化，必须维护项目记忆层。
- 每次维护只写未来接手真正需要的信息。
- 发现旧记录过期，先修正或删除，再新增。

反向审查:

- 不维护文档会导致每次接手重复摸索。
- 过度维护文档会制造噪音，最后 AI 和人都不读。

## 5. 体检分级

按任务规模选择体检深度，不做一刀切全项目审计。

### 5.0 执行分级

每次必做:

- 判断小改 / 中改 / 大改。
- 读相关文件。
- `rg` 调用方 / 引用方。
- 给改前影响图的最小版。
- 改后回扫。
- 说明是否需要更新项目记忆层。

每次必须说明本次改动对最终产物的破坏等级:

- 致命: 核心功能不可用、数据不可恢复、安全边界失效或关键入口无法交付。
- 高: 核心路径能跑但结果不可信、公共接口/状态流被带偏、回滚困难。
- 中: 局部功能、局部体验、局部排障或局部扩展受影响。
- 低: 边缘场景、内部整洁度、轻微效率或后续可优化项。

小改可一句话说明；中大改必须把破坏等级写进影响图。

条件触发:

- 触及接口、配置、数据流、测试入口，检查 `PROJECT_MAP` 是否需要更新。
- 触及架构边界、source of truth、degraded / 回退策略，检查 `PROJECT_MAP` 是否需要更新。
- 有遗留风险、未验证项、多轮任务，更新或压缩 `AI_HANDOFF`。
- 发现项目记忆层过期，先修正或删除过期内容，再新增。

大改必做:

- A/B/C 走法。
- 用户拍板。
- 分阶段或回滚策略。
- 项目记忆层维护。

反向审查:

- 老项目流程默认只跑最小闭环，复杂时再升档。
- 小 bug 不应被全项目体检拖死。
- 核心链路和架构边界不应被当成小改糊弄。

### 5.1 小改

适用:

- 局部 bug。
- 小字段、小文案、小逻辑分支。
- 不改公共接口。
- 不改数据流 / 状态流。

必须做:

- 读相关文件。
- `rg` 调用方 / 引用方。
- 找对应测试或验证入口。
- 判断是否触及项目记忆层。
- 输出最多保留改动落点、引用方、验证方式、破坏等级和剩余风险；不得展开全项目审计。

### 5.2 中改

适用:

- 新增功能。
- 修改模块行为。
- 改配置、依赖、接口、测试入口。
- 影响多个调用方。

必须做:

- 改前影响图。
- 相关模块职责检查。
- 测试影响检查。
- 是否需要更新项目记忆层。
- 是否需要用户在多种走法里拍板。
- 说明本次新增或改造会牺牲什么: 速度、一致性、兼容性、可回滚性、测试成本、用户操作习惯或未来维护空间。

### 5.3 大改

适用:

- 重构。
- 架构边界变化。
- source of truth 改变。
- 数据流 / 状态流改变。
- 多模块、多入口、多角色受影响。

必须做:

- 高压力体检。
- A/B/C 走法。
- 用户拍板。
- 项目记忆层维护。
- 明确回滚或分阶段策略。
- 每个走法都必须说明牺牲项，以及为什么值得承担。

## 6. 改前影响图

改任何老代码前，AI 必须输出与任务规模匹配的影响图。

最小影响图必须包含:

- 改动落点。
- 调用方 / 引用方。
- 影响测试。
- 可能触及的数据、配置、接口。
- 是否引入新风格或新范式。

中大改额外包含:

- 影响模块。
- 影响数据流 / 状态流。
- 是否触及 source of truth。
- 是否触及项目记忆层。
- 回滚方式或分阶段方式。
- 对最终产物的破坏等级。
- 本次改法会牺牲什么，牺牲是否值得。

禁止:

- 只看一个文件就改公共行为。
- 不查调用方就改函数签名。
- 不查已有能力就新建 utils / helper。
- 不说明影响范围就开始重构。

## 7. 散弹度与阻塞判断

散弹度是风险信号，不是绝对数字。

AI 应用 `rg` 或项目工具识别:

- 需求关键词出现位置。
- 相关函数 / 类 / 配置引用方。
- 调用链上的测试。
- 旧名、旧接口、旧配置残留。

需要阻塞并让用户选方案的情况:

- 影响多个模块或多个调用链。
- 触及核心状态、数据流或 source of truth。
- 需要改公共接口。
- 现有测试缺失且影响不可局部验证。
- 需求会迫使风格或范式分裂。
- 修改范围超过用户原始意图。

反向审查:

- 4 个很薄的调用方不一定危险。
- 2 个核心烂文件也可能很危险。
- 判断重点是影响深度，不是只看数量。

## 8. A/B/C 走法

阻塞时，AI 必须给用户选择，不得自行决定。

A. 直接局部改:

- 适合短期、低风险、影响面清楚的任务。
- 必须说明会留下什么债。

B. 先小范围整理阻塞点再改:

- 适合长期项目。
- 整理范围必须和本次需求直接相关。

C. 先重构 / 补测试，不加新功能:

- 适合当前结构已经阻碍安全改动。
- 必须说明用户何时复核，何时再进入功能实现。

AI 可以推荐一个走法，但必须说明代价和反例，最终由用户拍板。

推荐要求:

- 至少对照一个更小范围走法和一个更彻底走法，说明为什么不选。
- 反向论证不能只说“改动太大 / 结构太乱 / 太保守”；必须落到当前调用链、测试缺口、回滚风险、用户验收或长期维护事实。

## 9. 改动纪律

必须:

- 融入现有代码风格。
- 复用已有工具函数、配置、模块。
- 保持本次需求边界。
- 把新增抽象控制在真实复杂度之内。
- 对临时兼容写明未来清理条件。

禁止:

- 顺手重构无关代码。
- 引入第二套风格或范式。
- 重复造已有能力。
- 偷偷扩大需求范围。
- 把临时兼容写成长期架构。
- 为了“现代化”破坏老项目一致性。

反向审查:

- 如果老项目现有做法明显有害，可以提出改造，但必须单独列为用户决策，不夹带执行。

## 10. 改后回扫

改完必须按影响范围回扫。

检查:

- 旧名 / 旧调用 / 旧配置是否残留。
- 调用方是否全部更新。
- 对应测试是否存在并运行。
- 工具检查是否通过。
- 项目记忆层是否需要更新。
- 保留风险是否已说明。

阻断:

- 漏改调用方，必须补改或说明保留理由。
- 公共接口改了但测试未覆盖，必须说明风险。
- 文档过期但未修正，必须补维护或说明为什么本次不维护。

## 11. 退出条件

用户拍板并完成本次增量改动后，本流程在当前任务结束。

后续默认:

- 同一模块继续小修: 继承本次已确认事实，但重新做局部影响检查。
- 需求扩大、公共接口变化、source of truth 改变、数据流 / 状态流改变: 升档到中改或大改。
- 变成从零设计新模块或子系统: 切回新项目流程对应阶段。
- 线上事故或严重数据异常: 切到救火流程。

边界:

- 不得因为本次做过高压力体检，就在后续小修时重放全部分析。
- 已被用户否决的走法不带入下一任务，除非出现新证据。

## 12. 紧急通道

用户明确说急时，可以跳过完整体检，但不能跳过:

- 改动落点。
- 调用方 / 引用方检查。
- 回滚方式。
- 改后验证。
- 降级风险说明。
- 为了速度牺牲了什么，以及后续什么时候补。

紧急通道禁止:

- 借急扩大改动。
- 跳过公共接口影响检查。
- 把临时修复包装成长期方案。

## 13. 本流程反模式

- 不读现状直接改。
- 小需求夹带大重构。
- 全项目体检拖死小 bug。
- 小改输出全项目审计，消耗用户和 AI 注意力。
- 不维护项目记忆层导致反复摸索。
- 过度维护文档导致没人读。
- 改签名不查调用方。
- 新建能力前不查已有实现。
- 引入新风格不让用户拍板。
- 只说“旧代码太乱 / 需要现代化”，不说明当前需求被什么具体风险阻塞。
- 不说明改法牺牲项，只说“更规范 / 更干净”。
- 完成一次大改体检后，在后续小修里反复重放全部分析。
