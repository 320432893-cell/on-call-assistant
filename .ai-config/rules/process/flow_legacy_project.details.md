# 既有项目补充规则

## 1. 重构 / 大改补充

适用：

- 跨模块调整。
- 公共接口变化。
- 数据流、状态流或架构边界变化。
- 行为保持不变但结构明显变化。

补充要求：

- 重构动机必须先收敛到一个主目标：加功能铺路、性能、可维护性、删除技术债或其他。
- 行为快照必须先于结构改动：现有测试、关键输入输出样本、必要性能基线。
- 范围边界必须写清白名单和黑名单。
- 风险按生产 / 数据 / 公共契约 / 跨模块 / 测试缺口排序。
- 拆成多个可验证、可回滚的小步；每步只处理一个结构变化。
- 黑名单问题记录到待办，不顺手修改。

沉淀：

- 新结构、行为快照、拒绝过的方案和未验证项写入项目记忆层。

## 2. 加新功能补充

适用：

- 新功能影响多个既有模块。
- 新功能引入新的数据、状态、权限、外部依赖或用户路径。
- 新功能形成独立模块 / 子系统。

补充要求：

- 先确认业务接入点：用户动作、入口、路由、命令或任务调度。
- 明确复用哪些既有模块、数据结构、权限、配置和错误处理方式。
- 明确 source of truth。
- 明确 degraded / 回退。
- 明确对既有路径、测试、部署、数据或用户可见行为的影响面。
- 形成独立模块 / 子系统时，借用新项目的业务理解、风险收敛和候选方案。
- 新功能必须服从既有项目结构；除非用户明确拍板，不借新功能重开整体架构。

沉淀：

- 新模块职责、接入点、source of truth、回退和未验证项写入项目记忆层。
