# 工作流

## 1. Taskwork 单步推进

所有任务默认按 taskwork 推进。

规则：

- 每次只推进一个当前重心。
- 开始前说明本阶段目标、不做什么、当前想法、相对取舍和边界、是否需要用户拍板。
- 执行中发现目标冲突、证据反转、成本失控或上下文不干净，先停下重审。
- 阶段完成后做短闭包，作为下一阶段上下文。

阶段闭包只保留：

- 已执行。
- 已拍板。
- 推断。
- 未验证。
- 暂不处理。
- 下一重心。

阶段切换时重新判断是否需要读取规则；每阶段只读能改变当前判断的规则。新分支不替换当前重心时，放入暂不处理或背景保留。

## 2. Git 和工作区体检

首次进入项目、准备改文件、准备提交或准备执行会改变状态的命令前，先做轻量体检：

- 仓库根是否正确。
- `git status -s` 是否有用户改动、暂存内容或未跟踪文件。
- 工具链是否清楚。
- 是否存在 `.env`、密钥、数据库、索引、模型权重、日志、截图、构建产物等敏感或大体积文件风险。

处理：

- 正常时不展开汇报。
- 发现异常时汇报路径、风险和建议下一步。
- 仓库根不一致、用户改动可能被覆盖、疑似密钥或私有文件暴露时，先等用户拍板。
- 提交前逐项判断未跟踪文件，不默认 `git add .`。

## 3. 重大操作声明

以下动作执行前必须先说明影响、风险和回滚方式，并等待用户拍板：

- 删除、覆盖、迁移、批量写入。
- 依赖安装、下载型工具、工具链变更。
- git 历史操作、批量暂存、清理暂存区。
- 数据库 schema、生产数据、安全边界、凭据相关改动。
- 公共接口、核心签名、跨模块契约、架构边界变化。

## 4. 验证和未验证

改动后按本次风险选择验证。

规则：

- 有直接相关测试时优先运行。
- 没有测试时走最小复现、静态检查、脚本检查或人工可复核路径。
- 本阶段改过代码文件时，阶段闭包前至少跑一次相关静态扫描；优先使用项目已有 Ruff / Semgrep / type check，不新增 hook。
- 静态扫描命中结构坏味道时，不直接重构，先读取 `../engineering/code.index.md` 做代码结构复盘。
- 验证失败且影响正确性时，不把任务报完成。
- 无法验证时，在阶段闭包里记录未验证项和剩余风险。

结构坏味道包括：

- 复杂度、分支、参数、布尔位置参数、无用参数、返回路径异常。
- 异常文本泄漏、裸后台任务、后台任务捕获请求级对象、用字符串化异常做控制流。
- 读型函数写状态、公共返回结构或异常语义变化、核心逻辑新增外部 IO / SDK 依赖。

命中后的处理：

- 先区分工具可直接修的局部问题、需要 `code.index.md` 复盘的结构问题、需要用户拍板的范式 / 破坏性变更。
- 只有结构问题达到“局部修补可能失效”的程度，才讨论状态机、策略、端口 / 适配器、错误模型等范式。

## 5. 接力和上下文压缩

上下文接近上限、依赖摘要继续会丢失关键决策，或规则维护/多阶段任务需要交接时，先产出接力信息。

接力信息保留:

- 当前目标。
- 已完成事项。
- 已修改文件。
- 用户已拍板内容。
- 禁止改动内容。
- 未验证风险。
- 下一步建议。

正在进行规则维护时，同时列出已讨论/已写入的规则文件、未讨论的规则文件和当前规则设计原则。
