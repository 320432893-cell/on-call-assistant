# 新项目 / 新模块流程

本文件是 `process/` 目录唯一保留的新项目特定触发规则。用户提出从 0 到 1 的新项目、新模块、新工具、新架构地基、MVP、展示用途或短期工具时读取本文件。

默认先停在本文件内完成判断。

## 1. 轻量判断

默认先判断：

- 交付形态和用户真实验收路径。
- 是小项目、MVP、展示用途，还是中大型长期工程。
- 当前是讨论态、草案态还是用户已拍板执行。
- 是否走简单版流程，还是升级到标准流程。
- 哪些问题必须用户拍板，哪些可以先用假设推进。

阻断：

- 验收标准、source of truth、degraded / 回退、不做什么、用户拍板点任一项不清楚，不进入架构候选或实现。

## 2. 普通简单版

适用：

- 小项目、MVP、展示用途或短期工具。
- 用户只需要先跑通一版。

只输出：

1. 当前理解：交付形态、验收动作、输入 / 处理 / 输出。
2. 业务理解复核：先复述主业务逻辑，再补边缘、异常和极端场景。
3. 最低地基：source of truth、degraded / 回退、不做什么。
4. 关键风险：先发散用户假设和同类项目常见问题，再收敛最多 3 条，按破坏等级排序。
5. 方案对照：极简方案 vs 够用方案；需要时补一个更稳方案。
6. 推荐方向和 1-3 个用户拍板点。

## 3. 标准流程

命中以下任一场景，走标准流程：

- 已判断为中大型项目、长期工程或新架构地基。
- 需要阶段门、交付形态与业务画像。
- 需要展开假设与风险、架构候选、拍板前骨架。
- 准备落盘中大型新项目、新模块、目录结构、工具链或架构地基。

阶段：

1. 交付形态与业务画像。
2. 业务理解复核。
3. 风险收敛。
4. 架构候选。
5. 拍板前骨架。
6. 进入实现。

阶段边界：

- 第 1 阶段只确认交付形态、验收、输入输出、业务规则和不做什么。
- 第 2 阶段先复述主业务逻辑，再补边缘、异常和极端场景。
- 第 3 阶段先发散假设，再从假设中挖风险，最后按破坏等级收敛。
- 第 4 阶段只比较 3-5 个差异化架构候选，不写代码骨架。
- 第 5 阶段只在用户选方向后展开开工骨架。

## 4. 交付形态与业务画像

必须明确：

- 交付形态是什么。
- 用户用什么动作验收。
- 输入、处理、输出分别是什么。
- 关键业务规则是什么。
- 异常数据、脏数据、边界条件是什么。
- 明确不做什么。

输出要求：

- 先声明当前只处理交付形态和业务画像。
- 简短列出当前理解。
- 标明未确认项。
- 问用户是否补充或纠偏。

## 5. 业务理解复核

进入风险和架构前，必须先让用户复核 AI 的业务理解。

复核内容：

- 先复述主业务逻辑：目标用户、核心动作、核心对象、主路径输入 / 处理 / 输出、验收重点。
- 再补充边缘场景：非主流输入、非典型用户动作、状态切换、重复操作、撤销或重试。
- 再补充异常场景：脏数据、缺数据、权限不足、外部依赖失败、超时、并发、部分成功。
- 最后补充极端场景：数据量暴增、长时间运行、不可恢复错误、安全边界、核心路径完全不可用。
- 明确本轮不做什么。

输出要求：

- 用项目业务语言复述，不只写技术词。
- 区分已确认事实、AI 当前假设、需要用户确认的问题。
- 先让用户确认主业务逻辑，再讨论边缘、异常和极端场景。
- 一次只问会影响验收、数据流、状态流、架构边界或回退策略的问题。
- 用户纠偏后，先更新业务理解，再进入风险收敛。

阻断：

- 业务目标、核心对象、验收路径或不做什么不清楚，不进入风险收敛。

## 6. 风险收敛

风险讨论先发散，再收敛；最终输出 5-8 条关键风险，按破坏等级从高到低排序。

发散步骤：

1. 先列用户显式假设：用户已经说出的业务规则、数据来源、用户行为、验收偏好和约束。
2. 再列 AI 推断假设：从业务理解、交付形态、数据流、状态流和外部依赖推出来的前提。
3. 再补同类项目常见问题：业务规则歧义、source of truth、状态一致性、权限、安全、可观测性、测试难度、扩展和运维边界。
4. 从这些假设中挖风险：只保留假设不成立时会破坏验收、架构、数据可信度或维护方向的项。

收敛规则：

- 先列致命和高风险；中低风险只保留会改变架构、验收或实现顺序的项。
- 同一破坏原因只保留最高影响的一条，不展开近似变体。
- 每个风险必须能推动用户确认、架构取舍或验证设计；否则删除。
- 风险讨论结束时，收敛成需要用户拍板的 1-3 个问题。

每条风险包含：

- 当前假设和依据。
- 如果假设不成立会发生什么。
- 对最终产物的影响：致命 / 高 / 中 / 低。
- 对架构、交付或维护的影响。
- 需要用户确认什么。

破坏等级：

- 致命：核心验收失败、数据不可恢复、关键路径不可用或安全边界失效。
- 高：核心路径能跑但结果不可信，或后续重构代价很高。
- 中：影响局部体验、性能、扩展或排障效率。
- 低：影响边缘场景、表达质量或轻微效率。

## 7. 架构候选

提出候选前，先用成熟参照校准复杂度：

- 大一档参照：多出来什么复杂度。
- 小一档参照：省掉什么能力。
- 当前项目保留什么、砍掉什么、为什么。

候选数量：

- 标准流程给 3-5 个差异化候选。
- 候选必须覆盖极简方案、中等够用方案、企业级或高防御方案。
- 候选差异必须体现在边界、状态管理、source of truth、回退、测试或运维复杂度上，不能只是技术栈换名。

每个候选包含：

- 架构思路。
- 成立前提。
- 模块边界。
- Source of truth。
- Degraded / 回退行为。
- 测试策略。
- 扩展点。
- 主要代价。
- 不适合场景。

比较要求：

- 比较长期维护成本，不只比较技术栈。
- 根据已有约束选择推荐方案：够用、防御性、标准做法三者之间明确取舍。
- 说明为什么当前选择足够，为什么不升到企业级，为什么不降到极简。
- 说明每个候选牺牲了什么：速度、灵活性、可维护性、可观测性、扩展空间、学习成本、交付确定性或用户体验。
- 说明推荐方案失效的边界：哪些业务变化、数据规模、并发、权限、安全、交付形态或维护要求会让该方案不再合适。

阻断：

- 候选只是同一方案的小变体，重新选择。
- 没有 source of truth 或 degraded 行为，补齐后再继续。
- 只讲优点不讲代价，补齐后再继续。

## 8. 拍板前骨架

用户选方向后，先输出骨架，再进入实现。

骨架包含：

- 目录结构。
- 核心模块职责。
- 对外接口。
- 数据流 / 状态流。
- 关键依赖。
- 配置 / secrets 策略。
- 测试分层。
- 验证预算。
- 后续最可能变化点。
- 暂不处理事项。

边界：

- 用户未选方向前，不输出完整目录树。
