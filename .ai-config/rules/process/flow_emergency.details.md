# 救火型流程

## 0. 读取路径

默认只读主路径，避免救火时被大清单拖住:

- `1. 文件定位`
- `2. 不触发边界`
- `3. 处理强度分档`
- `4.1 最小执行闭环`
- `5. 硬红线`
- `7. 完成标准`
- `8. 本流程反模式`

按需读取:

- 需要用户协同补充事实 -> `4.2 取证协作`
- 需要判断临时恢复还是长期修复 -> `6. 止血 vs 根因修复`
- P0 / P1 / P2 判定不清 -> 只回看 `3. 处理强度分档` 对应段落，不展开全文件。

边界:

- 读取路径只控制注意力，不降低硬红线。
- 如果发现其实是小 bug，立即降级回老项目小改流程。
- 如果不确定是否继续读取某段，按全局“阶段切换与规则读取”机制问用户一句。

## 1. 文件定位

触发:

- 线上故障。
- 生产事故。
- 数据异常。
- 难复现且影响范围不明的问题。
- 严重 bug。
- 高风险排障。

动作:

- 本文件名字叫救火，但不等于永远追求最快修复。
- 目标是建立事实链、避免二次伤害、按风险选择止血或根因定位。
- 每阶段按全局“注意力锚”和“阶段切换与规则读取”机制执行，只保留当前轮取证或止血所需上下文。
- 不向上引用其他规则，避免读取链路膨胀。

边界:

- 日常小改、局部 bug、开发环境可复现问题，默认不进入本流程。
- 本流程不是普通“用户说急”的加速通道；越高风险越不能跳过取证和确认。

## 2. 不触发边界

以下场景默认走老项目小改流程，不进入本流程:

- 局部路径解析 bug。
- 文件 / 文件夹兼容性小改。
- 单个函数或单个模块内的行为微调。
- 开发环境可复现的小 bug。
- 不涉及生产数据、线上用户、不可逆操作、核心状态流的问题。

除非同时命中以下任一条件，才升级为本流程:

- 影响线上或真实用户。
- 数据可能损坏、丢失或不一致。
- 问题难复现且影响范围不明。
- 修复需要改公共接口、核心状态流、source of truth。
- 用户明确说明这是高风险问题。

降级动作:

- AI 发现问题其实是小改时，必须主动降级。
- 推荐话术: “这看起来是老项目小改，不需要进入高风险排障。我建议按局部影响图 + 调用方检查 + 回归验证处理。”

反向审查:

- 不能为了显得谨慎，把小 bug 套成事故流程。
- 也不能因为多数任务是小改，就削弱真正高风险问题的硬门禁。

## 2.1 救火注意力优先级

进入本流程后，AI 只把主要算力放在以下判断:

1. 问题是否还在扩大。
2. 影响范围: 用户、业务、数据、核心路径、外部依赖。
3. 哪些动作会改变现场或增加二次伤害。
4. 当前证据链: 错误、时间线、近期变更、复现或监控。
5. 是否有止血、回滚、快照或只读取证路径。

禁止:

- 在证据链不足时展开长期架构建议。
- 在 P0 未止血前追求完整根因。
- 在只是小 bug 时继续套事故流程。

## 3. 处理强度分档

进入本流程后，AI 必须先判定处理强度。

判定依据必须落到:

- 是否影响线上或真实用户。
- 影响是否还在扩大。
- 是否存在数据损坏、丢失或不一致风险。
- 是否影响核心路径或安全边界。
- 是否可回滚、可快照、可只读取证。

### 3.1 P0：线上正在扩大

目标:

- 止血。
- 保现场。
- 降低影响范围。

执行:

- 只做最小必要取证。
- 优先确认影响范围和是否继续恶化。
- 写操作强门禁。
- 根因修复可以后置。

禁止:

- 为了完整定位拖延止血。
- 连续尝试多个修复假设。
- 无快照做不可逆操作。

### 3.2 P1：高风险但可控

目标:

- 建立证据链。
- 定位根因。
- 设计可验证修复。

允许:

- 较完整取证。
- 临时调试日志。
- 复现测试。
- 只读数据检查。
- 增加监控指标。

要求:

- 每个动作说明是否会改变现场。
- 临时日志、诊断代码必须有清理条件。
- 写操作后置。

### 3.3 P2：难复现 / 数据异常 / 严重 bug

目标:

- 复现问题。
- 缩小范围。
- 证明问题边界。

允许:

- 构造最小失败用例。
- 写回归测试。
- 加诊断代码。
- 分析数据样本。
- 对比正常样本和异常样本。

要求:

- 不急着修，先证明问题存在和边界。
- 诊断代码必须可删除或有开关。
- 数据检查优先只读。

## 4. 主动协同取证

救火时，AI 必须主动组织取证，而不是等待用户自行提供完整信息。

用户不是只会聊天的信息源；用户可以跑命令、看监控、问业务方、复现场景、确认近期变更、判断影响范围。

### 4.1 最小执行闭环

进入本流程后，默认先做一轮最小闭环，避免一次性展开过多问题。

步骤:

1. 判定 P0 / P1 / P2。
2. 问 3 个关键问题: 错误是什么、什么时候开始、影响多大。
3. 给 1-3 个低风险取证动作。
4. 基于结果判断下一步: 止血、继续取证、写复现测试、小范围修复。
5. 每轮只推进一个假设。

只有满足以下条件才升档:

- 影响范围扩大。
- 数据可能损坏。
- 取证结果互相矛盾。
- 需要改公共接口、数据流、source of truth。
- 用户明确要求深入排查。

反向审查:

- 不加闭环会导致 AI 一次性抛出大清单，拖慢用户。
- 闭环过窄会漏掉高风险信号，所以出现升档条件时必须扩大取证。

### 4.2 取证协作

第一轮先问 3 个关键问题:

- 完整错误文本 / 日志 / 截图是什么？
- 什么时候开始，最近改了什么？
- 影响范围多大，是否还在扩大？

随后按结果给低风险取证清单:

- 复制完整错误文本、日志片段、stack trace。
- 确认开始时间、最近一次正常时间、近期部署 / 配置 / 数据导入 / 人工操作。
- 查看监控: 错误率、延迟、流量、资源、队列、第三方依赖。
- 复现一个最小失败场景。
- 确认影响范围: 多少用户、哪些业务、是否还在扩大。
- 补充 AI 无法知道的业务背景: 活动、批量任务、外部系统异常、运营动作。
- 做只读数据库查询或只读配置检查。
- 增加临时调试日志、复现测试、监控指标。

取证动作分级:

- 只读动作优先。
- 可能改变现场的动作，先说明风险，再确认。
- 不可逆动作，必须有快照和回滚方案。

禁止:

- 把“用户没给信息”当作猜测修复的理由。
- 一口气丢出巨大排查清单。
- 每轮给超过 3 个取证动作，除非用户要求完整排查清单。
- 让用户执行会改变现场的命令却不说明风险。

## 5. 硬红线

### 5.1 禁止猜测修复

禁止:

- 看了错误信息就直接改代码试试看。
- 没复现、没日志、没时间线就推断根因。
- 给“应该是这里”加改代码的组合。

正确做法:

- 先取证。
- 标明当前是假设还是证据。
- 证据不足时输出取证方案，而不是修复方案。

### 5.2 禁止连续尝试

禁止:

- 改一处不见效，立刻改另一处。
- 一个会话里试多个不同假设的修复。
- 没记录预期结果和回滚方式就动手。

正确做法:

- 一次只验证一个假设。
- 不见效先回滚、停止扩散或重新取证。
- 每次变更记录: 改了什么、为什么、预期结果、回滚方式。

### 5.3 禁止二次伤害

高风险动作必须单独确认:

- 重启服务。
- 清缓存。
- 改配置。
- 改数据库。
- 回滚发布。
- `force push` / `reset --hard`。
- 删除数据。
- 导出生产数据。

不可逆动作必须具备:

- 快照或备份。
- 回滚方案。
- 影响范围说明。
- 用户单独确认。

### 5.4 禁止单方面宣布修好

不能只说“修好了”。

完成说明必须包含:

- 复现验证。
- 监控验证或可替代验证。
- 根因或当前最可信解释。
- 是否仍有临时措施。
- 是否需要后续补偿、复盘、测试或文档维护。

## 6. 止血 vs 根因修复

止血:

- 目标是恢复服务或降低影响。
- 允许临时措施。
- 必须标注临时性。
- 必须有回滚或清理条件。

根因修复:

- 必须基于证据。
- 必须能解释为什么会出问题。
- 必须验证出事场景。

禁止:

- 把止血方案包装成永久修复。
- 在根因不明时大范围重构。
- 为了快速恢复破坏证据。

## 7. 完成标准

完成前必须回答:

- 问题是否已复现或已有足够证据。
- 改动是否只验证了一个假设。
- 出事场景现在是否通过。
- 监控或替代指标是否恢复。
- 临时日志、诊断代码、止血措施是否需要清理。
- 是否还有未验证风险。

未满足时:

- 不宣称彻底修复。
- 只能说当前状态、已验证事实、剩余风险和下一步。

## 8. 退出条件

根据当前状态切换流程:

- 确认只是局部小 bug: 降级回老项目小改流程。
- 已止血但根因未清: 结束本轮救火，另开根因定位任务，保留证据链和临时措施清理条件。
- 根因修复完成: 转老项目流程补测试、清理临时日志 / 诊断代码、维护必要文档。
- 涉及数据补偿、用户通知、复盘或长期防护: 明确列为后续任务，不包装成本轮已完成。

边界:

- 救火流程结束不等于所有后续工程债结束。
- 临时措施未清理时，不得宣称长期修复完成。

## 9. 本流程反模式

- 小 bug 套事故流程。
- 高风险问题按小改处理。
- 用户越急，AI 越猜。
- 无证据改代码。
- 连续试多个假设。
- 没快照就动生产数据或配置。
- 临时日志和诊断代码不清理。
- 止血方案被当成长期方案。
- 监控或复现未验证就宣布修好。
- P0 未止血就追求完整根因。
- 每轮抛出巨大取证清单，导致用户无法执行。
- 救火结束后不说明转入老项目、根因任务、补偿或复盘中的哪一种。
