# 项目接手

## 0. 读取路径与接手深度

本文件按接手深度读取，不默认执行完整深接手。

轻接手:

- 触发: 小修、小改、单模块任务、已有 `docs/PROJECT_MAP.md` 且未过期。
- 读取: `文件定位`、`0. 触发条件`、相关代码入口、现有项目记忆层。
- 动作: 只建立本次任务所需心智模型；不强制产出完整三份记忆层。

标准接手:

- 触发: 首次接触项目 / 新模块、用户要求“接手 / 理解一下 / 先熟悉”。
- 读取: `1. 前置`、`2. 核心步骤`、`5. 与流程层文件的衔接`。
- 动作: 做地图测绘，判断通读 / 不通读，必要时更新最小项目记忆层。

深接手:

- 触发: 架构调整、重构、长期维护、跨模块改动、生产风险、用户明确要求完整接手。
- 读取: 全文。
- 动作: 更新 `PROJECT_MAP`，必要时更新 `AI_HANDOFF`。

边界:

- 接手深度由任务风险决定，不因“第一次看到项目”自动进入深接手。
- 读取路径只控制注意力，不降低基础设施体检、用户拍板、雷区记录和过期记忆修正要求。

## 文件定位
- **按需加载**:首次接触项目、新模块、或用户要求"接手"时读
- 接手目标是**理解项目**(地图测绘 + 关键文件通读判断),不是改项目
- 配套机制是项目记忆层:
  - `docs/PROJECT_MAP.md`: 稳定项目地图
  - `docs/AI_HANDOFF.md`: 近期风险、未验证项、下次接手重点
- 接手完成后,新增功能/新模块走 `flow_new_project.index.md`;改老代码/修 bug/重构走 `flow_legacy_project.index.md`

---

## 0. 触发条件
- 首次接触新项目目录或新模块
- 用户明确说"接手"、"理解一下"、"先熟悉熟悉"
- 切换到陌生工作目录,需要建立心智模型才能动手

**不触发**:
- 纯文档阅读、一次性脚本(无后续改动意图)
- 已有 `docs/PROJECT_MAP.md` 且未过期,且当前任务不触及架构或近期风险 → 直接读取,跳过完整接手流程

## 1. 前置:开局体检

执行本流程前必须先完成 [workflow.index.md](workflow.index.md) 路由到的任务前体检(仓库根 / .gitignore / 暂存区 / 密钥 / 工具链)。

基础设施异常处理:

- 基础设施异常未报告时，不得写代码、改配置或执行有副作用命令。
- 只读地图测绘可以继续，但必须把异常标入接手风险或 `AI_HANDOFF`。
- 如果异常会影响测绘真实性，例如仓库根错误、依赖目录缺失、明显读错项目，必须先修正再继续。

## 2. 核心步骤(4 步)

### 步骤 1: 地图测绘(机械, 客观, 不糊弄)

只跑只读命令,**不下任何判断**。测绘命令必须按项目技术栈选择，不得默认所有项目都是 Python。

通用测绘目标:

```bash
总行数 / 文件数
入口候选
top 5 最长文件
主要依赖 / 框架
运行方式候选
```

Python 项目示例:

```bash
find . -name "*.py" -not -path "*/.*" -not -path "*/node_modules/*" | xargs wc -l 2>/dev/null | tail -1
find . -name "*.py" -not -path "*/.*" -not -path "*/node_modules/*" | wc -l
```

其他项目按文件类型和配置调整:

- JS / TS: `package.json`、`src`、`*.js`、`*.ts`、`*.tsx`、入口脚本。
- Web 前端: 路由、页面目录、构建配置、组件入口。
- Go: `go.mod`、`cmd`、`internal`、`*.go`。
- Java / Kotlin: `pom.xml`、`build.gradle`、`src/main`。
- 混合项目: 先识别主技术栈，再分别测绘关键部分。

输出格式:
```
[地图测绘]
- 总行数: ____ 行
- 源文件数: ____ 个
- 项目入口候选: ____
- top 5 最长文件: ____
- 主要依赖 / 框架: ____
- 运行方式候选: ____
```

### 步骤 2: AI 主动决定通读 / 不通读

基于地图测绘结果,AI **显式声明**决定:

```
[接手决定]
- 项目规模: ____ 行 / ____ 文件
- 我的决定: □ 通读(项目较小,通读可行) □ 不通读(项目较大,只做测绘 + 用户口述雷区)
- 理由: ____
- 请用户确认或反驳: ____
```

> **用户拍板规则**:用户可要求提高读取深度(如"5000 行,我希望你通读")。AI 必须说明上下文成本、遗漏风险和可替代抽样方案；用户确认后，按确认的读取边界推进。

### 步骤 3: 按决定执行

| 决定 | 动作 | 项目记忆层完整度 |
|------|------|----------------------|
| **通读** | 通读入口 + 全部源文件 → 产出/更新项目记忆层 + 主动报反模式作为雷区候选(用户拍板) | 完整: `PROJECT_MAP` + 必要 `AI_HANDOFF` |
| **不通读** | 只填客观事实(入口 / 行数排名 / 依赖) → AI 只给证据型低置信风险候选,不做结论；雷区仍以用户口述为准 | 简版: 最小 `PROJECT_MAP` + 用户口述风险写入 `AI_HANDOFF` |

### 步骤 4: 主动问用户口述问题

完整接手必须覆盖以下问题；如果用户已经提供部分信息，只补缺口，一次最多问 3 个:
- 哪些地方你早就知道是雷区,改的时候要小心?
- 哪些地方是别人写的,你也不太懂?
- 上次改它出过什么问题?

用户回答 → 进雷区清单。

## 4. 阻断条件

- 标准 / 深接手未完成对应步骤直接改代码 → **[阻断] 易出现调用链断裂、幽灵引用、状态不一致**
- 基础设施异常未报告就写代码、改配置或执行有副作用命令 → **[阻断] 先跑 workflow.index.md 任务前体检**
- `docs/PROJECT_MAP.md` / `docs/AI_HANDOFF.md` 与代码现状已不一致 → **[阻断] 先修正或标注过期,不能基于过期心智模型动手**
- AI 自行决定通读/不通读但未显式声明给用户 → **[阻断] 步骤 2 必须显式,用户可反驳**

---

## 5. 与流程层文件的衔接

接手完成后:
- **新增功能/新模块,涉及架构决策** → 走 `flow_new_project.index.md`
- **改老代码 / 修 bug / 重构** → 走 `flow_legacy_project.index.md`(其门 3 必读雷区清单,命中则按既定决策,不重复问)
- 稳定事实变化 → 更新 `PROJECT_MAP`
- 架构边界、source of truth、degraded / 回退变化 → 更新 `PROJECT_MAP`
- 有近期风险、未验证项、下次接手重点 → 更新或压缩 `AI_HANDOFF`

---

## 6. 反模式

- ❌ 跳过地图测绘直接通读 → 大项目 AI 通读 = 必糊弄
- ❌ AI 自行通读不报告 → 用户失去拍板权
- ❌ 把所有首次接触都升级成深接手 → 小任务会被流程拖垮
- ❌ 把非 Python 项目按 Python 命令测绘 → 地图从一开始就是错的
- ❌ AI 主动评价老代码"是屎山"→ 应"雷区"中性词 + 用户口述
- ❌ 接手中发现基础设施异常不汇报,蒙头继续
- ❌ 不维护项目记忆层,下次接手又重做一遍
- ❌ 把稳定事实、架构决策、临时风险全塞进一个文件,导致后续上下文不干净
