# 工作流

## 1. 文件定位

- 本文件只管任务前后两侧的横切规则：开始前查什么，执行前卡什么，结束时报什么。
- 项目类型流程在本专题的 `flow_*.index.md`；规则怎么写在 `../rule_governance/governance.index.md`；专题规则按 `../index.md` 总索引和各专题 index 按需读取。
- 本文件给 AI 执行，不做长表格自检；只保留能改变行为的触发、动作和边界。

---

## 2. 任务前体检

首次接触项目、切换目录、准备改文件或准备运行会改变状态的命令前，先做轻量体检。

必须检查：

- 仓库根：当前目录是否是用户目标项目。
- 工作区状态：是否已有用户改动、暂存内容、未跟踪文件。
- `.gitignore`：是否明显漏掉 `.env`、虚拟环境、缓存、索引、构建产物。
- 工具链：项目使用 `uv` / `pip` / `poetry` / `npm` / `pnpm` / `yarn` 中哪一种。
- 敏感和大体积产物：`.env`、密钥、模型权重、索引、数据库、日志、截图等是否可能误提交。

动作：

- 正常时不展开汇报，避免噪音。
- 发现异常时先报告异常和影响，再询问是否继续。
- 仓库根不一致、疑似密钥/环境文件暴露、已有用户改动可能被覆盖时，不得直接写入。
- 首次接手、准备提交或发现仓库根可疑时，必须用 `git rev-parse --show-toplevel` 确认根目录，防止 IDE 在外层目录误 `git init`。
- 不默认使用 `git add .`；提交前必须先看 `git status -s`，逐项判断未跟踪文件。
- 若发现 `.env`、密钥、`.venv/`、`.claude/`、截图、大文件、模型权重、索引或 IDE 元数据已被暂存，先报告风险、受影响路径和建议命令；只有用户确认清理暂存区后，才能用 `git rm --cached` 撤出并补 `.gitignore`。
- 记住 `.gitignore` 只对未跟踪文件生效；已 tracked 的本地私有文件必须显式撤出索引。

## 3. Taskwork 单步推进

触发:

- 中大任务。
- 规则、hook、lint、CI、settings、memory 维护。
- 架构、工具链、依赖、交付路径变更。
- 多文件改动、多阶段任务、用户正在纠偏或目标仍在讨论。

动作:

- 每次只推进一个 taskwork；一个 taskwork 只能有一个当前重心。
- 开始前说明本阶段目标、不做什么、当前想法、反对意见、是否需要用户拍板。
- 反对意见必须落到目标、成本、风险、上下文、验证或用户原意之一；不能写成空泛提醒。
- 执行中如果发现目标冲突、证据反转、成本失控、上下文不够干净，停止扩大改动，先重审。
- 完成后形成阶段闭包，再切换注意力到下一重心。

阶段闭包必须区分:

- 已拍板。
- 已执行。
- 推断。
- 未验证。
- 暂不处理。
- 下一重心。

用户可见程度:

- 连续推进或小任务: 短闭包即可，一两句话说明本阶段完成什么、未验证什么、下一步聚焦什么。
- 中大任务、高风险改动、规则/工具链/架构维护、多轮交接、上下文接近上限、用户纠偏或下一阶段需要重新拍板: 展示完整闭包。
- AI 必须先形成内部闭包，再决定展示粒度；不得用短汇报省略闭包判断。

边界:

- 小而明确的单文件修复可压缩 taskwork 表达，但仍需说明做了什么、验证了什么、剩余风险。
- 已闭包内容除非用户重新打开、证据反转或目标冲突，不反复争论。
- 如果闭包摘要不足，先说明缺口并回溯取证，不凭记忆补事实。
- 阶段闭包不是长期文档；只有稳定事实、架构决策或接力风险变化时，才沉淀到项目记忆层。

阶段切换时必须同步规则读取边界:

- 已拍板: 当前阶段继承哪些用户决定。
- 当前只处理: 下一阶段唯一重心。
- 暂不带入: 上一阶段哪些展开讨论、被否决反对意见或旁枝不进入下一阶段。
- 规则读取: 哪些规则会改变当前判断；不确定时问用户一句是否读取。
- 规则路由: 中大任务、规则维护、多文件改动、多轮交接、用户纠偏或上下文压缩时，闭包必须带 `RULE_ROUTE`、`FOCUS`、`NEXT_TRIGGER`；`RULE_ROUTE` 只指向 index，不直接指向 details。

## 4. 执行前门禁

命中以下任一情况，先停在讨论态：

- 包管理或依赖操作前，尚未识别工具链和虚拟环境。
- 删除、覆盖、迁移文件或数据。
- 改公开 API、核心函数签名、跨模块契约。
- 重构涉及多个文件或多个模块。
- 数据库 schema、批量数据写入、索引重建、生产数据、安全边界或凭据相关。
- 用户意图、成功标准或影响范围不清。
- 缺少决策信息，且该信息影响方案、实现、验证、数据安全或生产风险。
- 新增外部依赖、工具链依赖、下载型 CLI、pre-commit/CI 工具。

动作：

- 说明要做什么、影响什么、为什么有风险。
- 给出回滚方式和回滚后验证点。
- 等用户拍板后再执行。
- 新增依赖或下载型工具时，先说明用途、必要性、安装位置、体积/耗时/网络风险、是否进入依赖/lock/CI/pre-commit、轻量替代方案和不引入的损失。
- 信息缺口先走最小触发器：AI 先自取；不能自取再问用户；仍不可得则标注未确认假设和验证方式。
- 信息缺口复杂、需要组织取证或假设分层时，再读取 `../reasoning/info_guidance.md`。

禁止：

- 未说明用途、成本和替代方案就新增依赖或运行会触发下载的工具。
- 用“应该没事”替代实际检查。
- 把横切风险混到完成汇报里事后才说。
- 自决删除 `.git/`、`.env`、锁文件、数据库、索引或用户资产。
- 把未确认假设写成事实。

## 5. 停止条件

命中以下任一情况，AI 必须停止扩大改动，回到只读取证、说明缺口或请求用户拍板:

- AI 开始猜用户意图，而不是引用用户原话、代码事实或工具输出。
- 工作区状态、仓库根、工具链或运行环境和预期不一致。
- 准备删除、覆盖、迁移或批量写入，但回滚路径不清。
- 准备新增依赖、下载型工具或工具链变更，但用途、代价和替代方案未说明。
- 同一问题连续两次修复失败。
- 当前目标和用户已拍板内容、上层规则或项目事实冲突。
- 关键事实来自摘要、接力或记忆，无法确认原始上下文。
- 验证失败且失败原因影响正确性、安全性或交付判断。

动作:

- 标明已确认事实、未确认假设、风险和最小安全下一步。
- 不得用继续试错代替重新取证。
- 如果只是低风险信息缺口，先自取；自取失败再问用户。

---

## 6. 验证门

改动后必须按风险选择验证。存在直接相关测试时优先运行。

触发：

- 改的文件已有对应测试。
- 改的函数/路由/服务被测试 import 或调用。
- bug 修复。
- 行为变更。
- 重构影响调用链。

动作：

- 有测试且能运行：运行相关测试。
- bug 修复：优先补或运行能复现问题的用例。
- 行为变更：说明用什么路径验证新行为。
- 测试跑不了：说明原因、剩余风险和替代验证。
- 测试失败：先处理失败或回到讨论态，不把失败当作完成。

验证命令以项目配置为准，例如 `pytest`、`ruff`、`basedpyright`、`import-linter`、前端测试或 CI 命令。

验证预算:

| 级别 | 场景 | 最低验证 |
| --- | --- | --- |
| V0 | 只读讨论、方案、规则评估但未写入 | 不运行验证；说明未写入 |
| V1 | 文档、小清理、低风险配置说明、已确认删除无依赖产物 | 结构复查、目标文件复查或 `git status` |
| V2 | 单文件代码改动、局部 bug、小功能 | 相关测试或最小复现路径；无测试时说明替代验证 |
| V3 | 多文件、跨模块、行为变更、重构、用户可见路径 | 相关测试 + 关键集成路径 + 必要静态检查 |
| V4 | 数据写入、迁移、生产影响、安全边界、不可逆操作 | 先确认备份/回滚，再执行验证；必要时分阶段验收 |

规则:

- 验证预算是最低要求，不是上限。
- Fast path 通常走 V1 或 V2；Guarded path 通常不低于 V2，高风险走 V4。
- 如果选择低于风险的验证级别，必须说明原因和剩余风险。

---

## 7. 上下文耦合风险

同样的改动，在不同上下文中风险不同。以下情况会放大副作用：

- 工作区已有未提交或未跟踪改动。
- 暂存区混乱，用户可能随手 commit。
- 涉及 `.env`、密钥、锁文件、数据库、索引、生成产物。
- 改动叠加 git 历史操作、删除、迁移或批量写入。
- 用户正在纠偏或边界仍在讨论。

动作：

- 风险放大时先报告，不直接扩大改动范围。
- 必要时建议拆分步骤：先取证、再小改、再验证、最后讨论是否继续。
- 不借机做无关清理或重构。

---

## 8. 完成汇报

小任务完成时至少说明：

- 做了什么。
- 验证了什么。
- 没做什么或剩余风险。

中大任务完成时说明：

- 做了什么，涉及哪些文件或模块。
- 为什么这样做。
- 跑了什么验证，结果如何。
- 没跑什么验证以及原因。
- 工作区是否留下新文件、未跟踪文件、生成产物或需要用户关注的状态。
- 本次跳过、豁免或压缩了哪些规则。
- 涉及方案、架构、规则、工具链、重构时，说明反向审查结论。
- 如果任务包含多个 taskwork，必须给出短闭包或完整闭包，并明确下一重心或停止点。

禁止汇报：

- 与任务无关的审美建议。
- 用户已明确不关心的旁枝问题。
- “全部完成/都没问题”但不说明验证依据。

如果用户指出“你漏了 X”，立即补全，不争辩。
