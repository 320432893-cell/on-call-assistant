# 新项目流程

## 0. 读取路径

默认只读主路径，避免所有新需求都被完整架构评审拖住:

- `1. 文件定位`
- `2. 核心原则：AI 推假设，用户找反例`
- `3. 注意力分配与阶段解耦`
- `4. 复杂度分档`
- `5. 第 1 门：交付形态与业务画像`
- `12. 本流程反模式`

按需读取:

- 进入风险识别 -> `6. 第 2 门：假设与风险`
- 需要方案比较或架构取舍 -> `7. 第 3 门：架构候选`
- 用户已选方向、需要实现前骨架 -> `8. 拍板前骨架`
- 用户确认写入项目记忆层 -> `9. 落盘门禁`
- 用户拍板进入实现或后续改动 -> `10. 退出条件`
- 用户明确说急 -> `11. 紧急通道`

边界:

- 小项目优先走轻流程，不默认读取完整风险、候选和骨架段落。
- 读取路径只控制注意力，不降低最低地基: 验收标准、关键假设、source of truth、degraded / 回退和用户拍板。
- 如果不确定是否需要读取某段，按全局“阶段切换与规则读取”机制问用户一句。

## 1. 文件定位

触发:

- 新项目。
- 新模块。
- 从零设计子系统。
- 需求边界不清，需要先定地基。

动作:

- 本文件用于新项目地基期。
- 新项目地基期允许高压力推理，因为早期架构错误的长期代价最高。
- 高压力必须先经过复杂度分档和注意力锚定；小项目只保留最低地基，不套完整大项目流程。
- 不向上引用其他规则，避免读取链路膨胀。
- 默认处于讨论态；未获用户明确写入授权前，不写代码、不落盘文档。

边界:

- 既有项目改动走老项目流程。
- 线上事故走救火流程。
- 小脚本、小页面、小工具仍触发本流程，但必须走轻流程，避免过度设计。

## 2. 核心原则：AI 推假设，用户找反例

AI 不只整理用户需求，必须主动提出假设、风险、反例和架构代价。

动作:

- AI 负责提出候选、前提、风险、边界和长期影响。
- 用户负责反驳、补充、压缩范围、选择方向。
- 用户负责确认业务事实、真实偏好、风险容忍度和最终取舍；AI 不替用户拍板。
- AI 可以表达偏向，但必须同时给出理由、反例和不适用场景。
- 涉及业务偏好、审美、面试展示策略、用户真实验收路径时，AI 必须暴露不可靠点。
- 最终架构方向由用户拍板。

高压力集中在:

- 验收标准。
- 关键假设。
- 架构边界。
- source of truth。
- degraded / 回退行为。
- 扩展点。
- 测试策略。

禁止:

- 直接进入编码。
- 只给一个方案让用户默认接受。
- 只论证 AI 推荐方案，不给保守方案或最小方案对照。
- 为了省事低估复杂度。
- 为了显得专业过度设计小项目。

## 3. 注意力分配与阶段解耦

新项目流程必须解耦为“先判断，再展开”。AI 不得把后续阶段的细节提前塞进当前阶段。

注意力优先级:

1. 验收标准: 用户如何判断最终产物成功。
2. 关键假设和破坏等级: 哪些假设一错会破坏最终产物。
3. Source of truth: 数据、状态、配置、用户输入或外部系统谁说了算。
4. Degraded / 回退: 外部失败、数据缺失、模型失败、权限失败时如何降级。
5. 候选方案牺牲项: 每个方案为了什么目标牺牲了什么。

阶段解耦:

- 第 1 门只处理交付形态和业务画像，不展开目录结构、框架选择、测试矩阵。
- 第 2 门只处理假设、风险和破坏等级，不急着给最终方案。
- 第 3 门只处理成熟参照和架构候选，不写代码骨架和文件清单。
- 拍板前骨架只在用户选方向后展开，不回头重开所有风险，除非出现新证据。
- 落盘门禁只处理文档写入，不顺手改业务代码、工具链或 hook。

算力预算:

- 小项目: 主要算力给验收标准、3 条关键风险、2 个候选的牺牲项；其他内容压缩。
- 中大型项目: 主要算力给 source of truth、degraded / 回退、边界切分、成熟参照和候选牺牲项。
- 不把算力浪费在过早目录命名、抽象层命名、完整测试矩阵、漂亮但未拍板的扩展点。

阻断:

- 当前阶段输出开始讨论后续阶段细节，先收束回当前门。
- 如果验收标准、业务画像、不做什么或 source of truth 任一项不清楚，不得继续输出架构候选。
- 如果用户只想快速试验，AI 必须切到小项目轻流程，而不是继续完整地基流程。

阶段切换:

- 每一门切换时按全局“阶段切换与规则读取”机制执行。
- 本文件只补充新项目各门的注意力边界；不重复定义通用规则读取流程。

## 4. 复杂度分档

进入高压力推理前，AI 必须先判定复杂度，并说明为什么。

### 4.1 小项目

特征:

- 一次性脚本、小页面、小工具、单人短期使用。
- 数据源少，状态少。
- 失败代价低。
- 后续扩展概率低。

执行:

- 3 条关键假设 / 风险。
- 2 个候选方案即可。
- 不强制完整架构矩阵。
- 仍必须有验收标准、source of truth、degraded / 回退说明。
- 默认用压缩表达，避免把注意力消耗在低收益架构展开上。

小项目轻流程只输出:

1. 验收标准。
2. 3 条关键假设 / 风险，带破坏等级。
3. 大一档 / 小一档成熟参照，各一句。
4. 2 个方案: 最小方案 vs 稳一点方案。
5. 推荐方案、牺牲项、需要用户拍板的 1-3 个点。

反向审查:

- 小项目最容易被 AI 过度设计。
- 若引入复杂框架、状态机、事件驱动、多层抽象，必须说明为什么值得。

### 4.2 中大型项目

特征:

- 长期使用。
- 多模块、多数据源、多角色、多状态，或多人维护。
- 失败代价高。
- 未来会扩展。

执行:

- 5-8 条关键假设 / 风险。
- 3 个候选方案。
- 必须比较架构边界、source of truth、degraded 行为、扩展点、测试策略。
- 必须说明每个候选会牺牲什么，以及这些牺牲是否值得。
- 用户拍板后才进入实现。

输出上限:

- 风险 5-8 条，不额外扩展低价值风险。
- 候选 3 个，不额外追加“也可以”方案。
- 拍板前不展开完整目录树、完整接口清单或完整测试矩阵。

反向审查:

- 中大型项目最容易被 AI 低估复杂度。
- 若想跳过风险和架构比较，必须明确说明可能的长期返工代价。

## 5. 第 1 门：交付形态与业务画像

进入方案设计前，必须明确:

- 交付形态是什么: Web 应用、HTML 展示页 / 演示稿、桌面 GUI、CLI、API 服务、脚本、exe、Docker、报告或其他。
- 用户用什么动作验收。
- 输入、处理、输出分别是什么。
- 关键业务规则是什么。
- 脏数据、异常数据、边界条件是什么。
- 明确不做什么。

职责边界:

- 本文件只确认交付形态是否影响架构和验收，不展开具体交付规则。
- HTML 做 PPT、网页式演示稿、报告导出等展示型交付，具体打包、入口、离线资源、投屏 / 打印验收归 `../delivery/package.index.md`。
- 桌面 GUI 的交互和线程模型归 `../engineering/gui.md`；Web 应用的组件状态和 API 调用归 `../engineering/frontend.index.md`。

阻断:

- 验收标准抽象，停止。
- 业务画像只有技术词，没有业务语义，停止。
- 不做什么没有边界，提示用户确认范围。

输出要求:

- 先声明当前主注意力只在交付形态和业务画像，不提前展开架构细节。
- 简短列出当前理解。
- 标明未确认项。
- 问用户是否补充或纠偏。

## 6. 第 2 门：假设与风险

这是本文件的主要高压力区。

按复杂度输出风险:

- 小项目: 3 条关键假设 / 风险。
- 中大型项目: 5-8 条关键假设 / 风险。

每条必须包含:

- AI 当前假设，以及推断依据。
- 如果假设不成立会怎样，必须是具体失败场景。
- 对最终产物的破坏等级: 致命 / 高 / 中 / 低，并说明为什么。
- 对架构、交付或维护的影响。
- 需要用户确认什么。
- AI 在这条风险上不可靠的点；如果没有，说明已由哪些事实支撑。

反糊弄门槛:

- 描述必须包含本项目业务名词、字段、约束、数据源、用户动作或模块名。
- 假设必须说明依据，不能凭空断言。
- 失败场景必须能用“如果 X，会 Y”表达，X 和 Y 都要具体。
- 共性风险必须本地化到本项目，不能堆行业模板。
- 用户指出反例后，AI 必须更新风险理解，而不是维护原判断。

风险覆盖面优先级:

- 业务规则误解。
- 数据源和 source of truth。
- 状态流 / 时序 / 并发。
- 第三方依赖和外部系统失败。
- 权限、安全、隐私。
- 可观测性和排障。
- 测试难度。
- 未来扩展点。

破坏等级判定:

- 致命: 最终产物无法通过核心验收、数据不可恢复、关键路径不可用或安全边界失效。
- 高: 核心路径能跑但结果不可信、维护方向会被带偏、后续重构代价很高。
- 中: 影响局部体验、局部性能、局部扩展或排障效率，但不破坏核心验收。
- 低: 主要影响边缘场景、表达质量、轻微效率或后续可优化项。

禁止:

- 只写“可能有数据问题”“可能有性能问题”。
- 无假设、无失败场景、无确认问题。
- 只列风险不标破坏等级。
- 用风险维度清单代替假设式风险。
- 自评“风险已覆盖完整”。
- 为了凑数量列低价值风险。

## 7. 第 3 门：架构候选

### 7.1 成熟架构参照

提出候选前，AI 必须先找成熟架构参照，但不能直接套模板。

动作:

- 找一个比当前项目大一档的成熟参照，说明它多出来的复杂度是什么。
- 找一个比当前项目小一档的成熟参照，说明它省掉了什么能力。
- 当前项目方案必须落在两者之间，说明保留什么、砍掉什么、为什么。

边界:

- 参照是用来校准复杂度，不是用来复制目录、框架或流程。
- 成熟参照可以是类型参照，不要求具体公司、产品或开源项目。
- 如果 AI 无法确认真实成熟案例，必须标注为“类比参照”，不得伪装成事实案例。
- 小项目可以用一句话压缩参照，但不能省略大一档 / 小一档对照。
- 如果只给“大项目最佳实践”，没有小一档对照，视为模板化风险。

反向审查:

- 成熟架构参照会增加讨论长度；只有当它帮助判断复杂度是否匹配时才展开。
- 如果参照结论只是“当前项目不要太复杂”，但没有说保留和砍掉什么，作废。

### 7.2 候选方案

候选数量:

- 小项目默认 2 个候选。
- 中大型项目必须 3 个候选。
- 若只给 1 个候选，必须说明为什么其他候选明显不成立，并等待用户确认。

每个候选必须包含:

- 架构思路。
- 成立前提。
- 模块边界。
- source of truth。
- degraded / 回退行为。
- 测试策略。
- 扩展点。
- 主要代价。
- 不适合场景。

比较要求:

- 不只比较技术栈，要比较长期维护成本。
- 不只比较“能不能做”，要比较“以后怎么变”。
- 至少有一个候选是最小可交付或保守方案，用来对照 AI 推荐方案。
- 每个候选都必须说明会牺牲什么: 速度、灵活性、可维护性、可观测性、扩展空间、学习成本、交付确定性或用户体验。
- 牺牲是否值得必须落到验收目标和失败代价，不能只说“更规范”。
- AI 可以推荐，但必须同时说明推荐方案的反例。
- 最终推荐必须正反论证: 为什么选它，以及为什么不选更大一档 / 更小一档。
- 反向论证不能只写“流程冗杂”“项目结构太大”“过度设计”；必须指出当前项目哪个验收目标、数据流、状态流或失败模式不需要那部分复杂度。

阻断:

- 候选只是同一方案的小变体，退回重选。
- 只讲优点不讲代价，退回补齐。
- 只讲收益不讲牺牲项，退回补齐。
- 反向论证只停留在“过程冗杂 / 项目结构大 / 太复杂”，退回重做；这通常说明 AI 在套模板。
- 没有 source of truth 或 degraded 行为，退回补齐。

## 8. 拍板前骨架

用户选方向后，AI 先输出骨架，不直接写代码。

骨架必须包含:

- 目录结构。
- 核心模块职责。
- 对外接口。
- 数据流 / 状态流。
- 关键依赖。
- 配置 / secrets 策略。
- 测试分层。
- 验证预算: 哪些路径必须自动化验证，哪些只做手动/脚本验收，哪些暂不验证但要记录风险。
- 后续最可能变化点。
- 暂不处理事项，避免新项目一开始膨胀。

小项目骨架边界:

- 只列文件 / 模块、数据流、验证方式和暂不处理事项。
- 不展开完整分层架构、完整接口清单、完整测试矩阵。
- 若需要展开，必须说明它解决了哪个高破坏等级风险。

反向审查:

- 哪个模块最可能变成复杂度中心。
- 哪个边界如果切错，后续最难改。
- 哪个依赖或数据源最可能造成项目被卡住。
- 当前骨架为赶进度牺牲了什么，后续什么时候必须补回来。

## 9. 落盘门禁

禁止自动写 docs。

只有用户明确确认写入后，才生成或修改:

- `docs/PROJECT_MAP.md`
- `docs/AI_HANDOFF.md`
- 其他项目记忆层文件

两份核心项目产物的职责:

- `PROJECT_MAP`: 稳定事实、项目地图、易懂架构图、架构边界、source of truth、degraded / 回退。
- `AI_HANDOFF`: 近期风险、未验证项、下次接手重点。

文档日期要求:

- 新建或实质维护项目记忆层、项目维护文档、接力文档时，必须在文档开头写 `最后修改日期: YYYY-MM-DD`。
- 每次事实、入口、架构边界、风险、验证状态或接手信息变化时，同步刷新日期。
- 仅格式、错别字、链接修正且不改变事实时，可以不刷新日期，但完成汇报需说明。

`PROJECT_MAP` 架构图要求:

- 新项目、新模块、架构方向拍板后，写入 `PROJECT_MAP` 时必须包含初版 AI 友好的 Mermaid 树状图。
- 默认用 Mermaid 树状图表达主模块、子模块、数据/索引、外部依赖、source of truth 和关键边界。Mermaid 对 AI 解析友好，也方便用户通过 Markdown 预览渲染。
- 如果 Mermaid 放在 memory / 项目记忆层 / 交接文档里，图上方必须备注：此图需要用支持 Mermaid 的 Markdown 预览打开，例如 GitHub、GitLab、VSCode Mermaid 插件或 Mermaid Live Editor。
- 树状图每层或主要分支应使用不同颜色区分；颜色必须克制、可读、服务扫描，不做装饰。
- 小项目可用压缩树状结构，但不能只写文字而没有结构关系；树状图不是文件树，必须体现模块职责和关键依赖；不要画过细调用链或难以理解的全量系统图。
- 如果用户只授权讨论、不授权落盘，不写文件，只在输出中给草案图或说明待落盘。

这些产物服务项目长期维护，不记录讨论流水账；新项目上线后继续沿用同一套产物进入老项目维护。

写入前必须说明:

- 准备写哪些文件。
- 每个文件写什么。
- 是否覆盖旧内容。
- 哪些假设仍未确认。

## 10. 退出条件

用户拍板架构方向并进入实现后，本流程结束。

后续默认切换为:

- 既有项目改动、bug 修复、小功能、局部重构: 走老项目流程或普通 workflow。
- 架构方向重新打开、核心验收改变、source of truth 改变、关键外部依赖改变: 重新进入本流程对应阶段。
- 只是补文档、补测试、修局部实现: 不重开新项目地基流程。

边界:

- 不得因为本流程讨论过很多风险，就在后续每次改动时全部重放。
- 已拍板内容除非出现新证据，不反复争辩。

## 11. 紧急通道

用户明确说急时，可以压缩表达，但不能跳过最低地基。

仍必须保留:

- 验收标准。
- 关键假设。
- 架构边界。
- source of truth。
- degraded / 回退。
- 用户拍板。

降级输出必须说明:

- 哪些风险未展开。
- 哪些方案未比较。
- 哪些假设未验证。
- 这会带来什么返工风险。
- 这次为了速度牺牲了什么，以及牺牲是否可接受。

## 12. 本流程反模式

- 小项目套大架构。
- 小项目没有走轻流程，仍输出完整大项目流程。
- 小项目骨架展开完整分层架构、完整接口清单或完整测试矩阵，但没有对应高破坏等级风险。
- 中大型项目用小脚本心态开工。
- 没验收标准就谈技术栈。
- 当前阶段没完成就展开后续阶段细节。
- 没 source of truth 就设计数据流。
- 没 degraded / 回退就依赖外部系统。
- 候选方案只是同一思路换名字。
- AI 只推荐，不给反例。
- AI 只给扩展型方案，不给最小可交付或保守方案对照。
- 新规则、新架构或新抽象不说明牺牲项。
- 成熟架构参照只找大项目模板，不找小一档对照。
- 把类比参照包装成真实成熟案例。
- 反向论证只说“流程冗杂 / 项目结构大 / 太复杂”，没有落到当前项目的验收、数据流、状态流或失败模式。
- 风险只列概率，不说明对最终产物的破坏等级。
- 把用户偏好、业务事实或验收路径当成 AI 已知事实。
- 进入实现后仍反复重开新项目地基流程。
- 用户未拍板就落盘或写代码。
