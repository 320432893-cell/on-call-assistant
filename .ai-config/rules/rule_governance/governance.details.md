# 规则治理

## 1. 文件定位

触发:

- 新增、修改、删除、压缩、迁移规则文件。
- 修改 hook、lint、CI、settings、memory、规则索引。
- 用户要求判断某条规则该放哪里、该不该写。

动作:

- 本文件只管“规则怎么写、怎么分层、怎么下放到工具、怎么向用户反馈”。
- 不承载业务流程、代码规范细节、项目架构策略；这些放到对应 workflow / flow / code / 项目局部规则。
- 历史规则只作为来源读取；未获明确授权时只改仓库主规则或用户指定副本。

边界:

- 只读审查规则不触发写入要求。
- 用户还在讨论、未明确拍板时，不改任何规则文件。

规则状态:

- 讨论态: 用户在讨论规则方向、优缺点、执行压力、算力分配时，只分析，不写入。
- 草案态: 用户要求“草案”或“先讨论”，可以给拟写内容，但不落盘。
- 写入态: 用户明确说“改 / 写入 / 可以补充 / 按这个改”后，才修改规则文件。
- AI 从讨论中归纳出的偏好，未获用户确认前不能写成强规则。

## 2. 最高原则：规则给 AI 执行

规则必须体现用户意志，但表达形式必须转换成 AI 可执行结构。

新增独立强规则优先包含:

- 触发: 什么场景命中。
- 动作: AI 具体做什么。
- 边界: 什么情况下不适用。
- 反向审查: 这条规则可能带来什么副作用。
- 验证: 用户如何发现 AI 是否执行。

短规则、索引规则或同一章节内的规则，可共享章节级触发、边界和验证，不要求每条都机械重复字段。

禁止:

- 只写价值观，不写触发和动作。
- 把多个主题混成一条规则。
- 为了人读着完整，堆长背景解释。
- 把工具能稳定检查的事项写成 Markdown 自觉要求。
- 因为用户提出就直接写入；必须先给出风险、成本、替代方案或反例。

## 3. 规则层级与去重

层级:

- 全局层: 跨项目协作原则、用户偏好、AI 行为边界。
- 工作流层: 任务执行门禁、验证、汇报、上下文管理。
- 流程层: 新项目、遗留项目、救火、调研等场景流程。
- 专题层: 代码、GUI、测试、信息整理等单领域规则。
- 项目局部层: 当前项目业务、架构、运行、部署规则。
- 机械层: ruff、basedpyright、import-linter、pre-commit、CI、hook。

动作:

- 同一思想只在最高合适层主定义一次。
- 下层只保留“本场景补充”或单向引用，不复制完整清单。
- 发现重复时，优先合并、上提或改成引用。
- 跨文件引用用标题，不用行号。

冲突优先级:

`救火红线` > `全局协作原则` > `workflow` > `governance` > `流程层` > `专题层` > `项目局部偏好`

仍冲突时，停止写入并问用户。

## 3.1 读取路径与阶段解耦

新增或扩展规则文件时，必须判断是否需要读取路径和阶段解耦。

触发:

- 单个规则文件超过约 200 行。
- 文件同时包含默认流程、按需流程、例外流程、紧急流程或多个阶段。
- 小任务只需要文件中的一小部分规则。
- 用户或 AI 已经出现“读了太多规则、上下文不干净、注意力被拉散”的问题。

动作:

- 优先在文件顶部增加 `## 0. 读取路径`，区分默认只读主路径和按需读取段落。
- 多阶段流程必须说明每阶段只处理什么、不提前展开什么。
- 按需段落必须有触发条件；不能为了完整性默认读取。
- 如果某段只服务少数场景，优先降为按需读取，而不是放进主路径。

边界:

- 读取路径只控制注意力，不降低上层门禁、验证或安全边界。
- 短文件、单职责文件、机械配置说明不强制加读取路径。
- 不得为了“解耦”拆出大量小文件，导致索引和跳转成本更高；先在同一文件内做读取路径。

反向审查:

- 解耦会增加一点规则维护成本，但能避免 AI 默认加载长文件导致上下文污染。
- 如果读取路径本身比规则更复杂，说明该文件应继续压缩或拆分，而不是继续加路由。

维护原则:

- 规则文件优先维持单文件 + 强读取路径。
- 新增规则时，优先通过默认路径、按需触发、阶段边界、输出上限完成逻辑解耦。
- 不在每个规则文件重复声明“单文件 + 强读取路径”；本原则只在治理层主定义。
- 只有当单个主题膨胀为独立流程、读取路径过复杂、或单文件导致稳定漏读时，才考虑物理解耦。

## 3.2 索引与 details 解耦

索引不是目录清单，而是规则路由器。新增或调整索引时，必须让 AI 能在少量文字内判断“读哪个入口、何时停止、何时升级到 details”。

触发:

- 专题下存在多个规则文件。
- 单个主题文件超过约 200 行，且小任务只需要其中一部分。
- 用户明确要求降低上下文污染、减少 AI 误读或多轮后重新路由。
- 文件已经拆成 `*.index.md` / `*.details.md`，或准备这样拆。

动作:

- 总索引只做专题分流，不复制细节规则。
- 专题索引必须写清触发入口、停止条件、升级条件和文件分工。
- `*.index.md` 只做轻量判断和升级路由；`*.details.md` 才放完整规则。
- 跨规则引用默认指向 index，不直接指向 details。
- details 只能由对应 index 的复杂、高风险、正式交付或副作用条件触发。
- 阶段闭包里的 `RULE_ROUTE` 只允许指向总索引或专题 index，不指向 details。

边界:

- 不为短文件、单职责文件或每次命中都必须完整读取的文件拆 index/details。
- 不把索引写成第二份规则正文；索引越长，越应回头压缩触发条件。
- 不因为一处规则提到另一个专题，就自动串联读取；只在当前任务真实命中时读取。
- hook 只可提醒回到索引或检查 `RULE_ROUTE` 字段，不负责业务语义分流。`rule_activator.sh` 是例外：它只能根据用户 prompt 输出索引激活提示，不得替代 index/details 的最终读取判断。

反向审查:

- index/details 会增加文件数量和维护成本；只有它能明显降低默认读取负担或稳定防漏读时才值得。
- 过度细拆会让 AI 花更多注意力判断读哪个小文件，反而污染上下文。
- 如果 details 被其他文件频繁直接引用，说明路由设计失效，应改引用或合并规则。

验证:

- 修改后检查是否还有旧文件路径或绕过 index 的 details 引用。
- 检查总索引、专题索引和 AGENTS 规则表是否指向同一入口。
- 检查阶段闭包规则是否能给 hook 提供稳定的 `RULE_ROUTE`。

## 4. 机械层 vs 语义层

新增约束前先判定轨道。走错轨比少写一条规则更坏，因为会增加维护成本并分散 AI 注意力。

### 4.1 成熟工具优先

优先级:

1. 成熟工具配置。
2. 项目已有工具配置。
3. pre-commit / CI 编排。
4. 自定义 hook。
5. Markdown 规则。

动作:

- 能用 ruff、basedpyright、import-linter、pytest、coverage、detect-secrets、pip-audit、pre-commit 标准 hook 解决的，不写 bash 正则 hook。
- 能放进工具配置的，不写 AI 自觉规则。
- 能用项目已有工具表达的，不新增第二套机制。
- 自定义 hook 只处理成熟工具管不到的高风险、项目特异、流程性约束。
- 偏好 `ruff` 这类快速、成熟、能合并多套旧工具的实现；但速度差异若在当前项目规模下不可感知，不作为单独替换理由。
- 新静态工具必须说明维护性收益: 是否减少配置、减少误报、改善兼容性、统一本地/CI 行为，或覆盖现有工具表达不了的问题。
- 新增、删除或调整工具、semgrep ruleset、自定义 hook、pre-commit 或 CI 检查时，必须同步更新 `.ai-config/tooling.registry.toml`，并运行 `.ai-config/check_rule_tool_contracts.py` 验证。
- 本地 pre-commit 优先保留快且局部的检查；慢、全量、专项扫描优先放 CI 或手动审计。

禁止:

- 用 bash 正则重写 ruff / basedpyright / import-linter / pytest / pre-commit 已覆盖能力。
- 在 Markdown 里复述工具的完整检查清单。
- 为了“看起来更严格”增加多套重复检查。
- 把业务语义判断强塞进低质量正则，导致高误报。
- 为了“更新/更快”替换稳定工具，却增加配置、锁文件、CI、规则文档和团队心智成本。

### 4.2 责任映射

默认下放:

- 格式、lint、import 排序、常见 bug、复杂度: `ruff`
- 类型、签名、可空性: `basedpyright`
- 分层 import 边界: `import-linter`
- 单元测试、集成测试、覆盖率: `pytest` / `pytest-cov`
- JSON / YAML / TOML 语法和基础文件卫生: pre-commit 标准 hook
- 密钥泄漏: `detect-secrets`
- 依赖漏洞: `pip-audit`

工具契约:

- `.ai-config/tooling.registry.toml` 是规则、工具、hook、semgrep、pre-commit 和 CI 对应关系的机器可读登记表。
- `.ai-config/check_rule_tool_contracts.py` 与 registry 放在同一目录，负责验证 dev 依赖、pre-commit hook、CI 命令、semgrep ruleset、hook manifest 和 `rule_route` 是否一致。
- `docs/TOOLING_CONTRACTS.md` 给人看总览，不作为机器检查源。
- 规则文档只说明“应由谁负责”和边界；是否已接入工具链以 registry 和检查脚本为准。
- 修改工具契约相关文件后，必须运行 `python3 .ai-config/check_rule_tool_contracts.py` 或等价 CI 步骤。

保留给 AI 语义规则:

- 架构边界、职责归属、状态流、数据流。
- 失败模式、幂等、降级、可观测性。
- 用户意志、讨论门禁、反向审查、风险解释。
- 工具无法可靠判断的业务语义。

自定义 hook 仅适合:

- 危险命令或不可逆动作拦截。
- 项目特异且可稳定检测的反模式。
- AI 执行流程门禁，例如未确认前禁止写入。

### 4.3 新 hook 准入

写新 hook 前必须回答:

- 为什么成熟工具不能解决？
- 为什么不能只改现有工具配置？
- 为什么不能拆到 pre-commit / CI / 共享脚本后只让 hook 做适配层？
- hook 是否只有一个职责？如果包含多条规则，每条为什么必须同生同死？
- 误报率是否可接受？
- 失败提示是否能让用户直接知道怎么处理？
- 长期维护成本是否值得？
- 是否有正反样本测试？

规则:

- hook 默认必须单职责: 一个触发来源、一个判断目标、一个处置建议。
- 禁止把项目体检、静态代码规则、流程门禁、业务语义提醒塞进同一个 hook。
- hook 只应保留即时上下文能力: 当前工具调用、old/new edit 内容、即将执行的命令、用户确认状态、git diff 语义漂移。
- 可复用逻辑必须抽到共享脚本；hook 只做输入适配和即时提示，CI/pre-commit/manual 能复用同一份逻辑。
- 新 bash hook 必须配测试样本，至少覆盖正例、反例、边界例。
- 修改旧 hook 时，若触及匹配逻辑，必须补对应测试。
- 修改旧 hook 时，必须先检查是否已经变成“一坨”: 若同时承担多类检查，先拆职责，再谈新增能力。
- 新增 hook 注册前，必须列出“可下放部分”和“不下放原因”；没有不可替代的即时上下文，不注册 hook。
- 写不出准入理由时，不写 hook，改用工具配置或 AI 语义规则。

## 5. 新增规则过滤

强规则写入前必须通过四维过滤:

- 影响: 违反后是否影响架构、交付、数据、生产或跨模块行为。
- 易违反度: AI 是否容易在正常编码中忽略。
- 代价: 违反后是否难回滚、难发现、会污染长期设计。
- 可验证: 用户或工具是否能看出 AI 有没有执行。

强规则写入前还必须说明牺牲项:

- 这条规则会牺牲什么: 速度、注意力、上下文预算、用户阅读成本、执行灵活性、工具链简洁性或未来维护空间。
- 牺牲是否值得: 必须落到它避免了什么更高代价的问题，不能只说“更规范”。
- 治理层新增强规则时，必须额外判断是否会拖慢以后每次规则维护；如果只是让流程更完整但不能降低真实误用风险，不写。

强规则写入前还必须检查解耦影响:

- 它应该进入默认主路径，还是按需段落。
- 是否会让小任务默认背上大任务规则。
- 是否需要新增或更新 `## 0. 读取路径`。
- 是否能通过阶段解耦、输出上限或触发条件降低注意力消耗。
- 若默认主路径超过约 10 个必须项，应检查是否能压缩或改为按需读取；这只是维护性软指标，不作为机械阻断条件。

处理:

- 四项都通过，才允许写强规则。
- 有一项不通过，降级为推荐、项目备注、工具配置，或不写。
- 涉及数据损坏、生产事故、不可逆操作时，可高优先级保留，但必须写清触发和阻断方式。
- 说不清牺牲项或牺牲不值得时，不写强规则；改为推荐、工具配置、项目备注或只在本次任务口头提醒。
- 说不清默认读取还是按需读取时，先不写进主路径；改为按需段落或继续讨论。

容量:

- 单个规则文件强规则原则上不超过 10 条。
- 超过时必须合并、拆分、下放工具或降级推荐。
- 规则越多，AI 越容易走形式；治理目标是减少噪音，把算力留给核心判断。

## 6. 规则写入格式

推荐模板:

```md
## 规则名

触发:
- ...

动作:
- ...

边界:
- ...

反向审查:
- ...

验证:
- ...
```

写法要求:

- 用“必须 / 禁止 / 默认 / 优先 / 可”区分强度。
- 避免“建议 / 尽量 / 注意 / 最好”这类无法执行的强规则表述。
- 一个规则只管一个判断点。
- 规则文字短于解释文字；解释只在能降低误用时保留。

## 7. 修改后反馈

触发:

- 新增、修改、删除规则文件。
- 修改 hook、lint、CI、settings、memory。
- 修改规则索引或规则副本。

动作:

- 每次规则改动后，必须向用户反馈。
- 小改动一句话说明: 改了哪个文件、影响什么 AI 行为。
- 中大改动列清单说明:
  - 改了哪个文件。
  - 为什么改。
  - 引用了用户哪句原话或哪项拍板。
  - 改动影响哪些后续 AI 行为。
  - 原始规则文件是否保持未改。
  - 是否还有未处理的规则冲突或待讨论点。

边界:

- 只读检查规则文件不触发。
- 用户明确要求“只改不用解释”时，仍至少反馈改动文件和影响。

反向审查:

- 反馈本身会制造噪音，所以按影响分级；高风险和全局规则必须完整反馈，低风险小改保持短。

## 8. 复查清单

规则改完后必须检查:

- 是否改的是用户指定的规则主版本，而不是误改运行时副本。
- 是否与上层规则冲突。
- 是否重复定义同一阻断点。
- 是否把机械检查错写进 Markdown。
- 是否把语义判断错塞进 hook。
- 是否超过单文件强规则容量。
- 是否保留了用户最终选择权。
- 是否向用户说明改动和影响。

反模式:

- 同一规则在多个文件主定义。
- 用“建议/尽量”写强规则。
- 不讨论就写入用户尚未拍板的偏好。
- 能 ruff 解决却写 bash 正则。
- hook 没有准入理由和测试。
- 改规则不汇报。
