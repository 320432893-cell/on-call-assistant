# 规则维护流程

## 0. 读取路径

默认只读主路径，避免规则维护把后续业务任务拖进长讨论:

- `1. 文件定位`
- `2. 默认状态：讨论态`
- `3. 阶段化维护`
- `6. 写入前确认`
- `7. 执行后反馈`
- `8. 退出条件`
- `9. 本流程的反模式`

按需读取:

- 讨论规则设计、规则位置、规则副作用 -> `4. 讨论重点`
- 需要发散规则形态、下放工具、解耦或拒绝写入 -> `5. 发散方式`
- 涉及 hook / settings / memory / 规则索引 / 规则副本 -> 读取本文件相关门禁，并按目标文件规则单独确认。

边界:

- 读取路径只控制注意力，不降低规则维护的写入授权门槛。
- 用户只是问规则内容时，不进入写入流程。
- 如果不确定是否需要读取某段，按全局“阶段切换与规则读取”机制问用户一句。

## 1. 文件定位

触发:

- 修改、新增、删除、压缩、迁移规则文件。
- 修改 hook、settings、memory、规则索引、规则副本。
- 讨论规则应该保留、删除、下放工具、改写成什么形态。

动作:

- 本文件只管“规则维护时怎么讨论、怎么确认、怎么写入”。
- 本文件不向上引用其他规则，避免读取链路膨胀。
- 默认只改仓库规则主版本；运行时副本、历史副本或全局配置未获明确授权不得改。

边界:

- 用户只是问规则内容时，只读解释，不进入写入流程。
- 业务代码任务不加载本文件，除非任务本身是在改规则或 hook。

## 2. 默认状态：讨论态

规则维护默认处于讨论态。

讨论态允许:

- 读取目标文件。
- 分析现有规则。
- 发散规则设计。
- 提出保留、删除、压缩、下放工具、改写方案。
- 说明新增或保留规则会牺牲什么，以及可能糊弄点。

讨论态禁止:

- 写入规则文件。
- 修改 hook / settings / memory / 索引。
- 删除或覆盖旧规则。
- 把“可以、继续、ok、先这样、看看”当成写入授权。

只有用户明确说以下含义，才进入执行态:

- “确认写入”
- “按这个版本改”
- “执行落盘”
- “可以改这个文件”
- “确认可以修改”

反向审查:

- 授权词收窄会让协作变慢，但规则维护误写的代价更高，所以这里优先保护用户决策权。

## 3. 阶段化维护

规则维护必须按 taskwork 单步推进，一个阶段只处理一个重心。

阶段重心示例:

- 最高目标和协作原则。
- workflow 执行流程。
- 规则维护流程。
- hook / settings 注册。
- ruff / basedpyright / pre-commit / import-linter / semgrep / pip-audit / hook / CI 工具契约。
- `.ai-config/tooling.registry.toml` 与 `.ai-config/check_rule_tool_contracts.py` 工具契约。
- 旧规则压缩或废弃。
- 展示材料和运行时规则主源分离。

每个阶段开始前必须说明:

- 本阶段目标。
- 本阶段不做什么。
- 当前拟处理文件。
- 当前想法。
- 反对意见和可能误伤。
- 是否需要用户拍板。

每个阶段完成后必须形成阶段闭包:

- 已拍板。
- 已执行。
- 推断。
- 未验证。
- 暂不处理。
- 下一重心。

用户可见程度:

- 连续推进且无新拍板需求: 可用短闭包，说明本阶段完成什么、未验证什么、下一重心是什么。
- 涉及规则主版本、hook、settings、lint/CI、memory、旧规则废弃、用户纠偏或下一阶段需要重新拍板: 展示完整闭包。
- 短闭包只降低用户阅读压力，不降低 AI 内部闭包要求。

规则:

- 下一阶段默认只继承阶段闭包，不继承前面所有展开讨论。
- 已闭包内容除非用户重新打开、证据反转或目标冲突，不反复争论。
- 如果阶段闭包摘要不足，先说明缺口，再回溯目标文件或用户原话取证。
- 不得在一个阶段里同时改最高规则、工具配置、hook 和旧规则清理。

反向审查:

- 阶段化会降低速度，但规则维护的长期副作用高于普通代码改动；这里优先保证上下文干净和用户拍板边界。

## 4. 讨论重点

AI 不只整理用户意见，必须主动暴露自己的执行边界。

讨论时必须覆盖:

- 新增或保留规则会牺牲什么: 速度、注意力、上下文预算、用户阅读成本、执行灵活性、工具链简洁性或未来维护空间。
- 这些牺牲是否值得，理由是什么。
- 新增或保留规则应进入默认主路径还是按需读取段落。
- 是否需要新增或更新 `## 0. 读取路径`、阶段解耦、输出上限或触发条件。
- 哪部分容易被 AI 糊弄成打勾。
- 哪部分容易误伤正常开发。
- 哪部分更适合下放给成熟工具。
- 哪部分会增加上下文读取负担。
- 哪部分可能改变用户原本想法。
- 哪部分不该写入规则。
- 本阶段结束后哪些展开讨论应被压缩进闭包摘要，哪些不再带入下一阶段。

禁止:

- 纯迎合用户，把所有偏好都写成强规则。
- 只从代码质量看规则，不讨论架构、设计哲学、协作成本、长期维护。
- 把规则维护做成机械清单填空。
- 一次性横跨多个阶段，导致用户无法逐项拍板。

## 5. 发散方式

规则维护阶段应尽量发散，但发散必须服务于落地。

发散强度:

- 小规则修改只覆盖牺牲项、默认 / 按需位置、是否下放工具、是否需要用户拍板。
- 中大规则改动、全局规则、hook / settings / memory / lint / CI 变更，才展开完整发散角度。
- 不要求每次全量跑完所有角度；只展开能改变当前判断的角度。

AI 至少从以下角度审查:

- 保留: 这条规则解决什么高代价问题。
- 删除: 这条规则是否只是噪音或重复。
- 压缩: 是否能改成更短的触发/动作/边界。
- 解耦: 是否应拆成默认主路径和按需段落，是否需要阶段切换边界。
- 下放: 是否应交给 ruff、basedpyright、import-linter、pytest、pre-commit、CI 或 hook。
- hook 拆分: 是否把多类检查塞进一个 hook；能拆到工具、CI 或共享脚本的必须先拆。
- 拒绝: 是否不该写入，因为不可执行、误伤大、读取负担高。
- 长期副作用: 半年后是否会让 AI 或用户更难维护。
- 上下文副作用: 是否会增加后续 AI 的读取负担、迁就倾向或虚假确定性。

边界:

- 不要求引用用户原话做账本。
- 必要时可以复述用户意图，但重点是暴露理解偏差、规则牺牲项和设计取舍。

## 6. 写入前确认

进入执行态前，AI 必须先给拟改摘要。

拟改摘要必须包含:

- 目标文件。
- 准备保留什么。
- 准备删除或压缩什么。
- 准备新增什么。
- 准备放入默认主路径还是按需段落。
- 是否新增或更新 `## 0. 读取路径`、阶段解耦或输出上限。
- 是否只改副本。
- 是否涉及 hook / 工具链下放。
- 是否涉及工具契约 registry / contract checker / 人读总览文档。
- 若规则下放给工具，是否会新增或修改 pyproject、pre-commit、CI、semgrep、hook manifest。
- 是否仍有未决问题。
- 本阶段完成后的闭包展示粒度。

规则:

- 用户确认拟改摘要后再写。
- 若用户直接给出明确写入授权，可跳过长方案，但仍要在写入前用一句话说明目标文件和写入范围。
- 涉及删除原始规则、改历史副本、改全局配置、改 hook 阻断逻辑时，必须单独确认。

## 7. 执行后反馈

每次写入后必须反馈:

- 改了哪个文件。
- 改动影响什么 AI 行为。
- 工具契约相关改动必须说明 contract checker 是否已运行、是否通过。
- 是否触及原始文件。
- 是否还有未处理冲突或待讨论点。
- 阶段闭包展示粒度和下一重心。

反馈控制:

- 小改动一句话即可。
- 中大改动列清单。
- 高风险改动必须说明原因、影响和后续风险。

## 8. 退出条件

规则维护阶段结束条件:

- 用户确认写入且 AI 已完成执行后反馈。
- 用户只讨论不写入，AI 明确标注“未落盘”。
- 用户暂停或切回业务任务，AI 用短闭包说明已拍板、未拍板、未写入内容。

后续默认:

- 已落盘规则作为新边界进入后续任务。
- 未落盘讨论不作为规则约束，只作为背景保留。
- 后续业务任务不继续携带规则维护展开讨论，除非用户重新打开。

## 9. 本流程的反模式

- 还在讨论就写入。
- 把“可以”“继续”误判成授权。
- 不说新增或保留规则会牺牲什么，只把规则整理得好看。
- 不反对用户明显高成本或低收益的规则。
- 能交给成熟工具却写进 Markdown。
- 规则写完不反馈影响。
- 为了完整性增加大量跨文件引用。
- 完成一个阶段后不闭包，继续带着展开讨论滚到下一阶段。
- 把推断、未验证内容写成已拍板事实。
- 规则讨论未落盘，却在后续任务里当成已生效规则使用。
