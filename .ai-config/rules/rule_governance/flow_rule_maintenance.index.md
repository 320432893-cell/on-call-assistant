# 规则维护流程

本文件管规则新增、修改、删除、压缩、迁移时怎么讨论、怎么取舍、怎么落盘。目标是保持上下文纯净: 有用规则留下，重复、空泛、过度路由和不可执行内容删除。

命中规则文件、hook、settings、memory、规则索引、规则副本、工具契约讨论或修改时读取本文件。

## 1. 默认协作方式

- 规则维护默认先讨论，不因读取本文件自动写入。
- 用户明确要求修改、合并、删除、落盘时，可以进入写入；涉及高风险位置时单独确认。
- 一个阶段只处理一个规则重心，不同时横跨多个专题、hook、settings 和旧规则清理。
- 用户只问规则内容时，只解释，不进入写入流程。

## 2. 讨论先发散再收敛

发散是为了暴露选择，不是为了把所有想法写进规则。讨论时先覆盖:

- 当前规则想解决什么高代价问题。
- 用户真实偏好是什么，哪些是强偏好，哪些只是讨论过程中的临时想法。
- 同类任务经常出的问题，是否能补足用户未提到的知识盲区。
- 新增或保留会牺牲什么: 上下文预算、执行速度、用户阅读成本、灵活性、维护成本、误触发风险。
- 是否已有规则覆盖；已有规则覆盖时，优先引用或微调原规则，不重复新写。
- 哪些内容更适合变成交互提醒、提问、确认项，而不是长期规则。

收敛时按 ROI 排序:

1. 保留能防高代价事故的规则: 数据破坏、生产风险、不可逆副作用、权限密钥、用户误操作、长期上下文污染。
2. 保留能稳定改变 AI 行为的规则: 明确触发、明确动作、明确边界、能在执行中被观察。
3. 压缩经验性但有用的规则: 留判断句和执行证据，删长解释、示例堆叠和重复表述。
4. 合并同主题重复规则: index 承担默认路径，details 只在确实需要复杂展开时存在。
5. 删除低 ROI 内容: 自称可靠、自我打分、低价值元清单、口号、泛泛风险、重复路由、空泛退出条件、不可执行的读取说明、无法验证的要求。
6. 下放机械检查: 格式、lint、类型、import、secret、依赖漏洞、固定 sleep 等能由成熟工具稳定检查的内容，不写成 AI 自觉规则。

## 3. 什么时候补人机交互，而不是写规则

以下内容优先设计成 AI 对用户的短问题、确认或阶段总结，不写成长期规则:

- 需要用户业务判断才能决定的内容: 需求取舍、风险接受、验收口径、是否覆盖、是否删除。
- 低频但高差异的场景: 特定客户、特定系统、一次性数据口径、临时交付约束。
- 信息不在代码或规则里的内容: 历史原因、账号权限、线上真实数据形态、业务例外。
- 写成规则会让所有任务变重，但只在少数任务有价值的内容。
- 用户偏好尚未稳定，只是在当前讨论中探索的内容。

适合写入规则的内容:

- 多次出现且代价高。
- 可以用触发、动作、边界表达。
- 不依赖用户每次重新解释。
- 能减少未来上下文，而不是增加默认读取负担。

## 4. 写入边界

写入前先用短摘要说明:

- 目标文件。
- 保留什么。
- 删除或压缩什么。
- 新增什么。
- 是否已有规则覆盖。
- 是否涉及高风险位置。

用户已经明确要求“可以改、合并、删除、写入、执行”时，不需要长方案，但仍要在写入前说明目标文件和写入范围。

高风险位置必须单独确认:

- hook 阻断逻辑。
- settings、memory、全局配置。
- 规则主索引和跨专题路由。
- 规则副本、历史副本、运行时副本。
- 会改变工具链行为的 registry、contract checker、pre-commit、CI、semgrep。

## 5. 阶段总结

每阶段完成后只保留能服务下一阶段的上下文:

- 已改哪些文件。
- 影响什么规则读取或 AI 行为。
- 哪些讨论已收敛，哪些未拍板。
- 哪些未验证或仍有风险。
- 下一阶段处理什么。

已收敛内容不反复带入后续讨论；未落盘讨论不当作已生效规则。
