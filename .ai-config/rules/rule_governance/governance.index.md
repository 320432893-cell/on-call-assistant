# 规则治理原则

本文件管规则体系怎么设计: 规则放哪、该不该写、是否已有覆盖、是否下放工具、hook 是否值得加。具体维护流程读取 `flow_rule_maintenance.index.md`。

命中规则层级、去重、index/details 分工、hook / lint / CI 分工、工具契约 registry、hook manifest、semgrep、pre-commit、CI 对应关系时读取本文件。

## 1. 分层和去重

同一思想只在最高合适层主定义一次，下层只保留本场景补充或单向引用。

常见层级:

- 全局层: 跨项目协作原则、稳定用户偏好、AI 行为边界。
- workflow 层: 任务推进、阶段总结、上下文管理。
- process 层: 新项目、老项目、小改、重构、救急等流程。
- engineering 层: 架构、代码、前端、GUI、后端等工程判断。
- delivery 层: 交互、数据、打包交付、浏览器自动化。
- project 层: 当前项目业务、架构、运行、部署规则。
- mechanical 层: ruff、basedpyright、import-linter、pytest、pre-commit、CI、hook。

去重顺序:

1. 已有规则覆盖: 优先引用或微调原规则。
2. 同主题重复: 合并到最高合适层。
3. 下层只是场景补充: 保留差异，不复制完整清单。
4. 跨文件引用默认指向 index 或单一规则文件，不直接指向 details。

## 2. 新规则准入

新强规则写入前按 ROI 判断:

- 影响: 违反后是否影响架构、交付、数据、生产、权限、用户误操作或跨模块行为。
- 易违反度: AI 是否容易在正常任务里忽略。
- 代价: 违反后是否难发现、难回滚、会污染长期设计或上下文。
- 可执行: 是否能写成明确触发、动作、边界和应用证据。
- 已有覆盖: 是否已有规则、工具、项目约定覆盖。
- 牺牲项: 是否增加上下文预算、执行速度、用户阅读成本、灵活性或维护成本。

保留:

- 高代价、高频、可执行、已有规则未覆盖的内容。
- 能稳定改变 AI 行为，并能在执行中观察到证据的内容。

删除或不写:

- 自称可靠、自我打分、口号、泛泛原则、重复路由、无法验证要求。
- 只让规则看起来完整，但不能降低真实误用风险的内容。
- 会让小任务默认背上大任务规则的内容。

## 3. index 和 details 分工

- 能合并成单文件就合并，避免索引链路膨胀。
- index 承担默认可执行路径，不只是目录清单。
- details 只在复杂、中高风险、正式交付、长流程确实需要展开时保留。
- 总索引只做专题分流，不复制细节规则。
- 专题 index 写清触发入口和默认动作；不要把正文拆空后逼迫继续读 details。
- 如果 details 被频繁直接引用，优先合并或调整 index，而不是继续加路由。

## 4. 工具优先

新增约束前先判断能否下放工具。优先级:

1. 成熟工具配置。
2. 项目已有工具配置。
3. pre-commit / CI 编排。
4. 自定义 hook。
5. Markdown 规则。

默认下放:

- 格式、lint、import 排序、常见 bug、复杂度: `ruff`
- 类型、签名、可空性: `basedpyright`
- 分层 import 边界: `import-linter`
- 单元测试、集成测试、覆盖率: `pytest` / `pytest-cov`
- JSON / YAML / TOML 语法和基础文件卫生: pre-commit 标准 hook
- 密钥泄漏: `detect-secrets`
- 依赖漏洞: `pip-audit`

保留给 Markdown 语义规则:

- 架构边界、职责归属、状态流、数据流。
- 失败模式、重复执行安全、降级、可观测性。
- 用户意志、讨论门禁、风险解释。
- 工具无法可靠判断的业务语义。

## 5. hook 准入

自定义 hook 只适合成熟工具管不到、需要即时上下文、误报可控的高风险约束。

写新 hook 前必须能说明:

- 为什么成熟工具不能解决。
- 为什么不能只改现有工具配置。
- 为什么不能放到 pre-commit / CI / 共享脚本。
- hook 是否只有一个职责。
- 失败提示是否能让用户知道怎么处理。
- 是否有正例、反例、边界例测试。

hook 只保留即时上下文能力: 当前工具调用、old/new edit 内容、即将执行的命令、用户确认状态、git diff 语义漂移。

不能把项目体检、静态代码规则、流程门禁、业务语义提醒塞进同一个 hook。

## 6. 工具契约

`.ai-config/tooling.registry.toml` 是规则、工具、hook、semgrep、pre-commit 和 CI 对应关系的机器可读登记表。

修改以下内容时，同步检查工具契约:

- registry。
- `.ai-config/check_rule_tool_contracts.py`。
- `.ai-hooks/manifest.json`。
- pre-commit。
- CI。
- semgrep ruleset。
- 新增或删除工具依赖。

新项目、新模块或新代码目录产生可运行代码时，必须判断是否已映射到质量工具；至少覆盖语法编译、格式 / lint、相关测试、语义扫描、密钥检查，类型检查、import 边界、数据校验、浏览器验证按项目适用性补充。

若现有 registry、pre-commit、CI 或 `tools/check.py` 未覆盖新目录，必须先报告缺口和临时定向验证结果；实际修改工具链覆盖范围仍需用户单独拍板并经过工具契约检查。

工具契约相关改动后，运行 `python3 .ai-config/check_rule_tool_contracts.py` 或等价 CI 步骤；跑不了时说明原因和剩余风险。

新增或替换静态工具时，不得只因为“更快/更新”就切换。只有满足以下至少一项才推进:

- 能合并多套旧工具，减少配置和心智负担。
- 能降低长期维护复杂度或提升跨项目兼容性。
- 能表达现有工具难以稳定覆盖的问题。
- 当前项目规模下速度差异已经可感知，或 CI/pre-commit 已成为明确瓶颈。

否则优先扩展现有工具配置，而不是新增工具链。

## 7. 写法

规则优先写成:

- 触发: 什么场景命中。
- 动作: 具体做什么。
- 边界: 什么情况下不适用。
- 证据: 用户如何看出规则被执行。

写法要求:

- 用“必须 / 禁止 / 默认 / 优先 / 可”区分强度。
- 一个规则只管一个判断点。
- 规则文字短于解释文字；解释只在能降低误用时保留。
- 不写自我证明、自我打分、低价值元清单、口号和泛泛背景。
