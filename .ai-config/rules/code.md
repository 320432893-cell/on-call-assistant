# 代码语义规则

## 1. 文件定位

触发:

- 写业务代码。
- 修改公共接口。
- 引入或调整工程范式。
- 处理异常、日志、配置、测试语义。

动作:

- 本文件只管 AI 语义判断和设计范式。
- 格式、命名机械规则、import 排序、类型注解存在性、print、root logger、常见异常反模式交给 Ruff / basedpyright / import-linter。
- 老项目风格一致性、接手、改动影响面走老项目流程。

边界:

- 不写自检框，不要求每次填表。
- 不用本文件替代工具配置。
- 不把固定目录模板当成所有项目强规则。

## 2. 工具下放

默认由工具负责:

- 格式、import、基础 lint、常见 bug: Ruff。
- 命名机械规则: Ruff `N`。
- print、logging 格式、异常反模式、安全问题: Ruff `T20` / `LOG` / `G` / `TRY` / `BLE` / `S`。
- 类型注解存在性和类型一致性: Ruff `ANN` + basedpyright。
- 分层 import 边界: import-linter。
- 测试风格基础规则: Ruff `PT` + pytest。

AI 仍需判断:

- 是否该引入抽象。
- 是否该保持老代码风格。
- 异常在哪一层捕获。
- 日志是否有业务上下文。
- 公共接口是否稳定。
- 测试是否覆盖真实风险。

## 3. 范式使用原则

范式不是为了显得专业，而是为了控制变化、隔离复杂度、降低长期维护成本。

使用范式前，AI 必须判断:

- 变化点是否真实存在。
- 当前复杂度是否已经超过直写代码。
- 范式是否降低耦合，而不是制造抽象债。
- 老项目是否已有相反风格。
- 用户目标是长期维护还是一次性交付。

默认:

- 小脚本、小改、一次性任务优先直写。
- 新项目地基期可以提前设计关键范式。
- 老项目优先融入现有范式，除非用户确认改造。
- 数据写入、状态生命周期、外部依赖、公共接口是最值得使用范式的地方。

反向审查:

- 过早抽象会让项目变难读。
- 不抽象会让变化点散落，后期改动成本爆炸。
- AI 不得为了套模式而套模式。

## 4. 语义命名

触发:

- 新增变量、函数、模块、类。
- 改名。

规则:

- 名字必须表达业务职责，不只表达实现方式。
- 布尔值用 `is_` / `has_` / `can_` / `should_` 表达判断语义。
- 集合名用复数或集合语义。
- 禁止拼音和无意义缩写。
- 模块名优先表达职责，不优先表达具体技术。

反向审查:

- 老项目已有命名体系很强时，先保持局部一致；统一改名必须作为明确重构范围。

## 5. 依赖倒置

触发:

- 高层模块依赖带 IO、数据库、HTTP、文件、外部 API 的具体实现。
- 需要 mock 测试。
- 同一能力可能有多个实现。

动作:

- 高层依赖 Protocol / ABC / 接口形态。
- 具体实现放在边界层或基础设施层。
- 只在复杂度真实存在时引入抽象。

边界:

- 一次性脚本、单调用点、无外部依赖的小函数，不强制抽象。

阻断:

- 上层直接绑定具体外部依赖，且影响测试或替换能力时，必须改为抽象或说明不改理由。

## 6. 状态机

触发:

- 对象或任务有生命周期。
- 出现多个布尔标志互相影响。
- 同一状态判断散落多处。

动作:

- 用显式状态枚举。
- 定义合法转移。
- 集中状态切换入口。

边界:

- 只有两个状态且无非法转移风险时，不强制状态机。
- 小项目不能为了显得专业硬套状态机。

阻断:

- 状态分散导致非法组合可能出现时，必须集中建模。

## 7. 注册表 / 策略

触发:

- 分支按 key 路由。
- `if/elif` 分支达到 3 个以上。
- 后续可能继续扩展分支。

动作:

- 优先使用注册表、策略映射、handler 表。
- 新增分支应尽量只改一处。

边界:

- 分支固定且业务上不会扩展，不强制注册表。
- 各分支差异过大，共享接口别扭时，不强制。

阻断:

- 可扩展分支继续散落在多处时，必须收敛或说明原因。

## 8. 异常分层

触发:

- 新增 try/except。
- 设计错误类型。
- 修改边界层、服务层、引擎层错误处理。

动作:

- 引擎层优先只 raise，不吞错。
- 服务层把底层错误转译为业务语义。
- 边界层兜底，转译为用户可见信息，不暴露敏感 traceback。
- `except Exception` 只能用于边界兜底、任务隔离、UI 顶层保护等明确场景。

边界:

- 临时脚本可简化，但不能静默吞错。

阻断:

- 引擎层吞异常并返回假正常值。
- 宽捕异常没有记录原因。
- 错误信息泄漏 token、password、key 等敏感字段。

## 9. 日志语义

触发:

- 异常分支。
- 关键业务节点。
- 外部调用入口/出口。
- 状态转移。

动作:

- 异常日志保留 traceback。
- 日志带足够业务上下文，能帮助定位。
- 敏感字段必须脱敏。
- 高频循环避免 INFO 噪音，改 DEBUG 或汇总。

边界:

- 纯计算函数不强制日志。
- 一次性脚本可以简化，但错误仍要可见。

阻断:

- except 分支无可追踪日志。
- 日志暴露敏感信息。
- 日志只有“failed”但没有定位上下文。

## 10. 配置语义

触发:

- 新增配置。
- 新增环境变量。
- 新增 secret。
- 修改运行时行为开关。

动作:

- 配置集中管理，不散落读取。
- secret 使用脱敏类型或脱敏输出。
- 生产必需配置不能给危险默认值。
- `.env.example` 只放示例，不放真实 secret。

边界:

- 非长期脚本可局部读取参数，但必须避免硬编码 secret。

阻断:

- 业务代码到处读取环境变量。
- secret 被写入日志、文档、默认配置。

## 11. 公共接口契约

触发:

- 新增或修改公开函数。
- 修改跨模块调用。
- 修改 API 请求/响应。
- 修改返回结构、异常类型、副作用。

动作:

- 公共返回结构使用 dataclass / TypedDict / Pydantic 等结构化类型。
- 修改签名前先查调用方。
- 破坏性变更必须说明兼容策略或迁移方式。

边界:

- 模块内部私有函数可轻量处理。
- 实验性接口需明确标注不稳定。

阻断:

- 公共接口返回裸 `dict` / `Any` 且调用方依赖字段。
- 改签名不查调用方。
- 删除返回字段或改字段类型但无兼容说明。

## 12. 测试语义

触发:

- 新增公共行为。
- 修 bug。
- 修改异常路径。
- 修改外部依赖调用。

动作:

- 正常路径、异常路径、边界值至少覆盖与本次风险相关的部分。
- 外部依赖失败要有测试或可验证降级。
- 回归 bug 要优先补复现测试。
- 测试应独立、可重复、不过度依赖顺序。

边界:

- 小改可用局部验证替代完整测试，但必须说明未覆盖风险。

阻断:

- 修复 bug 但没有复现或回归验证。
- 公共接口变更没有测试或调用方验证。

## 13. 本文件反模式

- 把 Ruff / basedpyright / import-linter 能查的规则写成 AI 自觉要求。
- 在老项目里强行套新范式。
- 为小脚本引入复杂抽象。
- 修改公共契约却不查调用方。
- 只追求代码漂亮，不考虑运行、排障、测试和长期维护。
