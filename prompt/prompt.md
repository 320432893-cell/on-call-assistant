> 此文档浓缩"专属规则约束"与"AI 实际承担的角色"，作为面试作品的协作流程展示。
>
> 边界说明：本文是展示/面试材料，不是运行时规则主源。当前规则主源是
> `.ai-config/AGENTS.md` + `.ai-config/rules/`；实际加载方式取决于使用的 AI 工具、
> 规则索引和 hook 触发结果。

## 一、专属规则（强约束）

规则文件主版本存于 `.ai-config/AGENTS.md` + `.ai-config/rules/`，
通过项目规则入口、按需读取和 hook 激活共同约束 AI 行为。

### 1.1 决策流程（强制阻断）

```
用户输入
   ↓
[项目类型判定]：探索型 / 收敛型 / 救火型
   ↓
[四维自检]：What / How / Feedback / Scope
   ↓
置信度判断：
  ├─ 4 维齐 → 高置信度 → 按类型流程执行
  ├─ 3 维齐 → 中置信度 → 标注不确定项执行
  └─ ≤2 维 → 【强制阻断】等用户补齐
```

**阻断条件下 AI 不得**：
- 以"先试试"绕过
- 信息不足时输出代码
- 用户没明确确认就执行不可逆操作

### 1.2 输出渠道约束（强制）

- **禁止**对话框中输出代码内容（包括完整文件、配置文件）
- **禁止**让用户手动复制粘贴可用 Edit/Write 工具执行的修改
- **禁止**把可 Bash 执行的命令以"请你运行"的形式抛给用户
- 一切代码与命令**必须**通过 Write / Edit / Bash 工具直接执行
- 对话只保留**结论、影响说明、自然语言解释**

### 1.3 高风险操作阻断

删除文件 / `force push` / 改核心函数签名 / 影响生产环境 → 必须先说明"内容、影响、不可逆程度"，**等用户确认后**才能继续。

### 1.4 探索型必须方案对比

新项目 / 架构决策 → 必须输出：
- 至少 2 个方案（思路、好处、代价）
- 推荐方案 + 理由
- 待确认清单
- 用户确认前**不得**输出代码

### 1.5 收敛型必须影响分析

旧项目改动 → 执行前向用户说明：改动目标、涉及文件、风险等级（低/中/高），待确认后执行。

### 1.6 回滚方案自检

执行改动前必须输出：
- 改动类型
- 当前状态保存方式（git stash / commit / 备份）
- 回滚方式
- 回滚验证点

任一条不明确 → 阻断。

### 1.7 工具偏好与环境

- 中文回答，代码注释用中文
- pip 用清华镜像 `-i https://pypi.tuna.tsinghua.edu.cn/simple`
- 新建虚拟环境前需用户确认
- IDE 按项目/用户环境确认；当前规则默认 VS Code
- 第三方库引入：优先现代替代方案、最终选择权在用户

## 二、AI 在本项目的实际作用

不是"一键生成代码"，而是**按规则被驱动的协作伙伴**。

### 2.1 接手新项目（执行流程）

```
1. 读文档（README / AGENTS.md / 项目总结）
2. 找入口（GUI handler / CLI main / Service 公开方法，3-8 个）
3. 画调用链（入口→第一层→第二层）
4. 识层级（UI / Service / Engine / IO）
5. 标状态机（如适用）
6. 生成/更新项目记忆层，向用户确认
```

当前项目记忆层：`docs/PROJECT_MAP.md` / `docs/AI_HANDOFF.md`。

### 2.2 重大决策点的对话节奏

| 阶段 | AI 做的 | 用户做的 |
|---|---|---|
| 讨论 | 给方案对比 + 影响分析 | 确认方案、做选择 |
| 调试 | 加日志 / 临时观测点 | 执行取证 / 反馈结果 |
| 修改 | 在确认范围内改代码 | 确认范围 / 验证结果 |
| 完成 | 复查 / 汇报 | 验收 |

### 2.3 本项目典型协作样本（节选）

| 决策点 | AI 提供方案 | 用户拍板 |
|---|---|---|
| Phase3 工具集 | 方案 A：1 个 readFile / 方案 B：3 个工具 | A（贴合题面） |
| LLM Provider | 5 家分别实现 vs 3 类协议抽象 | 3 类协议（最少代码覆盖最广） |
| 状态机 | 4 状态精简版 vs 6 状态完整版 | 4 状态（去掉与题面冲突的状态） |
| Phase2 命中率优化 | A query 改写 / B lexical rerank / C RRF 融合 / D 不改 | B → 改后实测发现 C 更差 → revert 回 B |
| UI 改造范围 | 我想做大改 vs 用户只要"左右两栏 + 暂停" | 只做轻量两件事 |

**关键观察**：好几次 AI 主动想"做完美"，被用户拉回到"够用就行"，节省了几小时工作量。

### 2.4 边界把控

AI 自检了几个不该做的：
- 用户给的真实 API Key 出现在 `.env.example` → 立即提示泄漏风险 + 引导清掉
- 杀别人启动的 uvicorn 进程 → 按 AGENTS.md §4.3 高风险操作，问"杀 / 不杀"再动手
- baseline commit 前 `D:\python` 整目录 untracked 且无 .gitignore → 主动建 `.gitignore` 才入库，**避免 1.4GB `.venv` 和真实 API Key 入库**

## 四、为什么这套规则有效

1. **强制阻断 + 方案对比**：避免 LLM 信息不全时编造或盲跑
2. **影响分析 + 回滚方案**：每次改动可控、可回滚、可审计
3. **输出渠道约束**：所有改动用工具直接执行，对话保持干净，便于审阅
4. **用户始终掌控决策权**：AI 提建议、做执行；最终选择权在用户

→ 结果：项目 11 个 commit 干净落地，3 个 Phase 题面验证全过，
  没有产生废弃方案的代码污染。

## 五、对面试官的话

本作品**不是"AI 一键生成"的演示**，而是展示：
- 如何**用规则约束 LLM**，把它从"写代码工具"变成"按流程协作的工程伙伴"
- 如何在**复杂决策点**给出方案对比，让人始终是决策中心
- 如何把**产品经理思维**（用户故事 / 取舍 / 优先级）注入到 AI 协作中

工程实现是 AI 写的，决策与取舍是我做的。
